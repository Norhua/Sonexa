## 追问、选项与用户选择

问题：你说的“在复核队列只提供‘接受’和‘跳过’这两个选项”，是仅指候选行按钮，还是也要删除条目级的其他处置动作？

1. **只调整候选行按钮（推荐）**：上游候选的行内动作只有“接受”或“跳过”；保留条目级的“无需匹配”“移出队列”“无一匹配”，失败时仍可立即重试。
2. **整个复核页只保留接受和跳过**：复核页只保留接受候选和跳过条目两种处置动作；移除“无需匹配”“移出队列”“无一匹配”，保留搜索和失败重试。没有结果的条目只能继续搜索或跳过。

**用户选择：1，只调整候选行按钮。**

## 修改目的与 review 结论

- 现有生命周期：`queued → matching → imported / review / queued(退避) / failed`；人工接受和无需匹配经准入事务结束；合并、跳过和丢弃为终态。重启将 matching 重置为 queued。现有 setStatus 不检查终态，迟到改搜可能复活条目。
- 现有决策：无绑定本地曲名/艺术家检查 → 上游变体检索 → 曲名版本与旁证过滤 → 高置信集合 → library 同组/同录音/同发行位置检查 → 已有发行优先/总曲数/国家/稳定身份 → 准入计划与事务提交。库内精确身份重复已有提交保护，但前序复核判定可能阻止到达提交。
- 缺少活动条目去重；文件路径长期保存到批次并在复核页显示。将改为保留原始内容与内部批次身份，不保留源文件路径/行号。
- ResolveLocal 把 ISRC 和无绑定文本命中升级为本地收藏，行内合并误用 recording 证据。改为只以来源 + track 标识确认候选已绑定。
- 3253212：艺术家精确足以让两个专辑不匹配的现场版成为高置信，跨组检查因此否决完全匹配单曲。自动候选先取三字段精确子集（如果存在），其余仅供人工参考；不绕过成员确认或同 track 歧义约束。
- 复核表单的来源/地区未随条目恢复，候选列误用上一个条目的选择。按条目保存草稿和搜索状态；表格以实际结果来源能力呈现，按钮显示旋转动画。

## 设计边界

- 同一活动目标只保留一个可处理条目；保留各批次输入的审计/统计关联，被吸收项为 merged（与 merged_into 曲库目标区分），不同原始输入聚合展示，完全重复内容去重。
- 文本证明要求完整且非截断的曲名/艺术家/专辑、去非版本注释后的精确比较，已知位置与时长冲突不合并；或者双方自动可判定的唯一精确 track 身份一致。候选集合仅有交集、同 ISRC/recording 均不是合并依据。
- 搜索后先用可靠候选检查库内身份及输入与当前曲目一致性；确认后直接 skipped，不先进入 review，不修改库中用户字段。证据不足继续复核。
- 活动合并和状态写入在事务内执行，终态不得被改搜/重试复活。来源差异继续由 provider 包提供；不新增 switch source 业务分发。
- 本轮仅维护本目录 spec-diff，不修改主 spec、不创建 OpenSpec change。数据库结构不要求兼容历史应用数据。
