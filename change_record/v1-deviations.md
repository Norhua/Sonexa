## 一、应用外壳与导航（`platform/app-shell`）

### 1.1 侧栏四组导航 + 独立搜索入口与层级缩进 `[需改 spec]`

**spec 现状**（`platform/app-shell` → `Requirement: 侧栏导航分组`）：

> 侧栏 SHALL 包含四个分组：资料库（全部曲目 / 最近添加 / 艺术家 / 专辑）、歌单、标签、任务。
> 上游搜索 SHALL 是独立入口，不置于资料库分组内。

**改为**（对齐 Apple Music 的侧栏形态）：

```
搜索                      ← 顶层独立入口，无分组标题
[资料库]  最近添加 / 全部曲目 / 艺术家 / 专辑
[歌单]    ＋ 及各歌单
[标签]    ＋ 及各标签
[任务]    导入队列 / 复核队列
────────────────────────
设置                      ← 仅「设置」常驻在侧栏底部
```

变更点：

1. **「上游搜索」独立入口取消**，并入新的「搜索」页（见 2.1、2.2）。
2. **分组内的二级项需缩进**，与分组标题形成层级（此前平级，视觉上读不出从属关系）。
3. **「资料库」组内顺序**改为 最近添加 → 全部曲目 → 艺术家 → 专辑。
4. **「任务」组不再置于侧栏底部**，与其余分组同列于滚动区内；底部只保留「设置」。
5. **「任务」组拆为两个页面**：「导入队列」与「复核队列」（见 1.2）。

### 1.2 任务区拆为「导入队列」「复核队列」两个页面 `[需改 spec]`

**spec 现状**（同上 → `Scenario: 任务区进度`）：

> 任务区常驻显示导入进度（已处理/总数）与复核待处置数，点击可展开详细进度与日志

**改为**：任务区是**导航分组**，不再是「就地展开详细进度与日志」的面板。

- **导入队列**（新页面）：批次信息、进度条、各状态计数（已入库/待复核/排队中/失败）、
  暂停与恢复、以及完整的匹配日志。原「侧栏内展开日志」的交互移到这里。
- **复核队列**（既有页面）：内容不变。
- 侧栏两行仍保留常驻的轻量指示：导入队列行显示 `已处理/总数` 与细进度条，
  复核队列行显示待处置数徽章——「常驻显示进度与待处置数」这一条仍然满足，
  变的只是「详细进度与日志」的落点。

### 1.3 顶栏取消，红绿灯让位给侧栏 `[需改 spec]`

**spec 现状**：无显式条款描述顶栏，但实现中存在一条含 应用名 + 全局搜索框 + 导入按钮 +
主题切换 的顶栏。

**问题**：macOS 使用 `TitleBarHiddenInset` 时，窗口红绿灯浮在内容之上，与顶栏左侧的
应用名重叠。

**改为**：

- **整条顶栏取消**。应用名不再在界面内显示（窗口标题栏已有）。
- 红绿灯所在区域让给**侧栏顶部**：侧栏顶部留出安全区并设为可拖拽窗口区域。
- 原顶栏上的三个入口重新安置：
  - 全局搜索框 → 取消，改为「搜索」页 + 各视图右上角的搜索框（见 1.5、2.1）。
  - 「导入」按钮 → 取消。导入从「导入队列」页发起。
  - 深色/浅色切换 → 取消。主题只在设置中切换（设置里本就有该项）。

建议在 `platform/app-shell` 新增一条 `Requirement: 窗口外壳与红绿灯安全区`。

### 1.4 艺术家视图未选中时不再显示曲目表格 `[纯 bug 修复]`

`platform/app-shell` 已规定艺术家视图是「按 artist_id 过滤的标准曲目表格」，
但实现里主区无条件渲染表格，而 `goTo('artists')` 并不触发 `loadTracks()`。
于是从「全部曲目」切到「艺术家」时上一屏的行仍留在表格里，
读起来像是「这些曲目属于某位艺术家」。

改为与专辑视图一致：未选中时给出「从左侧选择一位艺术家」。

### 1.5 名单就地查找与曲目搜索区分 `[需改 spec]`

艺术家/专辑页右上角的 `ViewSearchBox` 过滤**中列名单**（艺术家名/专辑名），
不经曲目 FTS；中列顶部没有另一个查找输入框。
全部曲目、最近添加、歌单、标签页右上角的搜索则经 FTS 与 TrackFilter 筛选曲目。
三栏页目前没有独立的曲目 FTS 输入；如需同时提供名单查找与曲目检索，需另行确定布局。

### 1.6 设置改为模态弹窗 `[需改 spec]`

**spec 现状**（`platform/settings`）：设置以「六个分组」呈现，未规定是页面还是弹窗；
实现中为主内容区的一个视图。

**改为**：设置为**模态弹窗**，从侧栏底部的「设置」打开，左侧分组导航 + 右侧表单的结构不变。
理由：设置不是浏览目的地，占用主内容区会打断当前浏览位置。

「前往设置」类跳转（全局出网禁用提示、导入向导内的提示）改为**直接打开该弹窗**。

### 1.7 头部区域统一为「左标题 / 右操作区」并去掉分割线 `[需改 spec]`

**用户报告（第二轮 1、2）**：艺术家与专辑视图的搜索框被放进了中间栏列表上方，
而不是窗口右上角；标题盒子还带着一条突兀的底边。

**改为**（对齐 Apple Music，两种页面结构共用同一套规则）：

| | 两栏页面（全部曲目/最近添加/歌单/标签） | 三栏页面（艺术家/专辑） |
| --- | --- | --- |
| 大标题 | 主区左上角 | **中间栏**左上角 |
| 操作区（排序 + 搜索） | 主区右上角 | **主区**右上角 |

- 两者恒在同一水平线上并垂直居中，靠共用同一个高度常量保证——
  各写各的 padding 必然漂移。为此抽出 `PaneHeader` 作为唯一的高度来源。
- **去掉全部页面顶部的横向分割线**，头部与下方列表连成一片。

新增组件：`PaneHeader`（高度 + 垂直居中 + 窗口拖拽区）、`ViewSearchBox`、`SortMenu`。
（`ViewSearchBox` 使用 Volt `InputText`，`SortMenu` 使用 Volt `Menu`；
搜索页的主输入/范围/高级条件/搜索按钮也接入 `PaneHeader`，地区选项在其下方独立一行。）

**实现约束**：`--wails-draggable` 会从父级**继承**给子元素，因此头部内的输入框与
按钮必须各自声明 `no-drag`，否则点一下就开始拖窗口。

### 1.8 列表新增排序入口 `[需改 spec]`

排序菜单提供以下维度：

- 曲目表格：默认顺序 / 标题 / 艺术家 / 专辑 / 年份 / 时长
- 名单栏（艺术家、专辑）：名称 / 曲目数（专辑另有艺术家）
- 再次点击同一维度即反向，默认顺序除外

排序在**前端就地**做，列表顺序、选择与重排使用同一份数据。

**当前排序契约**（见第二十节）：

- 普通曲目表格的列头也是排序入口，与右上角菜单共用 `sortKey` / `sortDesc`。
  专辑清单的列头不可排序，保持后端碟号/曲序；艺术家/本地搜索中的曲目表格可点列头排序。
- `lib/trackRows.ts` 是唯一曲目比较器，使用 `Intl.Collator('zh-Hans-CN',
  { numeric: true, sensitivity: 'base' })`，同值稳定，缺失值始终最后。
  `App.vue` 不再计算第二份排序。DataTable 的 `lazy` 仅关闭其内部二次排序；
  并非远程分页。选择模型、渲染和重排读取同一份 `orderedRows`。
- 默认顺序总是恢复后端顺序，不显示无意义的升/降序；再次选默认也不翻转。
- 排序图标在已排序、悬停或键盘聚焦时可见。
- 歌单只有**无筛选且默认排序**时才能拖动，避免把可见子集提交为完整顺序。
- 名单栏排序仍由艺术家/专辑视图管理，与曲目排序互不混用。

## 二、搜索（`library/search`）

### 2.1 取消全局搜索框，改为「搜索页 + 视图内搜索框」两处 `[需改 spec]`

**spec 现状**（`library/search` → `Requirement: 快速搜索的作用域跟随当前视图`）：

> 顶栏的快速搜索框 SHALL 以当前视图为作用域，并在占位文案中明示该作用域。

**改为**：不存在「顶栏」，快速搜索拆为两个落点：

1. **搜索页**（侧栏顶层入口）：独立页面，可搜**资料库**或**某个上游**，
   右上角以下拉菜单选择搜索范围（见 2.2）。高级搜索**只在搜索页提供**。
2. **视图内搜索框**：全部曲目 / 最近添加 / 歌单 / 标签的右上角搜索
   经 FTS 与 TrackFilter 在当前视图就地筛选，不跳页、显示可清除的筛选 chip。
   艺术家 / 专辑页右上角输入过滤中列名单，不是曲目 FTS（见 1.5）。

原 `Scenario: 在歌单页搜索` / `Scenario: 在全部曲目页搜索` 的行为仍成立，
只是搜索框位置由「顶栏」改为「当前视图右上角」。

### 2.2 搜索范围为下拉单选，而非平铺多选 `[需改 spec]`

**spec 现状**（`upstream/search`）：上游搜索页以复选框勾选多个上游并发查询，结果分「聚合」
与各上游标签页。

**问题**（用户报告 9）：多选并发时，不同上游的结果落进同一个聚合列表，
来源难以区分、排序也不可比。

**改为**：

- 搜索页右上角为**单选下拉**：`资料库 / MusicBrainz / iTunes / …`，**默认「资料库」**；
  切到上游时**默认 MusicBrainz**。选项从 provider 注册表动态渲染，不平铺、不硬编码。
- 一次搜索**只查一个**上游，因此不再有「聚合」标签页与跨上游合并排序。
- 复核队列内的上游选择本就是单选下拉（spec 已如此规定），两处现在一致。

需同步修改 `upstream/search` 中关于「多上游并发 / 聚合标签页」的条款。

### 2.3 高级搜索改为「条件选择器」形态 `[需改 spec]`

**spec 现状**（`library/search` → `Requirement: 高级搜索的条件`）：

> 高级搜索面板 SHALL 提供：曲名、艺术家、专辑三个文本条件，年份区间，标签，
> 以及载体、国家或地区、类型三个下拉条件。

**改为**：

- 面板**不再默认铺开全部条件**，改为「从下拉列表选择条件并添加」，已添加的条件才渲染输入框，
  每条可单独移除。
- v1 支持的条件收敛为四项：**曲名、艺术家、专辑、标签**。
  年份区间、载体、国家、类型四项从高级搜索中**移除**。
- 高级搜索**只在搜索页提供**，其他视图的右上角搜索框只做单字段快速搜索。
- 面板**点击面板外任意处即关闭**（此前只有点「搜索」才关，属 bug，见 4.4）。

## 四、纯 bug 修复（spec 无需改动）

以下为实现未达成 spec 已有要求之处，修复后与 spec 一致。

### 4.1 `window.prompt` / `window.confirm` 在 Wails(macOS) 上静默失效 `[纯 bug 修复]`

**用户报告 4**：歌单和标签的「＋」点击无反应。

**根因**：Wails v2 的 macOS 前端基于 WKWebView，而 Wails 未实现
`webView:runJavaScriptTextInputPanelWithPrompt:` 与 `runJavaScriptConfirmPanel:`
两个 `WKUIDelegate` 方法。因此 `window.prompt()` 恒返回 `null`、
`window.confirm()` 恒返回 `false`，**不报错、不弹窗**。

受影响的交互（均静默失效，不止「＋」一处）：

| 位置 | 调用 | 表现 |
| --- | --- | --- |
| 侧栏「＋新建歌单/标签」 | `window.prompt` | 无反应 |
| 侧栏右键歌单/标签（重命名/删除） | `window.prompt` | 无反应 |
| 曲目右键「添加到歌单/添加标签」 | `window.prompt` | 无反应 |
| 曲目右键「删除」 | `window.confirm` | 恒为取消，删不掉 |
| 侧栏右键删除歌单/标签 | `window.confirm` | 恒为取消，删不掉 |

**修复**：全部改为应用内的 `PromptDialog` / `ConfirmDialog` 组件。
新增约定：**前端不得使用 `window.prompt` / `window.confirm` / `window.alert`**。

建议在 `platform/app-shell` 补一条约束条款。

### 4.2 上游 503 未重试，导致导入大面积失败 `[纯 bug 修复]`

**用户报告 8**：导入 10 条只成功 1 条；日志中大量
`[匹配失败]…（已达重试上限，不再自动重排）` 与 `上游返回 503 Service Unavailable`。

**根因**：`internal/provider.Client` 定义了 `Retry RetryPolicy` 字段，
`DefaultRetryPolicy()` 也赋了值，但 **`Client.Get` 里根本没有重试循环**——
`c.do()` 只调用一次，任何一次 503 都直接向上抛错。

而 MusicBrainz 在**完全遵守 1 req/s 的前提下**仍会高频返回
`503 {"error": "The MusicBrainz web server is currently busy. Please try again later."}`
（`Retry-After: 0`）。实测 20 次串行请求（间隔 1s）：**11 次 503，成功率仅 45%**。

叠加效果：条目级重试上限 5 次，单次请求成功率 ~45% 时，
5 次全败的概率约 5%，但每次条目级重试要等 2/4/8/16s 的退避，
用户观感就是「大部分都失败了」。

**修复**：在 `Client.Get` 中实现传输层重试——

- 对可重试错误（429 / 5xx / 超时 / 临时网络错误）按策略重试，
  默认 `TransportRetryPolicy`：最多 6 次尝试、基数 1s、指数退避上限 20s、带抖动（历次实测见第七节）。
- 每次重试**重新取令牌桶令牌**，不绕过限流。
- 尊重 `Retry-After`（比退避长时以它为准）。
- 遵守 `ctx` 取消。

实测：同样 10 条输入，成功率从 1/10 提升到 9/10。

条目级重试（`importer.Runner`）保持不变，作为传输层重试之上的第二层。

### 4.3 导入列映射：中文「歌手名 / 专辑名」未被自动识别 `[纯 bug 修复]`

**用户报告 7**：导入默认不自动匹配艺术家和专辑信息，需要手动选择。

**spec 现状**（`import/table-import` → `Requirement: 列映射词典`）已要求
「词典 SHALL 同时包含中文与英文的常见写法」，故属实现 bug。

**根因**：`importer.MapColumn` 的「包含匹配」阶段有一条
`minSubstringAliasLen = 3` 的过滤，本意是防止 `Note` 因含 `no` 被误判为音轨号。
但它按**字符数**一刀切，把所有 2 字中文别名（`歌手`/`专辑`/`唱片`/`艺人`/`歌集`…）
全部排除在包含匹配之外。于是：

- `歌手名` → 与 `歌手` 不完全相等，且 `歌手` 被长度规则跳过 → 判为「忽略」
- `专辑名` → 同理 → 判为「忽略」

**修复**：长度门槛按字符类型区分——

- **非 ASCII（CJK）别名**：≥ 2 字即可参与包含匹配（`歌手`/`专辑` 足够特异）；
  1 字的 `年`/`碟` 仍只允许完全相等。
- **ASCII 别名**：维持 ≥ 3 字符（`no`/`#` 仍只允许完全相等）。

并补充若干常见别名。

### 4.4 高级搜索面板点击外部不关闭 `[纯 bug 修复]`

**用户报告 10**：高级搜索只有点「搜索」才会关闭，点页面其他地方不会关闭。

**修复**：面板注册 `pointerdown` 外部点击与 `Esc` 关闭。
（面板现使用 Volt 的 `Popover`，外部关闭由它负责；
行为不变，见第二十节。）

### 4.5 设置里的主题下拉会翻转而非设值 `[纯 bug 修复]`

主题下拉的 `@change` 无条件调用 `theme.toggle()`，
因此在暗色下选「暗色」也会翻到亮色。改为按所选值调用 `theme.set()`。

同时：主题由 theme store 持有（需同步读取以避免首帧闪白），
保存设置时把当前主题写回草稿，免得 `settings.json` 里留一个与界面不符的值。

### 4.6 iTunes 搜索结果从来没有缩略图 `[纯 bug 修复]`

**用户未报告，审查时发现。**

`provider.Candidate.ThumbURL` 由 iTunes 解析器填好，`coverLadder` 与
`BuildCoverRefs` 也都为「无 release 级标识、只有一个基准图地址」这条路径
准备好了逻辑。缺的只是绑定层 `toRows` 里的一次赋值——
`CandidateRow.ArtworkURL` 恒为 `nil`，`ThumbKey` 又只在 `ReleaseRef` 非空时
才计算，于是 `BuildCoverRefs` 把每一条 iTunes 行都跳过，
iTunes 结果的封面列永远是占位方块。

**修复**：`toRows` 带出 `ArtworkURL`，并在没有 `ReleaseRef` 时以基准图地址
作为缓存键的取源（与 `BuildCoverRefs` 的 `sourceRef` 回退保持一致）。

### 4.7 复核队列里改搜出来的候选，重载后退化成三列 `[纯 bug 修复]`

**用户未报告，审查时发现。**

同一个 `import_item.candidates` 列上写着**三种**不同形状的快照：

| 写入方 | 形状 |
| --- | --- |
| `importer.Runner`（管线分流） | `[]matching.ScoredCandidate` |
| `App.ResearchReviewItem`（用户改搜） | `[]CandidateRow` |
| `Runner.localCandidateSnapshot`（疑似重复） | 自定义的简化结构 |

而 `parseCandidateSnapshot` 只认第一种和第三种。`[]CandidateRow` 解析成
`[]ScoredCandidate` 时 `Candidate.MatchRef` 为空，于是掉进第三种分支——
那个分支只读 badges/action/title/artist/album 五个字段。
表现：用户在复核队列改搜出一批候选，界面显示正常；一旦队列重载
（处置任一条目、切走再切回），置信度、年份、时长、载体、厂牌全部变成占位短横线。

**修复**：补上 `[]CandidateRow` 这一支，且解析时重新做本地判定——
入库/合并状态可能在存快照之后已经变了，徽章与动作不该随快照冻结。

**建议**：spec 里应明确复核队列候选快照的**单一**序列化形状，
现在这一列同时承载三种结构本身就是缺陷来源。

### 4.8 曲目右键菜单点击表格之外不关闭 `[纯 bug 修复]`

`TrackTable` 只在自身根元素上监听 `click` 关闭菜单，
点侧栏或页头时菜单会一直悬在那儿。改为监听 window 的 `pointerdown`，
与侧栏的右键菜单一致。
（两处右键菜单现均使用 Volt 风格 `ContextMenu`，关闭由它负责；行为不变。）

### 4.9 导入进度永远到不了 100% `[纯 bug 修复]`

**用户未报告，审查时发现。**

`ImportBatchView.TotalRows` 取的是 `import_batch.total_rows`（文件行数），
而 `Processed` 来自 `import_item` 的状态统计。缺少曲名的行在提交时
就被跳过、从不写进 `import_item`——于是只要有一行被跳过，
进度条就停在 90% 几再也不动。

**修复**：分母改为 `stats.Total`（真正入队的条目数）；
文件行数另存为 `FileRows`，界面上写明「文件 N 行，M 行缺曲名已跳过」。

### 4.10 同一条候选查三遍库 `[纯 bug 修复]`

`badgesFor` / `actionFor` / `noteFor` 三个函数各自调用一次
`matching.ResolveLocal`，而后者每次最多查三张表（match_ref → ISRC → 文本）。
一个 200 条、每条 10 个候选的复核队列因此要打 6000 次查询，
其中三分之二是重复的。

**修复**：合并为 `applyLocalMatch`，一次判定同时填徽章、动作与附注。

### 4.11 指数退避的抖动会削短 Retry-After `[纯 bug 修复]`

`JitteredBackoff` 对 `Backoff` 的结果整体施加 ±25% 抖动，
而 `Backoff` 在 `Retry-After` 更长时会返回 `Retry-After`。
于是上游明确要求「等 30 秒」时，我们可能只等 22.5 秒——
抢跑只会招来继续限流。

**修复**：抖动只作用于自己算出的指数退避，再与 `Retry-After` 取较大者。

## 五、构建告警

`~/.go/bin/wails build` 成功，但绑定生成阶段重复输出 5 次：

```
Not found: time.Time
```

**根因**：Wails 的 TS 模型生成器不认识 `time.Time`，凡是绑定层导出的结构体里
出现 `time.Time` / `*time.Time` 字段就会打印该行。命中两处：

- `bindings_review.go` → `ReviewItem.LastErrorAt *time.Time`
- `bindings_albums.go` → `AlbumDetail.FetchedAt *time.Time`

（`internal/store` 里的 `time.Time` 字段经由这些结构体间接触达。）

**修复**分两类：

1. **绑定层导出的时间** → 改用 `*string`（RFC3339），在绑定层用
   `formatTime` 转换。前端本就是 `new Date(...)` 消费，字符串同样适用，
   且生成的 TS 类型从 `any` 变为 `string`，更准确。
   - `ReviewItem.LastErrorAt`、`AlbumDetail.FetchedAt`
2. **前端根本用不到的时间** → 加 `json:"-"`，不再进入模型生成。
   - `store.TrackView.CreatedAt`（「最近添加」的排序在 SQL 里做）
   - `store.TrackMetadata.MatchedAt`
   - `provider.Detail.FetchedAt`（只在 Go 侧流转）

修复后 `wails build` 的告警数从 5 条降到 0 条。

**新增约定**：绑定层导出的结构体不得出现 `time.Time`/`*time.Time` 字段。
需要时间就导出 RFC3339 字符串。

## 九、MusicBrainz 检索算法重做（`upstream/musicbrainz`、`matching/*`）`[需改 spec]`

**用户报告（第二轮）**：导入 10 行的样例表格只有 2 条入库（3253212、Tetra.），
且 Tetra. 选错了版本。按用户核对，表中只有第 5/8/10 条在 MB 里确实没有。

修复后：**7 条直接入库 / 3 条进复核**，与用户的核对完全一致。

三处根因彼此独立，任何一处不改都到不了 7 条。

### 9.1 查询形态：三字段 AND → 锚定并联

**spec 现状**（`upstream/musicbrainz`）：未规定检索式的组合方式；
实现为 `recording AND artist AND release`。

**问题**：`artist:` 只匹配 recording **自己的** artist credit，而导出表格的
歌手列时而是碟的署名、时而是唱的人。实测（真实 MB）：

| 查询 | 命中 |
| --- | --- |
| `recording:"綿雪の夢" AND artist:"Crest" AND release:"狼と巫女とお菓子の家"` | **0 条** |
| `recording:"綿雪の夢" AND (release:"狼と巫女とお菓子の家" OR artist:"Crest")` | 1 条（正确） |

样例里「綿雪の夢」写 Crest、录音署名是 ハトリアヤ；「夕立」写 3L、录音署名是
CROW'SCLAW——两行的歌手列都不是录音署名，而歌集列两次都对得上。

**改为**：曲名是唯一的必须项，歌集/歌手/歌手备选写法是**并联**的锚点：

```
recording:"曲名" AND (release:"歌集" OR artist:"歌手" OR artist:"备选写法")
```

备选写法取自歌手列括号里那种写法（`3L（スリーエル）`），上限 2 个。

### 9.2 曲名闸门：词元包含 → 版本标记必须一致

**spec 现状**（`matching/confidence`）：规定「曲名不匹配即丢弃」，并统一定义了
含「词元集合包含」的三级文本比较；当前曲名不再与署名/歌集共用同一种比较。

**问题**：`{tetra}` ⊆ `{tetra, offvocal}`，于是 `Tetra.` 与
`Tetra. (off vocal)` 判成模糊匹配——这正是用户报告的「选错了版本」。

**改为**：新增 `CompareTitle`，曲名走它而不走 `CompareText`：

1. 两侧的**版本标记集合不一致 ⟹ 不匹配**，无论其余部分多像
2. 剥掉非版本注释后相等 ⟹ 精确（`綿雪の夢（繁雪之梦）` == `綿雪の夢`）
3. 括号里是上游用的那个写法 ⟹ 精确（中文平台常写「译名（原名）」）
4. 字符串相似度达标 ⟹ 模糊

版本标记不止在括号里找：`Tetra. -movie ver.-` 用破折号，同样是另一条录音。
`feat.` / `ft.` / `with` **不算**版本标记——它们标的是参与者，上游把
`By the Seaside (feat. Kitsui Akira)` 的录音名记作 `By the Seaside`。

署名与歌集仍走 `CompareText`：它们是旁证不是准入，宽一点是合适的。

### 9.3 署名判定：认同一位艺术家的三种异写

**spec 现状**：未规定署名的比较方式。

**问题**：导出表格里署名的写法差异几乎总是三种固定形态之一，而它们说的都是
同一位艺术家。判成不匹配会让本该直接入库的行落进复核队列（实测卡住 3 条）：

| 形态 | 例 |
| --- | --- |
| 括号里是另一种写法 | `原田瞳（原田ひとみ）` ↔ `原田ひとみ` |
| 括号里是声优 | `茅野愛衣` ↔ `霞ヶ丘詩羽(CV.茅野愛衣)` |
| 末尾挂着 feat. 从句 | `Kirara Magic` ↔ `Kirara Magic feat. Kitsui Akira` |

**改为**：新增 `CompareCredit`，在 `CompareText` 之上多认这三种形态。
放宽只针对「同一位艺术家的不同写法」——`Suzumiya Haruhi` 与
`Suzumiya Haruhi Band` 仍只算模糊。

### 9.4 检索前剥掉导出噪音

新增 `SearchCore`：去截断省略号 → 抹掉截断切在注释中间留下的半个左括号 →
剥掉**非版本**的括号注释。

`心の羽根（ドラゴンボール改ver.）（心...` → `心の羽根`

版本标记那一段**保留**：`That Girl (DJLIU Remix)` 必须带着 remix 去查，
否则上游返回的几百条裸 `That Girl` 里根本没有那条 remix。

### 9.5 检索阶梯从 4 级缩到 3 级

**spec 现状**（`matching/pipeline`）：「渐进式变体，首个高置信即停，上限 4 个」。

**改为**三级，且**删掉「原串」那一级**：

```
L1 锚定并联   曲名主干 AND（歌集 OR 歌手 OR 备选写法）   ← 绝大多数只花这一次
L2 取内层     译名那一层作曲名，锚点不变
L3 曲名独行   连歌集带歌手都对不上时，只用曲名
```

删原串的理由：上游的引号短语是**子短语**匹配，主干的结果集是原串结果集的
**超集**（`recording:"That Girl"` 会返回 `That Girl (DJLIU Remix)`），
原串那一级只可能命中同一批或更少——它在十条输入上白花 9 次请求。

推进条件从「有高置信」改为「有过得了曲名闸的候选」：`That Girl (DJLIU Remix)`
的锚定级会返回几百条同名的裸 `That Girl`，按「返回了就停」阶梯会停在一堆用不上的
候选上，更宽的一级永远不会被试到。

剥离变体不再扣分：曲名是否对得上由 `CompareTitle` 判定，
不需要再用分数去压制误剥离。

### 9.6 跨发行组的两个例外 —— 已于第三轮撤销

本节原先记录「为跨发行组新增两个有客观依据的例外」（全部候选同一 recording、
恰好一条歌集精确）。**两个例外已在第三轮全部删除**，理由与替代方案见第十节。
这里保留条目只为说明 spec 不需要为它们新增任何条款。

### 9.7 手动检索与「改搜」共用同一套文本处理

**审查时发现，用户未报告。**

`SearchUpstream`（搜索页）与 `ResearchReviewItem`（复核队列的「改搜」）
原先直接把用户输入的原串拼进查询，不做任何剥离。于是同一个
`原田瞳（原田ひとみ）`，导入路径查得到而手动检索查不到——
而用户在复核队列里「改搜」时填的往往正是从表格里复制过来的原串。

**修复**（第五轮已升级为第十八节的彻底统一）：手动检索与改搜直接走
`matching.Engine.Run`，与导入匹配是**同一个函数**，不再各自维护一份文本处理。

`Engine.Run` 内部检索与评分用的是两份不同的输入：变体（剥掉导出噪音的主干）
拿去查上游，原始 `Input` 拿去判分。拿剥离后的串去判分会把这次修复自己抵消掉：
`原田瞳（原田ひとみ）` 剥成 `原田瞳` 之后，让署名对上的恰恰是被剥掉的那个括号（见 9.3）。

### 9.8 参考实现

本次重做参考了本地 `musiclib` 项目的实现
（`internal/musicbrainz/types.go` 的 `RecordingQueryLadder`、
`internal/normalize/annotation.go` 的 `SearchCore` / `TitleAgrees` / `CreditAgrees`）。
那份实现里的实测结论（`artist:` 的语义、子短语匹配、词组级是 OR）经本项目
独立复测确认后才采用。

### 9.9 回归测试

`internal/acceptance/csv_import_test.go` 锁定这次导入的结果（7 入库 / 3 复核）。
候选的形状是拿真实 MusicBrainz 跑一遍抄回来的（曲名/署名/歌集/recording MBID/
release group MBID 照原样），因此不联网、不在仓库里塞几百 KB 响应 JSON，
而「引擎面对上游真实返回的东西会怎么判」这件事被完整钉住。

样例表格本身在 `tmp/`（gitignore），因此**不**作为测试夹具依赖。
需要重跑真实检索时，临时写一个 `SONEXA_LIVE_MB` 门控的测试即可。

## 十、分流规则严格化（`matching/pipeline`、`import/table-import`）`[需改 spec]`

**用户报告（第三轮）**：`世界中の雨` 被直接入库了，但在 MusicBrainz 上能搜到
多个一模一样的条目。

复核真实返回后确认属实：这一行的查询返回 2 条录音，其中正片那条
**挂在 11 张同名发行上**（release group 同一个、状态同为 Official、载体同为 CD、
国家同为 JP、发行日同为 2010-07-21）。实现把它们交给优选阶梯，阶梯逐级比下来
全部相同，最后靠第 6 级的 MBID 字典序收尾——那不是判定，是「随便挑一个」。

用户据此重申了完整的分流规则，并就三处不明确之处做了裁决。本节按裁决改写实现。

### 10.1 分流规则的权威表述

```
1. 先对比本地，疑似重复 → [疑似重复] 输入信息 + 曲目库信息，进复核队列
2. 仅一例高置信         → [直接入库] 曲名 艺术家 歌集名 置信率
3. 多条高置信 & 同一 release group
     → 先过滤 release 类型，优先实体光碟
     → 过滤后只剩一条才 [直接入库] …… 实体release 置信率
4. 多条高置信 & 跨 release group → [进入复核] 输入信息，进复核队列
5. 未找到结果                   → [匹配失败] 输入信息，进复核队列
6. 发生错误（如 503）           → [发生错误] 返回队列，错误信息
7. 完成/暂停 → [导入完成/暂停] 本次导入 X 条，进入复核 X 条，未匹配 X 条，失败 X 条
              （连续 5 次均出错的条目不再返回队列），换行列出全部失败曲目的输入信息
```

### 10.2 规则 3 的收尾：过滤后不止一条时进复核 `[需改 spec]`

**spec 现状**（`matching/pipeline`）：多条高置信同属一个 release group 时
「经优选阶梯选出一条后入库」——阶梯必定产出一条，因此**永远**会自动入库。

**用户裁决**：过滤实体载体后**恰好剩一条**才入库；剩 0 条或剩多条都进复核。

**改为**：

| 同组多条高置信，过滤实体载体后 | 去向 |
| --- | --- |
| 恰好 1 条 | 入库那一条（`OutcomeImportLadder`） |
| ≥ 2 条 | 进复核（新增 `OutcomeReviewManyReleases`） |
| 0 条（全是 Digital Media / 上游没给载体） | 进复核（同上） |

「实体」这一侧不枚举：MB 的载体分类有上百个，列举必漏，而漏掉一个实体格式会让
本该入库的行落进复核。改为枚举**非实体**的那一侧（`LadderConfig.DigitalFormats`，
默认只有 `Digital Media`），其余非空载体皆视为实体。**载体缺失不算实体**——
那是「不知道」而不是「是」，而这一步的产出直接决定要不要替用户入库。

优选阶梯（`SelectRelease`）本身保留：专辑视图选「代表 release」仍然需要它。
变的只是**匹配阶段不再用它替用户做入库决定**。

### 10.3 跨发行组的两个例外全部删除 `[需改 spec]`

**用户裁决**：规则 4 没有例外。

第二轮曾为跨发行组开过两个「有客观依据」的口子（见 9.6）：全部候选同属一条
recording、恰好一条候选的歌集精确匹配。它们把 `you`、`3253212` 两行从复核提到了
入库，代价是规则不再可预期——用户读到「多条高置信 → 复核」，实现却在某些情况下
替他做了决定。两个口子已删除，`dispatch_test.go` 里留了一条守卫用例
（`TestCrossGroupNeverAutoSelects`）防止它们被重新打开。

### 10.4 统计行的四个数互不重叠 `[需改 spec]`

**spec 现状**：未规定「进入复核」与「未匹配」的口径。实现里两个数都取
待复核总数，因此**永远相同**——第二轮的注释声称修过，但代码仍把 `stats.Review`
传了两次。

**用户裁决**：四类互斥，相加等于本批总数。

| 统计项 | 口径 |
| --- | --- |
| 导入 | 规则 2、3 直接入库 |
| 进入复核 | 规则 1 疑似重复 **+** 规则 4 跨发行组 **+** 规则 3 同组多义 |
| 未匹配 | 规则 5 无结果 / 全部低置信 |
| 失败 | 规则 6 连续出错达上限，不再返回队列 |

「进入复核」与「未匹配」的条目都停在复核队列里（`status='review'`），
仅凭状态分不开，因此新增 `import_item.review_reason` 列
（`duplicate` / `ambiguous` / `no_match`）。复核队列里的「改搜」与「都不匹配」
只更新候选快照，传 `ReviewReasonUnchanged` 保留原成因。

> **第六轮更新**：该列此前由迁移 0002 引入，现已并回 0001（见第十九节）。

### 10.5 规则 6 的提示不再冒用规则 5 的文案 `[纯 bug 修复]`

重试耗尽时实现输出的是 `[匹配失败]: …（已达重试上限）`。`[匹配失败]` 是规则 5
「上游没有这首歌」的判定，计入未匹配；而重试耗尽是规则 6「一直没问到上游」，
计入失败。两者在统计行里是两个互不重叠的数，提示混用会让用户对不上账。

改为 `[发生错误]: 已连续 N 次出错，不再返回队列，<输入信息>，<错误>`。
统计行末尾的「连续 5 次」也改为取自实际的重试上限，不再硬编码。

### 10.6 MusicBrainz 搜索响应的曲目数组从来没被解析 `[纯 bug 修复]`

**审查 10.2 时发现，用户未报告。这是本轮影响最大的一处。**

MB 在**搜索**响应里把碟上的曲目放在 `media[].track`（单数），在**发行详情**
响应里放在 `media[].tracks`（复数）。`schema.go` 里只声明了 `tracks`，
于是搜索结果的每条候选都走了「响应不带曲目清单」的发行级兜底分支：

| 字段 | 本该是 | 实际是 |
| --- | --- | --- |
| `match_ref` | track MBID | 合成串 `recMBID@relMBID` |
| `medium_format` | `CD` / `Digital Media` / … | **空** |
| `track_number` / `disc_number` | 曲序 / 碟序 | **空** |

实测：修这一处之前，真实搜索返回的**每一条**候选载体都是空的。这既让 10.2 的
实体载体过滤无从谈起（一条都过不了），也让入库曲目的 match_ref 粒度退化——
而 match_ref 用 track MBID 正是为了区分同一录音的 CD 版与数字版。

**修复**：`medium` 同时接受两个键名，新增 `TrackList()` 抹平差异。

顺带修正了金样例 `testdata/golden/responses/musicbrainz/search_recording.json`：
它此前用的是 `tracks`，即详情端点的形态——搜索端点的金样例写成详情端点的形态，
正是这个 bug 能一直藏着的原因。

### 10.7 验收夹具改为真实返回，不再每行只留一条发行 `[纯 bug 修复]`

`internal/acceptance/csv_import_test.go` 的夹具此前每行只留一条发行，
`世界中の雨` 那行的 11 张同名 CD 被简化成 1 张——于是「同组多条该不该自动裁决」
这个分支从来没有被这组用例走到过，bug 在测试全绿的情况下发布。

夹具已用真实 MusicBrainz 返回**原样**重建（track MBID / 曲名 / 署名 / 歌集 /
recording MBID / release group MBID / 发行状态 / 载体 / 国家 照原样）。
两行候选过多的（22 条、43 条）做了截断并在注释里写明截了多少、为什么截。

## 十一、封面加载（`upstream/cover-art`）

**用户报告（第三轮）**：所有位置的专辑图片都加载不出来——详情抽屉、搜索列表、
复核列表都是。详情抽屉里没有封面时还显示了一个 emoji。

那个「emoji」其实是 **WKWebView 的破图占位符**：详情抽屉的 `v-else` 空态分支
（写着「无封面」）根本没被走到，走的是 `<img>` 分支，图 404 之后由 webview
画出它自己的破图字形。因此这一条与「封面加载不出来」是同一个 bug 的两个表现。

根因有**四处彼此独立**，任何一处不修都还是有位置显示不出封面。

### 11.1 封面地址带的是缓存键，而键不可逆 `[纯 bug 修复]`

`/cover?key=<sha256 前 16 字节>&size=250`。handler 拿着键**构造不出降级链**，
只能查一张由 `PrefetchCovers` 登记的 `key → URLs` 表；查不到就返回 404。

于是三处走不通：

| 位置 | 为什么拿不到图 |
| --- | --- |
| 详情抽屉 | 从来不调 `PrefetchCovers` |
| 复核队列 | 从来不调 `PrefetchCovers` |
| 搜索页 | 调了，但预取是在行渲染**之后**完成的——`<img>` 的请求先到，拿不到降级链就 404，再被前端记进 `brokenCovers` 集合，此后永不重试 |

**修复**：地址改带**来源**而不是键：

```
/cover?provider=musicbrainz&ref=<releaseMBID>&rg=<releaseGroupMBID>&size=250
/cover?adopted=<落盘路径>
```

handler 据此就地构造降级链（构造器由绑定层注入，封面包不认识具体上游），
缓存键仍按 `CacheKey(provider+":"+ref, size)` 现算——与 `BuildCoverRefs` 一致，
因此预取暖好的字节照样命中。`Service.ladders` 那张表整个删掉。

`PrefetchCovers` 保留，但从「必要前置」降为「提前暖机」：它的价值是把并发交给
Go 的工作池，不受 webview 每主机连接数的限制。

### 11.2 `TrackView.CoverKey` 声明了但从没赋过值 `[纯 bug 修复]`

资料库表格读 `row.coverKey`，而 `store.TrackView.CoverKey` 从声明出来就没有任何
地方给它赋值——`trackSelectColumns` 里也没有对应的列。于是曲目表格的封面列
**永远**走空态分支，一张图都不显示（这一处连 404 都不会发生）。

**修复**：删掉 `CoverKey`，改为带出发行与发行组标识（`ReleaseRef` /
`ReleaseGroupRef`），前端用 `matchSource` + 这两个值拼地址。

> **第六轮更新**：这两个标识现由 `release` 表 join 带出而不再是
> `track_metadata` 的列（见第十九节）；封面本身也已挂到歌集上，
> 采用一次即对该歌集全部曲目生效。专辑视图的封面缺口另见 19.3。

### 11.3 「取消滚出视口的取图」实际是「取消全部取图」 `[纯 bug 修复]`

`library.ts` 里 `visibleCoverKeys` 从初始化之后只被赋过 `[]`，没有任何视口跟踪。
而 `loadTracks()` 每次都先调 `cancelOutOfViewCovers()`，即
`CancelCovers([])` → `CancelAllExcept({})` → **取消进程内全部在途取图**。
`library:changed` 事件会触发重载，于是取图任务被反复清空。

**修复**：删掉这个调用与那个恒为空的 ref，避免重载取消全部取图。
`<img loading="lazy">` 可以延后图片元素的请求，但**不等于**后台取图任务会随滚动取消：
搜索页仍会批量预取全部结果。Go 侧 `CancelOutOfView` 保留，前端尚无真实视口跟踪，
也未调用 `CancelCovers`。因此防止误取消已修复，spec 的「滚出视口任务取消/降级」
仍是实现缺口（见 21.4），不能认定为已满足。

### 11.4 复核队列的候选快照丢掉了 iTunes 的基准图地址 `[纯 bug 修复]`

`parseCandidateSnapshot` 从 `ScoredCandidate` 重建 `CandidateRow` 时没有带
`ThumbURL`。iTunes 没有 release 级标识，降级链只能由基准图地址构造，
因此复核队列里 iTunes 候选的缩略图列必然是空的。补上 `ArtworkURL: c.ThumbURL`。

### 11.5 图片加载状态的四种呈现 `[需改 spec]`

**用户要求**：为图片加载状态设计图标与动画提示。

新增组件 `CoverArt.vue`，是全应用唯一的封面渲染入口（曲目表格、候选表格、
详情抽屉都用它）：

| 状态 | 呈现 | 含义 |
| --- | --- | --- |
| 无来源 | 默认图片图标（`Image`） | 这首曲目没有可取图的发行标识 |
| 加载中 | 旋转动画（`LoaderCircle` + `animate-spin`） | 请求已发出，后端可能正在出网取图 |
| 失败 | 断图图标（`ImageOff`，取 destructive 色） | 取图出错（网络、超时、上游 5xx） |
| 无封面 | `nil` 字样 | 降级链走完都是 404，上游确实没有这张封面 |

这替换了原先三处各写一遍的 `<div class="bg-muted">` 灰块，以及详情抽屉里那个
永远走不到的「无封面」文案分支。

**后两种状态必须分开**：「上游没有这张封面」是常态（大量发行在 Cover Art
Archive 上没有图），而「取图出错」是可以重试的故障。画成同一个灰块，
用户分不清该不该去点「重新获取封面」。

而 `<img>` 的 `error` 事件**读不到状态码**，两种失败在前端看起来一模一样。
因此：

- 后端记下每个缓存键最近一次取图的结果（`ok` / `empty` / `error`），
  新增绑定 `CoverOutcomes(sources)` 查询；
- 前端只在 `<img>` 失败后问一次，且 30ms 内**攒批合成一次 IPC**——
  一页列表里取不到图的行往往是一起失败的，逐行一次调用会把几十次 IPC
  摊在同一帧里。

建议在 spec 中新增一条 `Requirement: 封面加载状态的呈现`。

### 11.6 顺带修掉的两处 `[纯 bug 修复]`

- `GetTrackView` 开头有一句 `views, err := s.ListTracks(TrackFilter{Limit: 1})`
  紧接着 `_ = views`——每打开一次详情抽屉就多跑一次完整的列表查询，结果丢弃。已删。
- 封面缓存目录改动后会重建 `covers.Service`。降级链构造器的接线因此抽成
  `attachLadderBuilder`，两处建服务的地方共用；测试辅助 `newTestApp` 也改走它——
  测试里另建一份不带构造器的服务，正是这类 bug 能在测试全绿的情况下发布的原因。

### 11.7 回归测试

在 `main` 包（打到真实生产入口，不手工调 store 原语）：

- `TestCoverSourceReachesFrontend` —— `ListTracks` 与 `GetTrackDetail`
  必须给出封面来源标识，守 11.2 那类「字段声明了但没人赋值」。

## 十二、候选闸门：曲名之外必须有一处旁证（`matching/confidence`、`matching/pipeline`）`[需改 spec]`

**用户报告（第四轮 1）**：`4円` 在 MusicBrainz 上只有一个专辑记录，
所以「羽翼」（表格里那行是 `ツバサ（羽翼）· 4円（ヨエン）· side-c`）本该无结果，
但实现返回了结果。

复核确认属实：MB 里同名录音有 **43 条**，它们的曲名全都过得了曲名闸
（`つばさ`/`ツバサ` 规范化后与 `ツバサ` 相等），于是整整 43 条与这一行毫无关系的
候选被写进候选快照，摆到复核队列里等用户手工否掉 43 次——而正确的结论是
「上游没有这首歌」。

### 12.1 新增 `Score.Plausible`：值得摆到用户面前的那道闸

**spec 现状**（`matching/confidence`）：只有两道判定——「曲名不匹配即丢弃」与
「高置信 ≡ 曲名匹配 AND（署名精确 OR 歌集精确）」。曲名过闸的候选一律进候选池。

**改为**在两者之间加一道**松闸**（`Weights.IsPlausible`）：

```
值得摆出来 ≡ 曲名过闸 AND（可比的旁证里至少一处对得上，或一处可比的都没有）
```

- 旁证有两轴：署名（`CompareCredit`）与歌集（`CompareText`）。精确与模糊都算对得上。
- **「可比」只在两侧都给出该字段时成立**。一侧空着是「没有这个信息」而不是
  「对不上」——把它当反证，会因为候选缺一个歌集名而毙掉一条曲名精确相符的候选。
- 两侧一处可比的都没有时（例如表格只有曲名一列），曲名自己就够。

三道闸各管一件事，不是同一判断的三个档位：

| 闸 | 管的事 | 落点 |
| --- | --- | --- |
| 曲名闸（`CompareTitle`） | 是不是同一条录音 | `Score.Rejected` |
| 旁证闸（`IsPlausible`） | 给不给人看 | `Score.Plausible` |
| 高置信闸（`IsHighConfidence`） | 要不要经人手 | `Score.HighConf` |

### 12.2 候选池按它筛——导入与手动检索同一道闸

**spec 现状**（`matching/pipeline`）：候选池只排除曲名不匹配的候选。

**改为**：`Engine.Run` 丢掉 `!Plausible` 的候选。筛掉之后 `ツバサ` 那一行走的是
「无结果」这条出口——那句话此刻是**准确**的。

第四轮曾让搜索页与复核「改搜」**不筛**（理由是「人在看」）。**第五轮按用户裁决撤销**：
同一上游不管从哪个入口检索都用同一道闸；用户留空的字段不可比、不参与
（见第十八节）。

### 12.3 阶梯的推进条件随之收紧

**此前实现**（第九节）：「有过得了曲名闸的候选即停」；
原 `matching/text-processing` spec 仍写「高置信即停」，两次调整都需同步。

**改为**：「有过得了**两道**闸的候选即停」。只过曲名那一道停不下来，
否则更宽的一级永远试不到。

代价写在这里以免下一个人重新发现它：上游确实没有的那些行现在要把阶梯走完
（`ツバサ` 从 1 次请求变成 3 次，在 1 req/s 下多花 2 秒）。换来的是
「未匹配」这个结论真的成立，而不是把 43 条噪音丢给用户。

### 12.4 参考实现与回归测试

思路来自本地 `musiclib` 项目的
`internal/musicbrainz/confidence.go` → `Plausible`（那里的实测记录是
`recording:"夕立"` 有 192 条同名录音，全摆出来等于让人手工否掉 192 次）。

- `matching.TestPlausibleNeedsOneCorroboration` —— 六种形态的真值表。
- `matching.TestNoCorroborationNeverEntersPool` —— 候选池为空、分流为无结果、
  且阶梯没有停在只过曲名那一级。
- `acceptance.TestCSVImportEndToEnd` 新增 `wantScored`：把 10 行**各自过闸几条**
  一并钉住（`ツバサ` = 0，`世界中の雨` = 11，`By the Seaside` = 4……）。
  此前这组用例只校验分流去向，「摆了多少条给用户看」这件事没有任何守卫。

## 十三、补全信息匹配：接受不发请求，详情交后台（`review/review-queue`、`platform/data-store`）`[需改 spec]`

**用户报告（第四轮 2）**：在复核队列点确认要等 1–2 秒歌曲才入库，
应该是发生了对 MB 的再次请求，非常影响体验。改为先把已得到的信息入库然后再匹配；
导入/搜索空闲时自动开始，用户搜索或导入进行时自动暂停。

根因如报告所述：`AcceptCandidate` 入库后**同步**调用 `RefreshTrackDetail`，
在 MB 1 req/s 之下那一次请求就是 1–2 秒的卡顿——而它的产出
（参与者、作曲作词、厂牌、目录号、风格）与「这条曲目能不能进库」无关。

参考实现：本地 `musiclib` 项目（`internal/matching/enrich.go`
的 `EnrichTask`、`internal/matching/matching.go` 的 `Accept`「不发任何网络请求」、
`internal/musicbrainz/transport.go` 的 `priorityGate`）。

> **验证范围**：零请求接受与调度行为已有回归；后台详情按目标曲目取数、
> 清单顺带落库及用户锁保护仍有实现缺口，见 21.3，不能由调度测试通过推断已满足。

### 13.1 零请求接受 `[需改 spec]`

**spec 现状**（`review/review-queue` → `Requirement: 动作语义`）：
「『接受』采用该上游候选入库并写入匹配来源与标识」——未规定是否同步补详情，
但实现同步补了。

**改为**：`AcceptCandidate` **不发任何网络请求**。候选已带着 match_ref 与四个上游
标识、以及 track/medium 层的全部字段，够写成曲库里合法的一行。曲目入库即为
「未匹配（待补全）」，详情由后台任务补。

同一改动覆盖搜索页的「加入曲库」（本来就不补详情，现在会触发后台任务）。

### 13.2 三态补全状态机 `[需改 spec]`

**spec 现状**（`platform/data-store`）：`track_metadata` 无补全状态字段。

**新增三列**（当时由迁移 0003 引入；第六轮已并回 0001 并随
`track_metadata` 一起合入 `track` 表，见第十九节）：

| 列 | 用途 |
| --- | --- |
| `enrich_state` | `pending` / `fetched` / `absent` / `skipped` |
| `enrich_attempts` | 连续失败次数，达 `MaxEnrichAttempts`(5) 退出工作集 |
| `enrich_error` | 最近一次失败原因 |

用户口径的三种状态与它的对应关系：

| 界面 | 存储 | 含义 |
| --- | --- | --- |
| 已匹配 | `fetched` ∪ `absent` | 详情已落库，或没有发行标识无从取起 |
| 未匹配 | `pending` | 有上游身份，详情还没取 |
| 无需匹配 | `skipped` | 用户以「无需匹配」入库，不追求外部身份 |

**`absent` 必须与 `pending` 分开**：「上游确实没有可补的东西」与「还没问过」
在数据上长得一模一样，合成一种的话后台任务会永远回到这条曲目上。
状态由 `store.InitialEnrichState` 在入库那一刻写下（唯一判定点，四条创建路径共用）。

顺带修掉一处：`RecordEnrichFailure` 此前把 `[丰富失败] …` 写进 `comment`——
那是用户自己的备注字段，一次取详情失败会把他写的内容冲掉。改写 `enrich_error`。

### 13.3 后台任务：空闲自动开始，导入/检索时整体让路 `[需改 spec]`

出网未启用（联系方式没填）也算「该让路」：这种情形下每一条都会失败，
重试计数被白白烧掉、任务最后转 stalled，而真正的原因只是设置里少填了一个字段。
因此自动启动直接跳过，已在跑的任务转入让路——用户在设置里补上之后它自己接着跑。

`Stop()` **等循环真的停下来**（上限 3 秒）。不等的话退出应用时 store 会在补全
还在写库的那一刻被关掉；测试里的表现是临时目录清理不掉（WAL 文件在 Close
之后又被建了出来）。


新增 `enrichWorker`（`enrich_worker.go`）与三个绑定
（`GetEnrichStatus` / `StartEnrich` / `PauseEnrich`）、一个事件（`enrich:progress`）。

- **工作集**：`enrich_state='pending'` 且有发行标识且重试未达上限，按入库顺序。
  枚举是**同步**的，调用方当场就知道有没有事可做。
- **自动开始**的时机：应用启动、导入批次跑完、接受一条候选、加入曲库，
  以及用户的检索结束（交互计数归零）。
- **自动让路**：`outboundBusy()` 报告「导入匹配在跑」或「用户检索在飞」时任务转入
  `waiting` 并说明在等什么。让的是**整个配额**而不只是次序——见 13.4。
- **手动暂停是用户的决定**：暂停后即使又空闲、又有新条目，也不自动开始，
  直到他再点「开始」。点「开始」同时把重试计数清零（那是「再试一次」的意思）。
- 连续失败 5 次转 `stalled` 并保留进度，不再无声地失败几百次。

**进度口径是全库而不是本轮**：`已匹配 / (已匹配 + 未匹配)`。本轮口径在这里读起来是
错的——用户接受一条候选、任务跑起来、他再接受一条，本轮的分母就变了，
界面上的数字会往回跳。无需匹配的曲目不进这两个数，否则它永远到不了头。

### 13.4 出网请求分两级优先级 `[需改 spec]`

**spec 现状**（`upstream/provider-registry`）：只规定「同一上游的各功能共用一个
进程级令牌桶」。

**改为**：令牌桶前面加一道**优先级闸门**（`provider.priorityGate`），
交互式请求整体排在后台请求之前。优先级经 context 传递
（`provider.WithPriority`），**默认后台**——忘记标注的代价应当是「慢一点」，
而不是「悄悄抢在用户前面」。

| 优先级 | 调用点 |
| --- | --- |
| 交互式 | `SearchUpstream`、`ResearchReviewItem`、`RefreshTrackDetail` |
| 后台 | 导入匹配、补全信息匹配 |

两点实现约束写在这里以免下一个人重新发现：

1. 闸门在**取到令牌后**即释放，不握到请求返回——握到返回等于把每次请求的
   网络耗时叠加到限流间隔上，实际速率会莫名其妙低于配置值。
2. 已经握着闸门的那一个**不被抢占**（它已经在等自己的令牌了）。
   抢占在途请求只会浪费一个已经预约的令牌。

闸门只解决**次序**，因此 13.3 的整体让路仍然必要：后台任务照样占掉那一秒的配额，
用户等的那次搜索还是要多等一轮。

### 13.5 事件推送抽出唯一出口 `[纯 bug 修复]`

**审查时发现。** Wails 的 `runtime.EventsEmit` 在**非生命周期** context 上
会直接结束进程（不是返回错误）。此前五处推送各自 `if a.ctx != nil` 后直接调它，
于是 main 包里任何走到推送的测试都会整包崩掉——`AddToLibrary`
（会 `notifyLibraryChanged`）因此从来没有被 main 包的测试覆盖过。

改为全部经 `App.emitEvent`，测试把 `App.emit` 换成记账函数。
这也是新增的 `enrich_worker_test.go` 能存在的前提。

## 十四、曲目表格改为文件管理器式选中（`platform/app-shell`、`library/export`）`[需改 spec]`

**用户要求（第四轮 3）**：移除勾选框列、工具栏改为补全信息匹配的开关与进度、
导出转入右键菜单、行级多选按文件管理器的习惯做，同时**保留单元格内划选文字的能力**。

### 14.1 勾选框列移除，整行底色是选中状态的唯一信号 `[需改 spec]`

**spec 现状**（`platform/app-shell` → `Requirement: 曲目表格的交互`）：
「曲目表格 SHALL 支持多选（连续选择与逐项加选）；**单击行 SHALL 打开详情抽屉**」，
并在 `Scenario: 全选跳过灰色行` 里预设了一个全选入口（实现为表头勾选框）。

**改为**：

| 操作 | 结果 |
| --- | --- |
| 单击 | 清除其他选中，仅选中这一行（**不再打开详情抽屉**） |
| 双击 | 打开详情抽屉 |
| Ctrl/Cmd + 单击 | 追加选中，或取消选中该行 |
| Shift + 单击 | 选中锚点到该行之间的全部曲目 |
| Ctrl/Cmd + A | 选中列表里的所有曲目（灰色行除外） |

单击不再打开抽屉是这一套的必然结果：文件管理器里单击是选中，双击才是打开。
两者合一的话，用户每选一行都会弹出抽屉，而多选时抽屉会被反复重建。

勾选框列与表头的全选勾选框一并移除——它与整行高亮是同一件事的两种表达。
选中态因此**必须明显强于悬停态**：两者取同一个值时，「已选中」与
「鼠标恰好停在这一行」在视觉上分不开。

灰色行的既有约束全部不变（不可选中、不计入计数、Cmd+A 跳过、菜单只有两项）。

**选择模型与键盘契约**：

- `useListSelection.ts` 是唯一选择模型，DataTable 不启用 `selectionMode`；
  仅受控传入 selection 作显示。锚点/焦点保存稳定行 key，不保存排序前下标。
- 原表五项动作保留；额外支持：上下/Home/End 移动并独选，Shift 扩展/收缩范围，
  Cmd/Ctrl+上下仅移动焦点，Cmd/Ctrl+Shift 追加范围，Space 切换，Enter 打开，
  Escape 清空，Shift+F10/菜单键打开菜单。无文字选区时 Cmd/Ctrl+C 复制所选曲目信息。
- Cmd/Ctrl+A 仅在行/列表获得焦点时生效；输入、工具栏、侧栏和弹窗不接管。
  空白处单击清空；右键已选行保留多选，右键未选普通行独选，灰色行保持既有选中。
- 灰色行在状态模型入口排除，键盘移动和全选均跳过；不是事后剔除。
- 清单位置 key 与曲目 id 分开：id=0 的多条灰色行不碰撞，多个位置命中同一曲目
  时可以显示多个选中位置，但计数/导出/删除/添加集合均按曲目 id 去重。
- 选中用 `--p-highlight-background`（浅色 surface-200/暗色 surface-700），
  hover 用 surface-100/800，焦点另有 outline；鼠标停在已选行不降低选中强度。

### 14.2 单元格内仍可划选文字 `[需改 spec]`

整行选中与「像普通网页那样选一段文字复制」必须共存。实现上两条：

1. `select-none` 在表格级、`select-text` 在文字单元格级——在行的空白处拖动
   不留下一片蓝底选区，在标题/艺术家/专辑等文字上拖动照常出选区。
2. 行选中判定放在 `click` 而不是 `mousedown` 上，并比对按下与松开的位移：
   位移超过 4px **且真的产生了文字选区**时，这一下算划选，不动行选中状态。

位移以欧氏距离 >4px 判定，并且必须确有文字选区。
普通点击后聚焦行，划选时不改选择、不强制 focus（WebKit 可能因此丢文字选区）。
由于 DataTable 内置选择已关闭，不需要捕获 click 并 stopPropagation 来对抗另一套选择。
歌单不设置整行可拖动，使用现有 # 列中的 DataTable 原生手柄；标题等文字仍可划选。

另有一处必须显式阻止：Shift + 单击时浏览器会顺手把整段文字选进选区
（读起来正是用户说的「整个页面的文字变成蓝底高亮」），因此
`mousedown` 上遇到 shiftKey 就 `preventDefault()`——连选由 `click` 处理。

Ctrl/Cmd + A 同理需要 `preventDefault()`，且**在输入框里不接管**
（`INPUT`/`TEXTAREA`/`SELECT`/contenteditable 中的全选仍归输入框）。

### 14.3 工具栏改为「补全信息匹配 [开始/暂停] xx/xx」 `[需改 spec]`

**spec 现状**（同上）：「工具栏 SHALL 提供导出入口，其范围可选
当前歌单 / 当前筛选结果 / 选中项 / 全库」。

**改为**：工具栏左侧仍是 `N 首曲目 · 已选 M 项`，右侧是后台补全任务的开关与进度
（见第十三节）。导出整体移出工具栏。

进度是 `已匹配 / (已匹配 + 未匹配)`，悬浮提示说明它此刻在等什么或最近为何失败。

### 14.4 导出移入右键菜单 `[需改 spec]`

右键菜单在「复制信息 / 从当前歌单移除」之后加一组：

```
导出选中项…      ← 无选中项时禁用
导出当前列表…
导出全库…
```

`library/export` 要求的四个范围仍然都在：**当前歌单与当前筛选结果在后端是同一条
路径**（`resolveExportScope` 的 default 分支都用 `req.Filter`，而歌单页的 filter
已经带着 `collectionId`），因此界面上合为「导出当前列表」一项，语义不缺。
`scope='playlist'` 这个取值从界面上不再产生，但绑定层仍接受它。

### 14.5 换一屏行时清理失效的选中项 `[纯 bug 修复]`

**审查时发现。** 切视图/筛选/重载后 `selected` 里可能留着已不在列表中的 id，
而「导出选中项」用的正是这个集合——用户会导出到一批他此刻根本看不见的曲目。
改为在 `rows` 变化时把不存在的 key 剔掉并重新上报有效曲目 id。
同一组件切换歌单/艺术家/专辑上下文时清空选择；卸载上报空集合。
普通后台重载保留仍存在的 key，并换成新行对象，避免菜单/批量操作读旧字段。

### 14.6 验证

`tmp/harness/`（gitignore）里放了一套 Wails 桩件 + CDP 驱动：把 `frontend/dist`
连同一份假绑定喂给无头 Chrome，用真实的鼠标/键盘事件逐条核对上面每一项，
并截图核对亮/暗两套主题。15 条断言全部通过：

```
勾选框列已移除 / 工具栏为补全信息匹配 xx/xx / 单击仅选中一条 /
单击不打开详情抽屉 / Shift 连选区间 / Cmd 点击追加 / Cmd 再点取消 /
Cmd+A 选中所有行 / Cmd+A 不产生文字选区 / 文字划选保留 /
划选不改变行选中 / 右键菜单含导出选中项 / 导出选中项传出选中 id /
双击打开详情抽屉 / 开始/暂停可切换
```

桩件里踩到的一处坑记在这里：`wailsjs/runtime` 的 `EventsOn` 实际转调
`EventsOnMultiple`，桩件只实现前者时应用会在 `onMounted` 中途抛错，
表现为「表格有数据但侧栏徽章与工具栏进度都是空的」。

当前可重复执行的验证为已纳入版本控制的
`frontend/tests/unit/` 与 `frontend/tests/e2e/`（真实应用 + Wails 桩件）。
选择读标准 `aria-selected`，结构用稳定行 key，交互通过真实鼠标/键盘事件驱动。
覆盖与执行结果见 20.7，包括灰色行、重复 id、排序后范围、焦点作用域与重排；
上述历史脚本的断言不重复计入当前结果。

## 十五、复核队列的三处交互（`review/review-queue`）

### 15.1 切换上游即刷新结果 `[纯 bug 修复]`

**用户报告（第四轮 4）**：重新搜索里修改上游不会清空当前查询结果。

改选上游后屏幕上仍挂着上一个上游的候选，而「上游」下拉已经指向另一家——
读起来像是这些候选来自新选的那个上游（来源徽章那一列此时是自相矛盾的）。

**改为**：切换上游即以新上游重新检索一次。

一处必要的限制：只在这个条目**已经手动搜过一次**之后才自动重搜。
否则刚打开一个条目、随手改一下上游就会出网，把 1 req/s 的配额花在
用户还没提出的请求上。换条目时该标记复位。

### 15.2 上一条/下一条移到条目动作的上面一行 `[需改 spec]`

**用户报告（第四轮 5）**：这两个按钮在窗口右上角，不容易点到。

**spec 现状**（`review/review-queue` → `Requirement: 逐条浏览与计数`）：
「**顶部**显示『3 条待处置 · 待选 1 · 失败 2』，并可用上一条/下一条在其间切换」。

**改为**：待处置总数与分项计数仍在顶部；**上一条 / N/M / 下一条**移到上半区，
紧贴在「无需匹配 / 移出队列」这一行的上面。理由是动线：处置完一条之后
用户紧接着要按的就是「下一条」，它该在手边而不是在窗口对角。

### 15.3 「删除记录」改名为「移出队列」 `[需改 spec]`

**用户要求（第四轮 6）**。

**spec 现状**（同上 → `Requirement: 上半区展示原始输入与条目动作` 与
`Requirement: 动作语义`）：动作名为「删除记录」，语义是「丢弃该条目且不入库」。

**改为**：名称为**移出队列**，语义不变（`DiscardReviewItem` 未改）。
「删除」会让人以为动的是曲目，而它丢弃的只是这条**待处置记录**——
曲库里什么都不会少。按钮也不再用 destructive 色：它不是破坏性操作。

### 15.4 验证

`tmp/harness/drive-review.mjs`（gitignore）用无头 Chrome 逐条核对，6 条断言通过：

```
条目动作为「移出队列」而非「删除记录」 / 上一条在无需匹配的上面一行 /
上一条不在窗口右上角 / 先手动搜一次 / 切换上游自动重搜 / 结果换成新上游的
```

当前上游下拉使用 Volt `Select`，Playwright 通过真实鼠标/键盘驱动，
覆盖先手动搜索、再切 iTunes 自动重搜并显示地区选择。执行结果见 20.7，
历史六条断言不重复计入当前结果。

## 十八、入库与检索各只剩一条路径（`matching/pipeline`、`matching/provenance`、`upstream/search`、`review/review-queue`）`[需改 spec]`

**用户裁决（第五轮）**三条：

1. 曲目**不保存原始导入值**。上游没给的字段不拿表格里的值去补。
2. 导入直接入库、复核接受、搜索页加入——刚入库时的记录**没有任何区别**。
3. 同一上游的搜索、导入、改搜**同一套逻辑**：验证署名与歌集，除非传入的是空值。

### 18.1 候选入库只有一个落点：`store.AdmitCandidate` `[需改 spec]`

**此前**三处各写各的：导入多写了发行状态与碟号，搜索页少写了它们，厂牌与目录号
三处都没写；复核「接受」在候选缺署名/歌集时拿 `import_item.in_*` 去补，
并在溯源里记一个 `import` 来源。同一条候选从不同入口进来，库里长得不一样。

**改为**：四条路径（导入自动入库、复核「接受」、搜索页「加入曲库」、专辑视图
灰色行「加入曲库」）全部经由 `store.AdmitCandidate(provider.Candidate)`。
它**只写候选自己带的字段**：上游没给的留空、如实呈现为缺失。

> **第六轮更新**：`AdmitCandidate` 现在把候选拆成两半写——曲目自己的字段
> （碟号、音轨号、时长、录音标识、ISRC）写 `track`，发行级字段
> （类型、载体、国家、厂牌、目录号、音轨数）写 `release`，并顺带登记发行组。
> 「只写候选自己带的字段」这一条不变。

**注意**：该段描述统一入口与目标契约，不表示四个调用方已传齐同样的数据。
灰色行入口尚未传入所属发行、碟号与音轨号；候选 `Year` 尚未映射到歌集日期，
`AlbumCredit` 则暂以曲目署名填入。现状与后续修复建议见 21.3、21.4。

`CandidateRow` 补了 `discNumber` / `releaseStatus` / `firstReleaseDate` 三个不显示的
字段，使行能**无损**还原成候选（`toCandidate` 与 `rowFrom` 互为逆运算）——
否则经过界面往返的那两条路径必然比导入少几列。

**与 spec 冲突处**（`library/track-library` 与 `design.md` D2）：规划把 `import`
（导入文件原值）列为逐字段来源的一种取值。候选入库路径不再产生它——曲目记录的是「上游怎么说」，
表格那一行是「用户当时怎么写」；补了会让一首曲目的署名一半来自上游、一半来自
表格，且看不出哪一半是哪一半。建议从来源取值里删掉 `import`。

**未动的部分**：`import_item.in_title/in_artist/in_album` 仍然保留——它们是复核队列
的工作数据（上半区显示原始文本、改搜预填、「无需匹配」按原始输入入库都靠它），
spec 明确要求这三件事。它们只在「无需匹配」这条明确按原始输入收录的路径进入 `track`，
不会为已接受的上游候选补缺失字段。

### 18.2 检索只有一个入口：`matching.Engine.Run` `[需改 spec]`

**此前**搜索页与改搜只发**一次**查询、只过曲名闸；编辑页「重新匹配」连剥离都不做。
导入走三级阶梯、两道闸。同一个 `原田瞳（原田ひとみ）` 在四处会得到四种结果。

**改为**：绑定层只剩 `App.matchUpstream`，它调 `Engine.Run`。导入、搜索页、
复核改搜、编辑页重新匹配四处因此完全一致：同一条变体阶梯、同一套剥离与备选写法、
同一对闸门、同一份评分。手动检索只是不看第 [4] 步的分流结果。

「除非传入的是空值」落在闸门的**可比**定义上（第十二节已有）：用户留空的字段
不参与判定。为此曲名也纳入同一规则——曲名留空时（搜索页只按艺术家找）曲名闸
不参与、不给曲名分、永远不高置信。此前曲名留空会把**全部**候选判成不匹配，
搜索页「三个字段可任意留空」在曲名那一格是假的。

代价：手动检索在没有过闸候选时会把阶梯走完（最多 3 次请求），与导入一致。

**与 spec 冲突处**：
- `upstream/search` 的「三个输入字段可任意留空」现在真的成立，但结果**不再是**
  上游原样返回——过不了闸的候选不显示。spec 应写明手动检索也按闸门筛。
- `review/review-queue` 的「已尝试变体」现在是改搜实际跑过的阶梯（此前改搜只记
  用户填的那一个串）。

### 18.3 回归测试

## 十九、数据库重构：歌集升格为实体，署名与参与角色拆开 `[需改 spec]`

**用户报告（第六轮）**三条，以及随之而来的一次数据库重新设计：

1. 艺术家视图中出现未署名的作词作曲。
2. 艺术家视图只应出现署名的艺术家与虚拟歌姬；只署名作词/曲（如 DECO*27）
   而没有虚拟歌姬署名的音乐，也应出现在该虚拟歌姬（如初音ミク）的视图中。
3. 专辑视图无法加载专辑封面，只显示默认图标。

三个问题里只有第三个是纯前端缺口，另外两个的根因都在表结构上——
「发行（歌集）」与「署名」这两个概念在库里没有独立的身份。

> **开发阶段约定**：v1 未发布，不考虑数据库兼容与迁移。此前的迁移
> 0002（`review_reason`）与 0003（`enrich_state`）已**并回 0001**，
> 迁移列表只剩一条。旧库由用户在测试前手动清理。
> 这使第 10.4 节与第 13.2 节里「新增迁移 0002 / 0003」的表述作废——
> 那两列仍然存在，只是不再作为独立的迁移单元。

### 19.1 歌集（release）升格为实体 `[需改 spec]`

**spec 现状**（`library/track-library` → `Requirement: 曲目的两层字段模型`、
`platform/data-store` → `Requirement: 丰富信息表可演进`）：
曲目由「基本信息 + 丰富信息」两层构成，丰富信息存在一张可演进的表里。
`library/release-catalog` 则把 release 定义为「上游事实的镜像」，
与曲目之间**无外键**。

**问题**：发行级事实（专辑名、类型、载体、国家、年份、碟数、音轨数、厂牌、
目录号、封面）此前逐曲目复制一份存在 `track_metadata` 上。一张 12 首的专辑
要存 12 份，改其中一份另外 11 份不动。而同时存在的 `release` 表只作上游镜像，
它的 `cover_path` 有列却**没有任何路径写入**。

**改为**：`release` 是承载歌集事实的实体，`track.release_id` 外键指向它。

```
release_group                 -- 发行组：同一专辑的不同版本合为一条
  id, provider, provider_ref, title, primary_type, secondary_types,
  first_release_date,
  release_count,              -- ✎ 组内共有几个 release（上游 browse 取得）
  release_count_fetched_at

release                       -- 歌集
  id, release_group_id → release_group(id) ON DELETE SET NULL,
  provider, provider_ref,     -- 均可空：本地歌集两者都为 NULL
  title,                      -- ✎ 歌集名
  credit,                     -- ✎ 歌集艺术家（原串保真）
  primary_type,               -- ✎ album | ep | single | broadcast | other
  secondary_types,
  disc_total, track_total,    -- ✎ 碟数、音轨数
  cover_path,                 -- ✎ 封面（本地文件路径）
  cover_source_url, cover_width, cover_height, cover_fetched_at,
  release_status, medium_format, country, release_date, first_release_date,
  label, catalog_number,
  tracklist_state, fetched_at,
  provenance_json, locked_json

track                         -- 曲目：单表
  id, release_id → release(id) ON DELETE SET NULL,
  title,                      -- ✎ 曲名，NOT NULL
  credit,                     -- ✎ 曲目署名艺术家（原串保真）
  disc_number, track_number,  -- ✎ 碟号、音轨号
  track_number_text, duration_ms,
  genre,                      -- ✎ 风格
  comment,                    -- ✎ 注释
  match_source, match_ref, matched_at, recording_ref, work_ref, isrc,
  enrich_state, enrich_attempts, enrich_error,
  provenance_json, locked_json
```

`✎` 标记模型设计要求可编辑的字段；当前界面的实际覆盖与未接线字段见 19.6。

**与 spec 冲突处**：

- `library/track-library` 的**两层字段模型**不再成立：`track` 与
  `track_metadata` 合为单表。此前两张表各存一份曲名、专辑名与署名，
  写入路径两边都写，而「哪一份为准」没有定论。
  「基本信息必存在」现由 `title NOT NULL` 表达，
  「丰富信息可整体为空」由其余列可空表达——语义不丢。
- `library/track-library` 的**基本信息三个布尔锁**（`title_locked` /
  `artist_locked` / `album_locked`）取消，并入 `locked_json`。
  合表后没有理由留两套锁机制，而逐字段锁本就要求
  「新增字段无需改动锁的存储结构」。
- `library/release-catalog` 的「发行清单与曲目之间 SHALL NOT 建立外键」
  **仍然成立**：`release_track`（清单位置）与 `track` 之间依旧没有外键，
  删曲目不破坏清单，位置自然回落为灰色行。新增的外键是
  `track.release_id`，指向**歌集**而非清单位置，两者不是一回事。
- `library/release-catalog` 的「发行 SHALL 只存储上游声明的事实，
  SHALL NOT 承载任何用户数据」**需要修改**：歌集名、歌集艺术家、类型、
  碟数、音轨数、封面现在是用户可编辑的，因此 release 上有
  `provenance_json` / `locked_json`。「用户拥有哪些曲目由曲目记录决定」
  这一条不变。
- `platform/data-store` 的「丰富信息表可演进」条款里的表名需改。
  可演进性本身不变：曲目级与歌集级各有一份 `provenance_json` / `locked_json`，
  新增字段无需改动来源与锁的存储结构。
- `library/browse-views` 的**专辑分组键三级降级**取消（见 19.4）。

**年份不再单独存一列**：它由歌集的 `release_date` / `first_release_date`
派生（`Release.Year()`）。曲目的年份本来就是发行年份，存两份必然漂移。
年份修改应写到歌集发行日期并记录歌集级来源与锁；目前编辑绑定尚未接通这条路径，
不能把存储层支持日期更新等同于界面已能保存年份（见 19.6、21.3）。

### 19.2 「署名」与「参与角色」拆为两件事 `[需改 spec]`

**这是问题 1 与问题 2 的根因与解法。**

**spec 现状**（`library/artists`）：
- `Requirement: 参与者以关系存储` —— 每条关系记录角色、**该曲目上的实际署名写法**、
  顺序、来源。
- `Requirement: 署名的可点击区间` —— 区间信息「SHALL NOT 参与查询」。

**问题**：库里只有 `track_artist` 一张关系表，没有任何字段能回答
「这个人是否出现在署名里」。于是：

1. `ListArtists` 无条件 `JOIN track_artist`，把全部 12 种角色的人都列成艺术家。
   未署名的作词作曲因此出现在艺术家列表里（**问题 1**）。
2. 署名串解析出的艺术家被一律写成 `role='vocal'`
   （`matching/cv.go` 与 `musicbrainz/detail.go:206` 两处都硬编码），
   于是只作词作曲的署名艺术家（DECO*27）在库里被标成**演唱者**。
3. 「这位艺术家是否被署名」只能从 `credit_spans_json` 这个 JSON 列看出来，
   而 spec 明确禁止它参与查询。

**目标与实现边界**：表结构与 `applyDetailArtists` 已拆开署名和角色，
但 MusicBrainz 的 `parseRecordingArtists` 仍把 recording 的 `artist-credit`
转成 `role='vocal'`；抽屉也仍把署名区标为「演唱」。因此下述成员判定已实现，
「署名不再冒充演唱」尚未在真实解析链路完全落实（见 21.3）。

**存储与绑定层调整后**：

| 表 | 回答的问题 |
| --- | --- |
| `track_credit` | 谁出现在这条署名串里，以什么写法、在哪个区间 |
| `track_artist` | 谁在这首歌上担任什么角色（演唱/作曲/作词/编曲…） |
| `release_credit` | 歌集署名的同构分解 |

```sql
track_credit (track_id, artist_id, position, credited_name, span_start, span_end)
  PRIMARY KEY (track_id, artist_id, position)
```

`position` 进主键：同一位艺术家可能在一条署名里出现两次（形如 `A feat. B & A`），
各自有各自的区间。

`track_artist` 随之**去掉 `credited_name` 列**——它归 `track_credit`。

**艺术家列表的成员判定**（`store.artistListMembers`）：

```sql
SELECT track_id, artist_id FROM track_credit
UNION
SELECT track_id, artist_id FROM track_artist WHERE role = 'vocal'
```

一位艺术家出现在列表里，当且仅当他**在某曲目的署名中出现**，
或**在某曲目上担任演唱**。按用户第六轮的裁决，「虚拟歌姬」不单独识别，
凡有演唱角色即出现——真人主唱与未署名的和声也一并进来，它们本来也该在。

- DECO*27 凭署名进来（**问题 2 的前半**）。
- 初音ミク 凭 MusicBrainz 的 vocal 关系进来，哪怕没有出现在署名串里
  （**问题 2 的后半**）。
- 未署名的作词、作曲、编曲、制作两条都不满足，从列表消失（**问题 1**）。

**进入某位艺术家之后，曲目列表仍取全部关系**（署名 ∪ 全部角色）。
列表成员与视图内容是两件事：DECO*27 的「作曲」分面若只取署名过的曲目，
会漏掉他未署名的那些作品——那些曲目该在他自己的视图里，
只是不该让他因此进入艺术家列表。

**与 spec 冲突处**：

- `library/artists` 的「每条关系 SHALL 记录……该曲目上的实际署名写法」
  需改：署名写法归 `track_credit`，`track_artist` 只记角色。
- `library/artists` 的「可点击区间 SHALL NOT 参与查询」**需要修改**：
  区间本身仍是渲染辅助数据，但「这位艺术家是否被署名」必须可查询——
  艺术家列表的成员判定要用它，JSON 列做不到。建议改为
  「区间的**位置信息**不参与查询，但署名成员关系可查询」。
- `library/browse-views` 需**新增**一条艺术家列表的成员条件条款。
- 角色分面新增「署名」一项（`store.RoleCredited`），排在「全部」之后。
  「全部」是署名 ∪ 全部角色，可能大于任何单一角色分面。

### 19.3 封面挂到歌集上 `[需改 spec]`

**问题 3 的两半**：

**后端**：`SetCover` 此前把封面写在 `track_metadata` 上，逐曲目一份。
用户在一首歌上采用封面之后，同专辑的其余 11 首仍然没有图；
而 `release.cover_path` 有列却没有任何路径写入它。
现在封面只存在歌集上一份，采用一次即对该歌集全部曲目生效。
曲目没有所属歌集时 `SetCover` 报错而不是静默丢弃——
没有歌集就没有地方放这张封面。

**前端**：`AlbumsView.vue` 从头到尾**没有引用过 `CoverArt.vue`**：
中列每项、详情头部、详情里的曲目行都没有传封面来源，
于是三处永远是默认图标。这是「专辑封面加载不出来」的直接成因，
后端的 `/cover` handler 本身是好的（第十一节已修好）。
现在三处都接上，用的是同一张歌集封面。

专辑详情头部顺带补上此前没有的：歌集署名、歌集类型的中文呈现、碟数、
厂牌、目录号、以及「共 N 个版本」（发行组内的 release 数）。

### 19.4 专辑分组的三级降级取消 `[需改 spec]`

**spec 现状**（`library/browse-views` → `Requirement: 专辑的分组键三级降级`
与 `Requirement: 派生分组不显示清单与计数`）：
优先按发行组分组，其次按单个发行，两者都无时按
「标准化专辑名 + 发行级署名」**派生分组**。

**改为**两级，且不再有查询时现场派生的分组键：

| 情形 | 列表中的一条 |
| --- | --- |
| 有发行组 | 同组的多条 release 合为一条，代表版本由优选阶梯选出 |
| 无发行组 | 一条 release 就是一条专辑 |

没有上游标识的曲目（手动录入、「无需匹配」入库）在入库时就被挂到一条
**本地歌集**上（`provider_ref IS NULL`，按「歌集名 + 署名」归拢）。
它们因此与上游来源的歌集走同一条取数路径，而不是让专辑视图为它们
单独走一条代码分支——歌集的字段（碟数、封面、类型）对派生分组本来也无处可放。

**行为差异**：完全没有歌集名的曲目此前归进派生分组的「未命名专辑」，
现在 `release_id` 为空，**不出现在专辑视图里**。

「派生分组不显示灰色行与计数」这一条改为「**本地歌集**不显示灰色行，
计数呈现为 `3/-`」——语义不变，触发条件由「没有上游标识」变为
「歌集没有上游标识」。

本地歌集在最后一首曲目离开后自动删除（`DeleteOrphanLocalRelease`）；
上游来源的歌集保留，它同时是清单缓存——这一条 `library/release-catalog`
已有规定，不变。

`AlbumListItem` 的 `Key` / `Level` 与 `TrackFilter` 的
`ReleaseGroupRef` / `ReleaseRef` / `DerivedAlbumKey` 随之取消，
改为 `ReleaseID` / `GroupID` 与 `TrackFilter.ReleaseID` / `ReleaseGroupID`。
`App.GetAlbumDetail` 的参数从 `(key, level string)` 改为 `(releaseID int64)`。

### 19.5 改歌集名的三路处置 `[需改 spec]`

**spec 现状**：`editing/track-editing` 把基本信息三字段一视同仁，
未涉及「改专辑名影响谁」。

歌集升格为实体后，一首曲目的「歌集名」是它所属歌集的属性，
改名默认影响该歌集下的**全部**曲目。按用户第六轮的裁决，
改名时要二次确认影响范围：

| 该歌集下的曲目数 | 行为 |
| --- | --- |
| 1 首 | 直接改，不弹确认（没有歧义） |
| >1 首 | 弹确认，三个选项 |

三个选项（`App.PlanAlbumRename` 给出，`App.ApplyAlbumRename` 执行）：

1. **改这张歌集** —— 该歌集下的全部曲目一起改名。
2. **关联到已有的同名歌集** —— 仅当库中已有叫新名字的歌集时出现，
   只把这一首挪过去。
3. **只把这一首挪走** —— 新建一条本地歌集，原歌集及其余曲目不变。

`release.title` 因此**不能加唯一约束**：不同版次、不同艺术家的同名歌集是常态。

`App.ApplyEdits` 新增尾参 `albumRenameMode`。未给处置方式且该歌集不止一首
曲目时**拒绝保存**并要求先走 `PlanAlbumRename`——歌集是共享实体，
改名会波及同专辑的其他曲目，不该在用户没看见影响范围时发生。

编辑界面对发行级字段（歌集名、厂牌、目录号、载体、国家、类型、年份）
标「歌集」徽标并说明改动对该歌集全部曲目生效（`FieldRow.ReleaseScoped`）。

### 19.6 编辑界面的字段集合与接线边界 `[待修复]`

歌集成为实体后，存储层具备曲目字段与歌集字段的独立更新原语；
这不代表所有字段都已出现在编辑界面。当前 `buildEditSession` 实际返回：

| 层 | 当前界面字段 |
| --- | --- |
| 曲目 | 曲名、曲目署名艺术家、碟号、音轨号、时长、风格、注释 |
| 歌集 | 歌集名、年份、厂牌、目录号、载体、国家、类型 |

- 注释已接入；时长仍可编辑。
- 年份仍以「年份」输入框呈现，不是日期输入框；`ApplyEdits` 没有将 `year`
  转成歌集的 `releaseDate`，保存不会更新年份。
- 歌集艺术家、碟数、音轨数、封面路径尚无编辑字段；封面可经详情抽屉重新获取并采用，
  不等于有手动路径编辑入口。碟数与音轨数的后端保存分支已有，但前端尚未提供。
- 厂牌、目录号、载体、国家、类型的值写入歌集；歌集锁与来源在编辑会话中的读取
  仍有缺口（见 21.3）。

歌集类型的存储取值域为 `album` / `ep` / `single` / `broadcast` / `other`
（`store.NormalizeReleaseType` 归一）。上游给出域外值时归入 `other`，未给时留空。

### 19.7 顺带修掉的四处 `[纯 bug 修复]`

**审查本次改动时发现，用户未报告。**

1. **`credited_name` 写的是整条署名串**。`applyDetailArtists` 对署名串解析出的
   每一位艺术家都写 `CreditedName: &credit`——那是**整条**署名串而不是
   该艺术家自己那一段。`participantGroups` 取
   `COALESCE(ta.credited_name, ar.name)`，于是参与者区把整条署名
   当成了某一位艺术家的名字；FTS 的索引内容同样受影响。
   现在 `track_credit.credited_name` 存的是该艺术家自己那一段。

2. **署名拆分不确定时连带丢掉全部上游关系**。`applyDetailArtists` 在
   `parsed.Uncertain` 时直接 `return`，而该 `return` 在 `d.Artists` 循环**之前**——
   于是一条署名串难解析，会连带丢掉 MusicBrainz 给出的全部作曲、作词、
   器乐演奏关系。两者没有关系。现在只标记待人工确认，关系照常写入。

3. **取值域之外的角色会被写进库**。`applyDetailArtists` 把 `da.Role` 直接
   转成 `store.ArtistRole` 就用，只在 `SetTrackArtists` 里才校验——
   而那里是整组一起报错。现在逐条跳过取值域之外的角色，
   与 `library/artists` 的「SHALL NOT 引入取值域之外的新角色值」一致。

4. **`MarkTrackForReview` 冲掉用户的备注**。它把 `[需确认] …` 写进 `comment`，
   而那是用户自己的字段。改写 `enrich_error`——与第 13.2 节对
   `RecordEnrichFailure` 的同类修复一致（那一处当时改了，这一处漏了）。

### 19.8 部分唯一索引不能直接作 ON CONFLICT 目标 `[纯 bug 修复]`

**实现过程中踩到，记在这里以免重复发现。**

`release` 与 `release_group` 的唯一约束是**部分**索引
（`... WHERE provider_ref IS NOT NULL`，因为本地歌集没有上游标识）。
SQLite 要求 `ON CONFLICT` 的冲突目标**重复该 WHERE 谓词**，
否则报 `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`。

表现是导入全量失败且错误只出现在 `import_item.last_error` 里，
进度条上只显示「失败 N 条」。

### 19.9 代表 release 的选取不受「它自己有没有曲目」影响 `[纯 bug 修复]`

**审查本次改动时发现，用户未报告。**

代表 release 由优选阶梯在**整个发行组**里选，而专辑列表的成员只包含
「用户有曲目的」那几条 release。两者不一定重合：阶梯偏好实体载体，
而用户可能只从数字版入库。

合并逻辑此前拿阶梯的结果去成员里找，找不到就静默退回第一条成员——
于是列表上的 `RepresentativeRef` 与 `RepresentativeRelease` 给出的
不是同一条，**而前者正是清单读取的依据**，专辑视图会去读另一个版本的清单。

触发它只需要普通操作：CD 版与数字版各入库一首，再把 CD 版那首删掉。
CD 的 release 行作为清单缓存保留（`library/release-catalog` 要求如此），
阶梯仍然选它，但它此刻没有已入库曲目。

**修复**：阶梯选中的那一条不在成员里时，用它的身份与发行事实构造列表项；
已入库数仍是全组求和，封面与清单总数缺失时退到组内任一非空值。

### 19.10 遗留观察（第六轮新增）

1. **发行组内的 release 数尚无生产写入路径**。`release_group.release_count`

4. **本地歌集的归拢键是 (标题, 署名) 的大小写不敏感精确比对**。

- 删除 `reka-ui`、`class-variance-authority`、`clsx`、`tw-animate-css`、shadcn CLI 配置与旧 Button/cn。

### 20.2 控件覆盖与风格入口

| 领域 | 当前实现 |
| --- | --- |
| 曲目/候选表格 | 共用 `volt/DataTable.vue` + `primevue/column`；各自仍是唯一业务组件 |
| 侧栏/曲目右键 | 本地 Volt 风格 `ContextMenu`（上游未提供），自动定位/关闭/键盘导航 |
| 排序/高级搜索 | Volt `Menu` / `Popover`，Popover.hide 调用 hide，不再错误 toggle |
| 设置/导入/编辑/输入/确认/歌集改名范围 | Volt `Dialog`，统一焦点/滚动/关闭语义 |
| 文本/数字/下拉/勾选 | `InputText` / `InputNumber` / `Select` / `Checkbox` |
| 操作/状态 | `Button`、`SecondaryButton`、`DangerButton`、`Tag`、`Chip`、`Badge`、`Message`、`ProgressBar` |

不为了“换库”把每个 HTML 标签都包装成库组件。

- 唯一基础调色板为 `--p-surface-*`；中性主色 `--p-primary-*` 引用它，而非复制相同色值。

- DataTable 显式合并传入 PT，不能让业务行属性覆盖整套主题；加了实际 computed style 回归测试。
- 各基础控件布局/语义默认在 `src/volt/` 调整；应用自有色也在 `style.css`，不是第二套主题。

### 20.3 为什么不直接启用 DataTable 原生 selection

审查 PrimeVue 4.5.5 源码发现：范围锚点保存数组下标；普通方向键只移焦点，Enter 选中；
没有逐行不可选的公开 prop。只启用 multiple 再过滤 ghost，仍达不到约定且形成两套逻辑。

因此 DataTable 负责结构、粘性表头、排序事件与原生拖拽；
`useListSelection.ts` 独占选择/锚点/焦点，`trackRows.ts` 独占顺序/位置 identity/曲目去重。
具体行为以 **14.1、14.2、1.8 的交互契约**为准。

额外核对：`value-change` 不是每次 value/sortField 外部变化都触发，不能把它当作唯一顺序源。
统一 `orderedRows` 传入 DataTable 并关闭二次排序，不再猜测其内部 processedData。

### 20.4 歌单手柄与上下文

- 不新增一列：完整歌单在 **# 列**显示原生重排手柄，其他视图仍显示曲序。
  列定义数量/其余列/菜单保持一致。这是 # 单元格的显式视图变体，建议 spec 明确允许。
- 不在冒泡阶段强改 draggable、不访问 DataTable 私有实例。图标插槽明确带
  `data-pc-section="reorderablerowhandle"`，由 PrimeVue 原生重排流程管理。
- 只在默认顺序且没有筛选时可拖动；文字单元格始终可拖选文字。
- 批量拖动/框选/列宽持久化未实现，不将“文件管理器式”泛化为已支持这些功能。

### 20.5 弹窗与 Wails

- 全部模态框用 Volt Dialog；限制视口尺寸、固定头尾/内部滚动，默认不因点遮罩丢弃编辑。
- PrimeVue 4 的全局 Escape 会同时通知多个 Dialog，本地 `dialogStack.ts` 只关闭顶层。
  不能只在弹窗根元素监听：**WebKit 点击 button 后不一定聚焦它**，保存按钮临时 disabled 后
  焦点还可能落到 body，根监听会漏 Escape。新增双浏览器回归已覆盖此场景。
- Select/Popover 已消费 Escape 时，不继续关父弹窗；关闭顶层不关底层编辑器。
- Prompt 输入自动聚焦；破坏性确认默认聚焦取消；取消时恢复可用的来源焦点。
- 右键菜单无进入动画，避免动画期间尚未绑定 outside click/焦点而漏第一次关闭。
- 所有按钮/输入/combobox 默认 `--wails-draggable: no-drag`；安全区与 PaneHeader 仍可拖窗口。
- 搜索页也接入 PaneHeader（48px 主操作行，地区选项另起一行）。

### 21.3 已核实的关键缺口 `[待修复]`

#### A. 后台详情缺少目标曲目标识，且未保存返回的清单

- **依据**：`internal/store/enrichstate.go:35` 的 `EnrichTarget` 只有发行标识，
  `bindings_enrich.go:319` 构造 `provider.Ref` 时没有 `TrackRef`。
  `internal/provider/musicbrainz/detail.go:340` 的 `findTrack` 在该值为空时取发行第一首。
- **影响**：补全第二首及之后的曲目时，可能把第一首的曲名、录音标识、曲序与参与者写进去，
  原 `match_ref` 却仍指向目标曲目。`ApplyDetailToTrack` 也没有将 `Detail.Tracklist`
  交给 `ReplaceTracklist`；目前完整清单保存仅在 `FetchTracklist` 路径。
- **核验**：本地两曲 HTTP 桩件经真实 `RefreshTrackDetail` 执行后，第二首的
  `match_ref=audit-second` 保持不变，标题却成为 `First song`、录音变为 `rec-first`；
  该发行清单仍为 `none`、0 行。
- **建议**：工作集携带并传递曲目级标识；详情落库统一保存整张发行清单，
  增加从非首曲入库到后台补全的完整回归。对应第十三节、`upstream/musicbrainz`、
  `library/release-catalog`，不能仅把文档改成允许串曲。

#### B. 用户锁未被所有详情写入路径遵守

- **依据**：`internal/store/enrich.go:17` 的 `WriteDetailColumns` 直接更新曲名、署名与歌集字段，
  没有读取锁；`applyDetailMeta` 对部分字段的过滤挡不住这条直接写入路径。
  `GetMetadata` 只带出 `track` 的来源/锁，未合并 `release` 的来源/锁。
- **核验**：先用 `UpdateTrackFields(..., true)` 锁定标题，再执行真实
  `ApplyDetailToTrack`；标题被上游值覆盖，而 `locked["title"]` 仍为 true。
- **建议**：曲目与歌集的所有写入口统一遵守各自字段锁，编辑会话读取正确归属的来源/锁，
  并覆盖同歌集多首曲目与后台补全场景。关联 `library/track-library`、
  `editing/track-editing`；既有 F11 测试只调用存储原语，不能证明这条链路正确。

#### C. 署名仍在 MusicBrainz 解析阶段被推断为演唱

- **依据**：`internal/provider/musicbrainz/detail.go:191` 的 `parseRecordingArtists` 遍历
  recording 的 `ArtistCredit` 时仍写 `Role: "vocal"`；`DetailDrawer.vue` 仍将署名区标为「演唱」。
- **核验**：没有任何 vocal 关系、仅有 recording 署名的原始 JSON 经
  `ParseDetailJSON` 后，仍生成该署名者的 vocal 关系。
- **测试边界**：`TestVocaloidAndCreditedComposerReachArtistView` 传入手工构造的
  `provider.Detail`，绕过了上述解析器，因此其通过不能证明真实响应中作词者不会被标成演唱者。
- **建议**：从原始响应分别构造署名与参与角色，只有真实演唱关系才产生 vocal，
  并对抽屉文案与原始 JSON → 解析 → 落库 → 分面做联合回归。对应 19.2 的已确定裁决。

#### D. 灰色行入库未携带所属歌集与位置

- **依据**：`frontend/src/views/AlbumsView.vue:188` 与 `bindings_albums.go:364`
  的灰色行入库路径
  仅传来源、track ref、标题、署名、时长、recording ref；未传已知的发行、碟号、音轨号。
- **核验**：调用后新曲目的 `release_id` 为 NULL，补全状态为 `absent`。
  它仍可通过 match_ref 在清单位置被识别，但没有歌集归属、不能进入该歌集的后台详情补全工作集。
- **建议**：从当前清单/发行取得并传入真实上下文，再经 `AdmitCandidate` 入库；
  回归应验证歌集归属、专辑计数与后台工作集，而不仅是几个共有字段。对应 18.1、19.11。

#### E. 编辑年份及重新匹配/取消的持久化语义不完整

- **年份**：`bindings_edit.go:166` 的编辑字段仍返回 `year`，但 `ApplyEdits` 的曲目、歌集写入白名单
  都没有把它映射为 `releaseDate`。本地核验：2006 年曲目保存为 2015 后仍读出 2006。
- **重新匹配**：`bindings_edit.go:68` 的 `RematchTrack` 仅以候选填充上游字段；`buildEditSession` 的匹配身份
  仍来自旧 metadata，没有返回新候选标识。前端仅在手工改变 `manualRef` 时提交新标识，
  因而普通「更换 → 保存」不会自动把溯源换成新候选，跨源填充还可能记为旧来源。
- **取消与失败**：`frontend/src/views/EditDialog.vue:156` 的 `clearProvenance` 立即调用持久化 API，不等待保存；
  `ApplyEdits` 在校验匹配标识或完成改名确认之前已分步写入，后续报错不能整体回滚。
- **建议**：建立包含新候选身份、待清空溯源与年份/日期映射的编辑草稿；
  保存前完成校验，曲目/歌集/溯源在同一事务提交。补「清空后取消」「非法标识保存」
  与「跨源更换后保存」测试。对应 `editing/track-editing` 的保存前不落盘及溯源覆盖要求。

上述动态核验使用独立临时数据库与本地 HTTP 桩件，没有接触用户数据或真实上游。
它们确认的是缺陷现象，不计入 20.7 的功能通过数；其余条目由生产调用链静态核对确认。

### 21.4 其他未完成项与应明确的边界 `[待修复]`

1. **设置参数**：高置信没有数值门槛是正确的结构性设计，需同步
   `platform/settings` 与 `design.md` 的既有冲突。界面「复核阈值」虽可保存，
   `ReviewThreshold` 未被匹配引擎消费；权重与相似度配置可由后端读取，但没有设置 UI。
   建议先决定复核阈值的用途，再接线或移除，不能写成所有参数均即时生效。
2. **封面尺寸、预取与取消**：自动详情封面仍使用 `CoverArt` 默认的 250px，未实现
   spec 的自动最高质量；手动选图/采用另有高档降级链。搜索页有批量预取，复核页没有；
   前端没有实际调用 `CancelCovers`。建议补目标尺寸与视口跟踪的端到端测试，
   不将浏览器 lazy 属性等同于工作池取消（见 11.3）。
3. **入库字段与来源**：`AdmitCandidate` 未将 `Candidate.Year` 写为歌集日期，
   并以 `ArtistName` 同时作为歌集署名；候选自身没有独立的歌集署名字段。
   初次候选入库也未逐字段记录 provider 来源。需明确候选字段契约并补持久化映射，
   不将「不用表格值补缺」扩大为「候选全部字段均无损保存」。
4. **歌集配套能力**：`release_count` 主动获取/手动编辑、`release_credit` 生产填充、
   歌集独立编辑入口仍未实现（19.10）；19.6 列出的部分歌集字段缺少编辑入口。
5. **导出与规模**：字段深度 UI 仍固定 full；无分页/虚拟滚动性能验收。
   快速 FTS 在 `internal/store/library.go` 中取最多 2000 个 id，因此
   大规模筛选并非无上限；后续需明确结果截断或分页语义。
6. **不确定署名的人工处置**：`MarkTrackForReview` 只写 `enrich_error`，
   `TracksNeedingReview` 未接入复核界面，成功补全后的 `SetEnrichState` 还会清掉该错误。
   不能声称此类曲目已经进入可操作的复核队列；需单独持久化标记并提供处置入口。
7. **出网提示与禁用态**：后端有前置条件检查，但详情的「重新获取封面」按钮未按
   `outboundAllowed` 禁用/提供设置跳转；搜索、复核等页面仍有局部错误提示，
   并未全部统一到全局提示位置。需补全 UI 状态与错误事件接线。
8. **iTunes 生命周期**：原始响应缓存与清单读取有 TTL，已入库 track/release
   元数据没有统一过期清理或重取机制。不能据缓存测试宣称全部 iTunes 元数据都满足
   spec 的短期留存要求；需单独明确已收藏元数据的生命周期与条款边界。
