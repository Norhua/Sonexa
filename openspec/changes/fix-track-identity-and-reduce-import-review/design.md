# Design

## Context

动机和范围见 [proposal.md](proposal.md)。本设计将“本次输入对应哪个 track”和“该 track 是否已收藏”分开，规格分别集中在 `matching/confidence`、`matching/pipeline` 与 `matching/provenance`。

已核实的实现与旧约束：

| 位置 | 当前行为 | 本次处置 |
|---|---|---|
| `internal/matching/provenance.go` | 精确 ref、ISRC、无绑定文本命中均返回本地目标，并生成合并动作 | 候选所有权只保留精确绑定；相关性与所有权分离 |
| `internal/app/bindings_upstream.go`、`ReviewView.vue` | 非零 `localTrackId` 决定已在库中或调用 `MergeCandidate` | 使用结构化所有权及接受/跳过动作，不按关联 ID 分流 |
| `internal/store/migrations.go` | `track(match_source,match_ref)` 唯一，ISRC 只有普通索引 | 保持收藏约束，不增加 Recording/ISRC 唯一性 |
| 初版提交 `04b12d3` 与归档 v1 规格 | 同时要求 track 粒度与 ISRC 桥接合并 | 明确替换旧候选合并行为，而非将其继续解释为正确的多版本规则 |
| `matching.Engine.CheckLocalDuplicate` | 只看无上游绑定曲目，命中即复核 | 移除该前置短路；用本地召回参与完整输入判定 |
| `matching.ScoreCandidate` | 高置信为曲名加署名/歌集任一精确；有 relevance 时不计时长 | 保留展示评分，自动资格改用独立证据 |
| `library.selectCandidate` | 先跨组否决，再考虑已有发行；不了解原始输入的完整限定 | 将输入证据传到决策入口，先收敛目标，保留真正的跨组歧义 |
| `importer.Runner.processItem` | 输入只传曲名、歌手、专辑和时长，未使用已存年份/碟号/轨号 | 传完整输入与字段语义 |
| `provider/musicbrainz` | 缺位置时生成 recording@release，当前准入可保存该合成标识 | 展示保留，接受/自动选定前解析真实位置 |
| `store.queue`、`bindings_review` | 原始行就是复核项；状态更新不普遍校验修订 | 分离原始行与活跃问题，所有修改有范围和 CAS 校验 |
| `store.CommitAdmission` | 精确重复可原子返回旧曲目，但按 imported 结束且只支持一个导入 ID | 结果分新增/已存在；支持获批输入集合与精确跳过 |
| `internal/lyrics/search.go` | 直接使用现有 matching 比较和默认评分 | 新元数据证据函数不改变现有歌词调用行为 |

只读样例提供了可复现基线：`you` 的特典 CD track 为 `f0a33d1a-628a-4a53-bc4e-6af077505956`，合集 track 为 `f4458acc-aa40-40b0-a0b7-aaa27df24b04`；两者同 Recording `2283ceda-78b1-4d20-8f52-bdf73bd53686`、同 ISRC `JPE301500361`，但发行与组不同。新测试使用固定 fixture，不依赖开发者应用数据库。

现行主规格仍有“候选 ISRC 本地命中”“疑似重复直接复核”“跨组一律复核”“逐行独立处置”的约定。本变更通过对应 delta 明确替换它们；规划阶段不修改主规格或另一活动歌词变更。

## Goals / Non-Goals

**Goals:**

- 收藏目标稳定为来源精确 track；当前输入识别、默认选版、候选已收藏三种结论分别建模。
- 多格式输入使用同一套可解释证据，原文保留；不同专辑/版本不会被去重吞掉。
- 确定的已收藏目标自动跳过；不能确定时尽量只让用户处理一个相同语义问题。
- 纯决策可离线测试；网络只补确有必要的事实，提交只消费已准备的事实与批准。
- 所有语义变化都有正例、反例和真实业务入口回归，不能仅以新的数量断言证明正确。

**Non-Goals:**

- 不构建“旧输入/文件指纹 → 上次选择”的学习或复用表；不让历史人工选择为新输入授权。
- 不做跨来源 track 自动实体统一，不按 Recording/ISRC 合并收藏，不改专辑聚合展示的身份规则。
- 不新增音频扫描、指纹、外部翻译或 LLM 身份判断，不保证没有任何共同文本/来源证据的纯译名必然匹配。
- 不取消新增发行成员确认，不自动接受人工明确选中的另一个版本，不新增“批量接受最高分”。
- 不把无绑定本地收藏的文本相似升级为上游精确绑定；这类实体换绑仍属于明确编辑操作。
- 不改变歌词候选、Top 3、自动预览或当前值/快照同步规则，不转换历史应用数据。

## Decisions

### D1. 精确所有权与相关性分离

引入元数据候选所有权结果，含 `unowned / owned / identity_conflict / lookup_error`、精确目标身份、可选已有本地 ID、已读绑定修订。`owned` 只由来源精确 track 命中且发行关系一致产生。关联录音、ISRC、相似文本即使将来用于提示，也置于独立的 related evidence，不能写进拥有状态的目标 ID。

`CandidateRow` 返回结构化 `ownership` 和动作枚举；显示文案由上下文决定：复核 `accept/skip`，搜索 `add/owned`。不使用中文 action 字符串或非零相关 ID 作为业务分支条件。来源错误不能被 `applyLocalMatch` 当成未收藏；界面保留候选并显示错误、禁止在未知状态下执行跳过。

本地图片 `releaseId` 和 `CoverRevision` 仍按候选自己的发行取得，不沿用相关曲目的封面。删除复核 `MergeCandidate`、`MarkMerged`、旧简化本地候选快照及合并动作路径；保留编辑器的专辑组/成员合并能力，它与本问题无关。

**备选否决：** 只改“合并”为“跳过”会保留 ISRC 误判；仅改复核前端会留下搜索页阻止添加及后端绕过问题。

### D2. 元数据输入证据使用独立模型

在 `internal/matching/` 内增加 `InputProfile`、`FieldEvidence` 和元数据专用比较入口，输入保存以下维度：

- 三个文本字段：原文、完整主体、可接受异写及依据、截断状态、未知片段。
- `recordingVariant`：版本类型及完整限定负载，如 remix 作者、演出场次、重录/重制年份。
- `releaseQualifier`：豪华/限定/再版、已明确国家或载体等本次实际提供的限定；不增加新导入列，先解释现有文本及映射值。
- `creditEvidence`：完整角色/声优、主署名和显式合作信息；只描述匹配证据，不修改艺术家实体。
- 已有映射的年份、碟号、轨号、时长及其值/缺失/解析失败状态；含规则版本。

`FieldEvidence` 至少区分 `exact`、`verified_alias`、`compatible_truncation`、`fuzzy`、`unknown`、`conflict`，并保存证据来源和采用的比较形式。空字段相同不产生 exact，截断不产生 exact，规则无法解释的内容不通过去括号悄悄消失。

字符规范化只用于比较，原文和上游快照不改写。对名称的标点差异提供比较键，但版本/角色提取在信息丢失之前执行；`A Remix` 和 `B Remix` 的负载分别保留。明确支持 `(Vocal) you`、`you(Vocal)` 作为普通人声描述与 `you` 对照，仍与 `Off Vocal` 区分；不能因复用旧“未知括号全剥离”逻辑误吞这一层语义。

可靠异写按证据分级：明示译名/读音、来源提供的别名是明确依据；无提示的跨文字系统括号只先生成备选，只有完整共同主体及独立的其他字段/目标事实共同支持、且无版本或身份限定时才提升为可用格式差异。只有脚本不同、词元包含或 Jaro-Winkler 高分不提升为身份等价；未知注释原文不相等时，自动资格保持不足。规则表和负例将明确这些界限，不增加按单首歌曲特判的名字白名单。

新的元数据比较器可以复用无副作用的字符/括号解析函数，但不直接修改旧 `CompareTitle`、`CompareCredit`、`ScoreCandidate` 的歌词行为。元数据自动证据与检索展示证据同时存在，词义规则集中在 matching，不散落到各来源。

**备选否决：** 统一哈希原始行无法识别译名；统一删除括号会把 Live、remix、限定版和不同角色折叠；把现有宽松展示比较直接用于自动身份会扩大误跳过。

### D3. 候选解析能力由业务声明，上游解释自身标识

matching 声明其消费的候选身份/决策资料接口，通过应用装配注入来源能力；数据结构采用通用的来源身份、位置要求、精确程度和完整性。library 的准入入口复用该解析能力。provider 根包保留公共数据，具体来源包实现接口，不向业务暴露 MusicBrainz 的 `@` 编码判断、iTunes 地区拼接或 QQ MID 规则。

能力分两类操作：

1. 已有候选事实的无网络身份检查，返回 `exact / unresolved / invalid`。
2. 按需 `resolve target / load decision facts`，返回精确候选集合、目标发行事实、清单完整性和错误，不创建收藏。

MusicBrainz 真实 track 直接校验现有来源/发行关系；只有缺关键目标资料时补取。合成候选通过指定发行的清单定位 recording 及位置，多个可能位置返回集合，未找到、部分清单不足或网络失败各自返回明确状态。一个 recording 在同发行出现多次时不以首项或已收藏状态选位置。iTunes/QQ 精确候选按已有来源规则返回，不为满足统一接口额外出网；未提供能力明确 unsupported。

选定合成候选后 UI 仍只有接受入口；若解析出多个真实 track，回到候选列表让用户选具体位置，不保存合成身份。提交到 library 的 seed 必须携带已解析精确身份；来自旧或直接 API 的未解析 seed 也不能绕过约束。

一次解析内按发行身份复用摘要/清单响应，优先已有有效清单和 HTTP 缓存。最多针对当前有界检索所得候选涉及的发行取必要事实，不遍历原生组；遇尚不能排除的未知竞争者不能直接丢弃以制造唯一答案。网络在数据库事务与长期锁外，服从现有共享桶、重试和取消。

**备选否决：** 继续收藏合成 ID 会使以后真实 ID 入库再产生重复；业务中 switch 来源会违反来源差异隔离约束；全组枚举会无界扩大网络成本。

### D4. 单一决策流水线：先确定输入目标，再执行偏好和所有权

将 `Runner` 与 `library.SelectCandidate` 连接为同一决策用例，入口接收完整 `InputProfile`、输入/问题修订以及候选事实，而不仅是 `HighConf` 数组：

```text
InputProfile
    --> local recall + upstream recall when needed
    --> metadata evidence for each target
    --> constrain album / recording variant / position
    --> resolve missing decision facts and real track
    --> eligible same-group same-content targets
    --> explicit constraints or compatible-edition preference
    --> exact ownership check
          owned   --> skip-existing transaction
          unowned --> admission plan / required confirmation
          unclear --> one review problem with reasons
```

自动候选资格的顺序与默认值：

1. 曲名必须为可靠原名/异写对应，模糊标题不能只因分数高自动处理；至少有署名或目标专辑可靠正证据。
2. 明确录音版本或角色/合作冲突直接阻止该候选自动入选。输入未写版本不作为等价于任何显式录音版本的证据；不放宽普通版对 Live/Off Vocal 的现有保护。
3. 已给专辑必须对应目标专辑，允许有区分力的截断相容，但需完整目标事实支撑。目标专辑不符的候选可以留在人工列表，不进入自动竞争集合。相同专辑标题也不能凭名称宣称两个实际发行相同。
4. 艺术家列与歌曲署名不同，只有来源的发行署名、结构化成员或角色关系及其他目标证据足以解释时才不是冲突；同声优不授权跨角色。
5. 位置在目标发行内检查；碟号未知不默认 1。同发行多个可能 track 必须消歧。明确位置与候选冲突阻止自动选择，解析失败不变成零。
6. 时长检查独立于 relevance：差 ≤3000ms 为支持，3000–10000ms 为弱相容，>10000ms 阻止自动选择。秒级格式的舍入在解析精度内处理，不增加比例越长越宽的无限容差。时长不能证明专辑或发行相同。
7. 一般“年份”列只作带语义的旁证；输入未说明是首次发行或再版时不作唯一决定。专辑/版本文字明确的重制年份属于显式限定。
8. 若仍有可改变结论的未知事实，补取必要资料，不能把未知当不匹配排除。查询结果有上限，因此“唯一”仅在本用例有足够正证据与可用决策范围时成立，不宣称枚举了全世界所有发行。
9. 本次输入收敛后仍跨组、不同内容或同发行位置不唯一则复核。已被输入排除的跨组候选不再触发旧 `TestCrossGroupNeverAutoSelects` 式全列表否决。

细发行未被输入指定时，且已确定单一目标组、同内容及无位置歧义，采用以下**默认偏好**，不称其为身份等价：

```text
已收藏的兼容 track
    > 包含兼容候选的已有发行
    > 已知发行总曲数更多
    > 已知非世界国家
    > 稳定来源/发行/track 顺序
```

多个已收藏兼容 track 在同一可比较组内可以按后续偏好选一，不新建；同发行重复位置先消歧，不能进入偏好。未知总数仅在实际需比较的子集内补齐，仍未知则复核。输入明确指定另一专辑、Live、限定版或位置时，任何已收藏优先都不得覆盖。

`you` 的固定验收：特典 CD 的区分性截断专辑、对应署名与真实 track 事实成立后，合集不进入自动集合；特典 track 已收藏则跳过，没有则准入。若把输入换为合集，必须选择合集 track；若去掉专辑且保留两个跨组候选，则复核。

**备选否决：** 最高分直接自动选、跨组一律复核、先选已收藏再检查输入，分别会造成误选、无谓人工成本和吞掉新版本。

### D5. 本地召回是事实源，不是结论捷径

store 提供批量本地召回接口：使用候选键索引/FTS 获取候选 ID，再读取完整当前值、有效 track/release 快照、署名关系及清单。不得依赖有 2000 条上限的浏览接口作为全库去重查询；候选召回截断须明确表示，不能伪称唯一。

- 当前用户值可解释输入的显示名称；绑定快照提供上游事实。按来源分别比较并保留出处，不从多个矛盾快照拼出一条完全匹配的假候选。
- 同精确身份的本地/远程结果合一，事实冲突保留来源与修订，必要时补取或复核。
- 纯本地快速跳过需要与完整流水线相同的正证据：输入能可靠限定目标专辑/组和歌曲，已给的版本/位置/时长均满足，已有有效发行清单或等强的精确位置事实足以排除目标内位置歧义，且没有未解决的竞争目标。输入未指定细发行时可依 D4 的显式默认偏好使用已收藏兼容 track，而不是宣称本地唯一就全球唯一。
- 只有曲名、歌手或一条稀疏本地快照时继续上游查询。精确候选所有权不需要查历史导入；没有旧批次也必须同样工作。
- 未绑定本地曲目可成为相关提示，但不返回精确上游所有权，不给它自动写绑定。用户仍可明确接受上游 track 或在编辑器处理原收藏，不能为了减少重复数悄悄改用户收藏。

**备选否决：** 全库模糊命中后直接 skip 不能区分专辑版本；继续只查无绑定曲目会漏掉绝大多数已有收藏。

### D6. 活跃语义问题与导入原始行分离

保留 `import_item` 作为批次行记录，新增活跃 `review_problem`、成员关系及证据字段（具体列名在实现时可按风格调整，语义固定）：

| 数据 | 内容 |
|---|---|
| `import_item` | 原始值、profile/rule version、独立状态/错误、整数 revision、resolution reason/target |
| `review_problem` | 稳定 ID、active/closed、语义锚点、等价证明、revision、候选事实及查询修订 |
| `review_problem_item` | 问题与输入行、一行最多一个活跃归属；关闭问题后保留诊断或清理非必要数据 |
| 派生匹配索引 | 带规则版本的名称/异写/版本键；由当前事实和活跃输入重建 |

**归并是有证明的等价，不是相似度聚类：**

- 文本路径要求非空、可靠的歌曲/署名/目标专辑锚点，录音及发行限定一致，已给字段的缺失掩码一致，数值要求一致。时长表示不同但换算相同可归并；不使用“差 3 秒”构造可传递的输入等价。
- 不确定注释不同、短截断无法证明尾部相同、无专辑与有专辑、无位置与明确位置均不自动归并。
- 身份路径可以使用当前证据明确解析到同一个精确 track 的输入，但仍核验所有明确要求没有冲突；即使最终都能选择同一 track，也不能用弱集合重叠证明相同问题。
- 不把别名集合相交或两两相容做传递闭包；A 对 B、B 对 C 的弱相容不能授权 A 与 C 同问题。新成员须对统一锚点和现有证明重新校验，必要时拒绝归入。
- 保守的 blocking key 只缩小候选问题范围，不负责最终判定。事务内重新核验并创建/加入问题，保证并发同语义只留下一个活跃问题。
- 未解析无结果的输入也可在上述强文本条件下归并，不需要先有 track 或历史选择；证据不足的缺字段行保持独立。

首次实现仍可逐行执行匹配，正确归并发生在进入 review/failed 之前；共享相同网络请求只能作为优化，不能让一个输入的弱结论被其他输入继承。已归并问题的再次处理、失败重试只处理列明成员；单批暂停不自动取消其他批次的独立运行。

人工可把来源行拆出。拆出设置当前活跃工作范围隔离标记，防止下一次自动整理立即把它合回；这不是历史音乐身份记忆，问题完成后不用于未来输入判断。

**备选否决：** 前端去重会导致后端计数和动作不一致；按原始行哈希解决不了异写；按候选池相同归并会把特典/合集两个意图混合；通配缺失字段会导致链式误归并。

### D7. 接受与跳过采用有界计划和原子结果

扩展 `AdmissionSeed/Baseline` 的输入范围：单行自动导入或多行问题都变成同一种 `InputScope`，包含问题 ID/revision、成员 ID/revision、profile/proof version 和候选事实修订。保留现有计划 Hash、过期、确认凭据与 `operation_result` 的同请求幂等，不将操作结果用于新输入查找。

- **接受：** 先解析真实候选和必要准入事实，生成计划。事务内检查队列状态/范围，核验来源 track 及发行一致性。新目标仍走既有组/成员确认；目标已被另一请求收藏则只返回旧目标并跳过，不能更新其字段。
- **跳过：** 准备轻量 skip 计划，绑定精确 target、本地 ID/绑定修订及输入范围；不要求发行新增确认，不发网络。提交时目标不存在或换绑则失败，不转为“跳过任意相关曲目”。
- **多行：** 任一范围或等价检查失效则整体回滚。新建一个 track 时以成员 ID 稳定顺序确定唯一创建行，其余记 `skipped/existing_track`；目标原本存在时全范围 skipped。问题无活跃成员后关闭。
- **重入：** 同成功 plan 返回同结果；另一旧 plan、旧改搜或旧 retry 必须 CAS 失败，不能恢复终态。检查范围应早于任何会产生实体变更的分支。
- **本地无需匹配：** 先选择单个来源行，继续既有原始值准入，不借多行问题一次创建多份或以文本把其他行自动跳过。移出可选择单行/列明范围；无一匹配及改搜更新问题当前查询与候选，但原始行不变。

来源身份、实际新增与各输入处理结果由服务端结果返回。`App.CommitAdmission` 根据是否真实库变更通知 library 与补全，skip 只通知任务，防止循环重评。

**备选否决：** 沿用 `MarkMerged(itemID,targetTrackID)` 或任意 `setStatus` 无条件 UPDATE 无法验证身份与迟到请求；只在前端禁用按钮不足以保护并发。

### D8. 事件驱动地重评活跃待办，并保护用户正在操作的范围

收藏新增/删除/换绑及有效事实变化后，由应用提交成功通知调度后台重评；匹配索引给出受影响问题，更新事件按范围合并，重评有界执行、重读最新 revision。重评默认只消费现有库/候选事实；确需出网的输入继续既有匹配工作队列和门禁，而不是打开复核页即搜索。

重评与人工接受都使用同一 profile/decision 函数；只对重新得到确定已收藏目标的输入 skip。一个问题的人为选择不能被当作其他问题的指定目标。所有持久化结论保留“当前规则与事实得出”的原因，不增加历史输入映射。

复核页获得问题的短期交互租约：聚焦/编辑、改搜、确认期间保护当前范围，离开/卸载释放，意外退出有超时回收；租约续约不轮询库数据。后端在受保护范围内允许刷新候选拥有状态，但暂缓自动结束/重组；新加入成员使计划失效，不静默扩展当前操作。迟到请求带问题与查询修订，写回必须 CAS。租约释放后合并安排一次重评，避免长期遗漏。

刷新问题采用稳定 ID，与现有 request revision 策略一致；新 `review:changed` 事件覆盖纯跳过、问题成员变化和库触发重评，前端任务汇总不必依赖导入正在运行。

**备选否决：** 仅在前端丢弃旧响应不能阻止后端 `MarkReview` 恢复终态；全库变更都重新联网搜索会放大配额成本；复制一次人工选择到所有相似输入又回到了历史复用错误。

### D9. 行统计和问题统计使用不同单位

`BatchStats` 以 import_item 为单位：`Total = Queued + Matching + Imported + Review + Failed + Skipped + Discarded`。`Unmatched` 是 Review 子集，`ExistingSkipped` 是 Skipped 子集，不能再次相加。Processed 延续“本轮已处理”概念，review/failed 可计已处理但不表示用户全部处置完。

全局与每批关联问题单独计算 `ReviewProblems`、`PendingProblems`、`FailedProblems`、`SourceRows`。一个问题有可处置 review 成员时归 Pending，只有活跃成员全部 failed 时归 Failed；跨批问题不可简单把各批问题数相加为全局。

UI 标注“X 个待处理问题，涉及 Y 行”；多来源问题展开原始曲名/艺术家/专辑、位置/时长、文件与行号。接受/跳过前操作范围清楚可见；无需匹配先选择原始行。导入页新增“已存在跳过”，不将返回旧 ID 的 imported 计入新增。日志输出结构化原因对应的短句，分值仍是检索分，不显示百分之多少正确版本。

### D10. 验证矩阵和边界

采用 fixture + 真正应用/Runner/Store 入口，不只测试旧 `Engine.Run().Decision`（生产导入现在由 library 选版，旧 acceptance 单测不能代表完整入口）。新增表格成对样例在 `testdata/`，每行固定预期的来源/track/发行和处理原因。以下为必过集合：

| 集合 | 正例 | 必须保留的反例 |
|---|---|---|
| 所有权 | 同 source+track 重复接受返回旧 ID | 同 ISRC/Recording 不同 track、不同来源、发行冲突 |
| 异写 | 原名/可靠译名/读音/全半角/等值时长得到同目标 | 未知注释、无共同证据纯翻译、A/B Remix、不同角色 |
| 专辑 | you 特典 CD 截断收敛、改为合集可添加第二版 | 无专辑跨组、短通用前缀、同名不同专辑 |
| 位置 | 明确第二碟轨号、合成候选唯一解析 | 同发行重复录音、部分清单局部唯一、碟号缺失 |
| 自动默认 | 同组同内容未指定细发行优先兼容已收藏 track | 显式新版本不被已有优先覆盖、跨组不默认 |
| 本地召回 | 无历史批次也能从有效快照识别、用户改名仍保留值 | 稀疏本地唯一、旧绑定、无绑定文本不假装已拥有 |
| 问题归并 | 两表异写只留一问题、跨批来源保留 | 相同候选池不同意图、缺失通配、非传递链式相似 |
| 事务 | 两行一次接受只新增一首；并发同 track | 删除/换绑后 skip、确认期间新增成员、写盘/DB 失败 |
| 异步 | 新收藏只关闭重评明确命中的待办 | 迟到改搜恢复终态、当前交互被后台结束 |

前端 Playwright 覆盖真实按钮分流、问题来源/计数/拆出、取消后草稿保留、library/review 事件及竞态。Go 测试验证真实持久化结果与身份，不用浏览器桩件替代后端验证。保留未匹配样例，不以提高召回数作为成功指标；对照记录“独立复核问题数、错误自动接受/跳过数、新增收藏数、请求次数”。固定反例中错误自动接受和跳过必须为零，格式等价样例不重复新增、复核问题数按等价组计算。

## Risks / Trade-offs

- [译名/版本语义无法穷尽] → 只提升有明确证据的异写，未知保守复核，使用可扩展规则表与反例，不以同脚本/跨脚本直接判同一。
- [本地已有偏好被误解为客观唯一] → 先完成目标范围与内容检查，输出默认策略说明；显式限定与人工选择优先。
- [细节补取增加 MusicBrainz 请求] → 只取当前决策所缺事实，同发行复用缓存，数量有界，不枚举全组；报告请求计数作为回归指标。
- [强规则降低部分自动匹配率] → 检索展示保持宽松，先用来源结构化关系解释差异；仅必要的不确定情况人工处理，不让猜测换取更低队列数。
- [多行问题扩大确认影响面] → 显示来源范围，严格证明等价，提供拆出，全部成员修订纳入计划并事务重验。
- [索引或队列租约失效] → 派生证据可重建，整数修订/CAS 保底，租约超时回收，启动时重新核验活跃范围。
- [共享 matching 改动影响歌词] → 新元数据策略独立入口，现有歌词样例及 Top 3 回归结果必须保持，活动歌词文档不修改。
- [旧测试证明的是旧行为] → 明确替换合并与无条件跨组守卫，补同业务入口正反例；保留真实跨组、位置与成员准入保护。

## Migration Plan

1. 仅在 apply 阶段新增模型/接口、事务与测试，再接入候选和导入流程；以小范围中文约定式提交分阶段保存。
2. 开发阶段使用清空应用数据后的新库。模型代际需能拒绝旧结构，不能在旧库上悄悄假定新增队列字段已存在；不运行自动删库、不迁移历史 merged 或合成收藏。用户清理数据由用户执行。
3. 移除旧合并绑定与状态统计，重新生成 Wails 类型，并在 frontend stub/测试中同步协议；不保留能绕过新身份校验的旧 API。
4. Go/前端定向与全量验证完成后同步受影响主规格及 README/架构说明，再按独立请求归档。本次 propose 只写当前变更目录，不把规划当作已实现行为。
5. 回滚使用对应代码提交和测试新库重新初始化，不把新库交给旧模型读取；如需保留测试数据，应在用户明确安排下备份，不在实现中擅自导出或清理。
