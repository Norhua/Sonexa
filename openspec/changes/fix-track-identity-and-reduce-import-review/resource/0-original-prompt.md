### 调查结论：数据库允许，候选操作拦住了

当前数据库的收藏唯一约束是：

```text

```

Recording 和 ISRC 都没有全库唯一约束。因此，不同 track 共用同一个 Recording/ISRC，在存储层是允许的。

主要错误发生在这条调用链：

相关位置：

- internal/matching/provenance.go：将 ISRC、文本命中也纳入本地判定。

### “合并”来自最初版本的设计矛盾

Git 中最早的相关实现是 04b12d3，初版规格定义了：

│ 标识匹配 → ISRC 桥接 → 文本疑似匹配 → 提供“合并”。

当时“合并”的含义其实不是合并两个收藏实体，而是：

│ 认为这条导入记录对应已有收藏，因此不再创建歌曲，直接结束任务。

但同一份初版规格又明确规定收藏粒度是 track，不是 Recording。这两套规则存在冲突，后续候选页面沿用了前者。

因此，修复方向不是放宽数据库约束，而是：

1. 删除候选“已收藏”判断中的 ISRC、Recording、文本替代路径。
2. 删除复核里的“合并”分流。
3. 不同 track 可以分别接受、分别收藏。
4. Recording 聚合只用于展示，不影响收藏身份和添加权限。

3. 目标：不同格式的输入也能识别同一个 track，减少重复添加和复核

这里需要重新设计的是输入匹配流程。

核心流程应是：

```text
  本次输入
      --> 理解格式差异，提取歌曲与版本信息
      --> 找候选
      --> 根据本次输入确定目标专辑、版本、位置
      --> 选定具体 track
      --> 检查这个 track 是否已收藏
            已收藏：自动跳过
            未收藏：正常入库或执行必要确认
            无法确定 track：进入复核
```

### 第一步：统一处理格式差异，但不抹掉版本差异

对于你的例子：

```text
  歌曲原名,       歌手原名,       专辑原名,       10:20
  歌曲原名(译名), 歌手原名(异写), 专辑原名(译名), 10:20
```

两行可以经过文本处理后获得相同的匹配依据，不需要查询任何导入历史。

但不能采用“把括号全部删除”的办法，应区分：

┌─────────────────────────────────┬──────────────────────────┐
│ 内容                            │ 处理方式                 │
├─────────────────────────────────┼──────────────────────────┤
│ 全半角、大小写、空白、标点形式  │ 统一比较形式             │
├─────────────────────────────────┼──────────────────────────┤
│ 可识别的译名、读音、别名        │ 作为同一字段的备选写法   │
├─────────────────────────────────┼──────────────────────────┤
│ Live、Remix、伴奏、重录、重制等 │ 保留为版本信息           │
├─────────────────────────────────┼──────────────────────────┤
│ 豪华版、初回限定版等专辑后缀    │ 保留为发行信息           │
├─────────────────────────────────┼──────────────────────────┤
│ 无法确定含义的括号内容          │ 保留，不能直接当翻译删除 │
└─────────────────────────────────┴──────────────────────────┘

特别是版本信息不能只保留一个 Remix 关键词：A Remix 和 B Remix 仍可能是不同版本。

现有代码已经有曲名译名、署名异写处理，但专辑仍主要使用普通文本相似度比较；这些处理需要统一到“输入识别”中，同时收紧不确定注释的自动判定。

### 第二步：本地曲库和上游都可以提供候选

目前本地前置检查只看“没有上游绑定”的曲目，这不适合判断导入输入是否对应已有收藏。

新方案应：

- 从已收藏曲目的当前信息、有效上游快照中召回候选。
- 本地证据不充分时，继续查询上游。
- 本地和上游命中同一个精确 track 时，作为同一个候选处理。
- 不因某个候选在库，就提前认为它正确。

这里必须区分：

│ 文本相似可以把某个 track 找出来，但不能直接证明这次输入就是它。

同样，“本地只找到一首”也不代表不存在其他发行。

### 第三步：先利用专辑和版本信息消除歧义，再自动选版

这是当前规则最需要调整的地方。

现在的高置信规则是：

```text
  曲名匹配，并且歌手或专辑至少一项精确匹配
```

这导致：歌手匹配了，即使专辑不符，候选仍可能成为高置信。 随后多个候选又因为跨发行组进入复核。

建议改成两层判断：

- 搜索展示层：可以宽松，保留可能有用的候选。
- 自动决策层：必须结合本次输入的专辑、版本、位置等证据，不能让一个字段的匹配抵消明确冲突。

具体规则：

┌────────────────────┬───────────────────────────────────────────────────────────┐
│ 本次输入提供的信息 │ 自动决策中的作用                                          │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 曲名及译名         │ 确定歌曲名称是否对应                                      │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 艺术家及结构化署名 │ 判断演唱/署名是否对应；不能只因同一声优就认定角色版本相同 │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 专辑名及可靠异写   │ 确定目标专辑，排除明确属于另一张专辑的自动候选            │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 版本描述           │ 明确冲突时禁止自动选择                                    │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 碟号、轨号         │ 在目标发行中定位具体位置，不能跨专辑单独比较              │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 时长               │ 接近是旁证，明显差异阻止自动判断；不能单独证明版本相同    │
├────────────────────┼───────────────────────────────────────────────────────────┤
│ 年份               │ 作为辅助证据；需区分首次发行年与当前发行年                │
└────────────────────┴───────────────────────────────────────────────────────────┘

缺失信息是“未知”，不是“匹配”；模糊或截断信息也不能伪装成精确一致。

另外，当前导入已经保存了年份、碟号和轨号，但匹配输入没有把它们传入选版流程；MusicBrainz 有相关度分数时，当前评分也不会使用时长补分。 这些已有信息
没有充分参与判断。

### 用你的 you 举例

本次输入中的专辑是：

```text
  冴えない彼女の育てかた 第4巻 特典C...
```

两个候选：

- A：第4巻 特典CD
- B：ギャルゲーカバーソングコレクション

新规则不应只是算出 A 为 92、B 为 80，然后因为跨组就全部复核。

而应判断：

1. 输入包含有区分力的 第4巻 特典C...。
2. A 与这个截断信息相容，B 是另一张专辑。
3. 必要时查看完整发行信息、清单，确认是否能定位到 A 的具体 track。
4. 能确定 A：检查 A 是否已收藏，已收藏就自动跳过。
5. 不能确定：保留复核。

这次跳过的依据是当前输入与 A 对应，不是“上一次选过 A”，也不是“A 在库”。

B 仍可以作为人工候选供你选择；如果你明确选择 B，就接受 B，不能被同 ISRC 拦住。

### 第四步：同一张专辑仍有多个发行时，明确区分“身份判断”和“选版策略”

即使歌名、歌手、专辑、时长全部相同，也可能对应同专辑的不同再版 track。文本本身无法提供不存在的信息。

为了减少复核，我建议保留并明确这条策略：

│ 已确定同一专辑组、同一录音内容，且不存在版本或位置冲突时，如果输入没有指定更细的发行，优先采用已收藏的兼容 track。

但它有边界：

- 输入明确指向另一张专辑：不能沿用旧收藏。
- 输入明确指向不同发行版本：不能沿用旧收藏。
- 同发行重复收录、位置无法区分：仍需复核。
- 连目标专辑都无法确定：不能仅因库里有一个版本就跳过。

这是对未指定发行的默认选版，不是宣布不同 track 是同一个。 用户明确选择另一个 track 时，仍允许收藏。

### 第五步：复核中的重复问题，也按当前语义处理

对于尚未解决的重复条目：

- 两行虽有翻译、括号等差异，但能确认表达的是相同歌曲、相同目标专辑和相同版本要求：可以作为一个复核问题展示，保留各自来源。
- 只是命中了相同 Recording，或者候选列表有重叠：不能合成一个问题。
- 一条指定 Live，另一条没有指定；或两条专辑不同：不能因为歌名相同就归并。
- 一个 track 入库后，对相关待办重新运行当前匹配判断；能明确对应它的自动跳过，仍有歧义的留下。

这不是复用历史选择，而是用同一套当前匹配规则处理当前待办。

────────────────────────────────────────────────────────────────────────────────

最终应统一成两个独立判断：

1. 这次输入想要哪个 track？——依靠文本语义、专辑、版本、位置、时长等证据。
2. 这个 track 是否已经收藏？——只依靠精确绑定身份。

前者负责减少复核，后者负责防止重复入库。ISRC、Recording 不能越过这两个判断，把不同专辑的 track 强行视为已收藏。
