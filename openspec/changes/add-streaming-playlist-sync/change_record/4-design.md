## 1. 术语

| 术语 | 含义 |
|---|---|
| 组 G、发行 A / B | Sonexa 本地发行组与其中的具体发行。A 指库内已有的发行，B 指候选所在、可能需要新建的发行。 |
| 歌曲 s | 正在准入的那首歌：候选或计划里的曲目快照（曲名、署名、时长、录音标识、来源）。 |
| 录音级相同 | 两侧录音标识都有值、来源相同、标识相同。 |
| 文本级相同 | 见 3.1。只在录音级无法比较时使用。 |
| 提供者 | 组内**除目标发行以外**的某个发行里，与 s 相同的那条清单条目。 |
| 可判定 | 能对“该发行是否含 s”给出结论。见 3.3。 |
| 覆盖结论 | `provided` / `possible` / `unknown` / `absent_proven` / `absent_text` / `not_applicable`。见 3.3。 |
| 主发行 | 多个提供者时优先采用的发行。见 3.4。 |

## 2. 行为规则

### 2.1 自动导入（Runner → `library.SelectCandidate`）

自动候选集合、歧义检查、组解析（含 2.4 的修改）、选版先照旧执行。设选出的候选为 C，所在发行为 B。

- **A1 组不存在**：照旧，新建组与发行；多候选仍按总曲数较多者优先。
- **A2 B 已在库**（有曲目引用）：与 A3 走同一套解析步骤（含按需补取清单），区别只在结论的用法：`provided` 且主发行（3.4）不是 B 时改用主发行的那条清单条目；`provided` 且主发行就是 B、`absent_proven`、`absent_text` 时照旧准入 B（B 已在库，不产生新增成员确认）；`possible`、`unknown` 进复核 `song_unresolved`。（推论 2、12）
  - 原稿写的是“只用本地数据、不为此发请求”。这与 3.3 的闸门矛盾：清单默认懒加载，组内另一个发行的清单不完整时覆盖结论恒为 `unknown`，基线要求输入确认，自动提交必然被拒——修改 3 已经做到的“已有发行直接入库”会整体退化成复核。所以 A2 也要补取。
- **A3 B 不在库、组 G 已存在**——组内歌曲解析：
  1. 先让 G 内与 C 同来源、**有曲目引用**的发行（3.3 的参与范围）都具备完整清单：`tracklist_state` 不是 `complete` 的，取一次发行详情并用现有的 `ApplyReleaseSnapshot` 保存。请求失败按现有请求失败处理（退避重排），不进复核；取回后仍不完整则保持不可判定。
  2. 重新准备计划，读取基线里的覆盖结论：
     - `provided`：取主发行。主发行内恰有一条提供者就用它；有多条（同一录音出现在多个位置）时取碟号、音轨号与 C 相同的那条，取不到则复核 `song_unresolved`。“用它”= 用该清单条目构造曲目（与灰色行准入同一构造，library/service.go:218-239），带上导入条目与自动导入标记，重新走已拥有判重（佐证集合就是这一条，依赖 P3）→ 准入计划 → 提交。已拥有则 skipped，否则 imported，不产生新增成员确认。替换后的判重与后续动作见 2.1.1。提供者条目没有曲目标识时无法构造曲目，复核 `song_unresolved`。
     - `absent_proven`：s 是 B 独有。C 的原生组标识已经映射到 G（判组证据含 `native` 且不是新映射）→ 自动创建 B 并准入，不要求确认；否则复核 `new_release`。
     - `absent_text`：复核 `new_release`（证据不足以自动创建）。
     - `possible`、`unknown`：复核 `song_unresolved`，证据写明疑似提供者或不可判定的发行及原因。
- **A4 解析到多个组**：经 2.4 过滤后仍多于一个 → 复核 `group_conflict`（现状）。
- 自动路径永远不会带输入确认凭证。基线“需要输入确认”的计划一律不提交，复核原因记 `song_unresolved`（不是 `new_release`）。

#### 2.1.1 替换为提供者条目之后（执行前复核补充）

把候选 C（发行 B）替换成主发行 A 的清单条目后，下列四处都必须改用**替换后的身份**，否则会出错：

1. **已拥有判重不能拿 A 的专辑文本和位置去比输入。** 现有判定（matching/owned_import.go 的 `MatchOwnedInput`）要求专辑名、版本段、碟号/音轨号与输入一致。输入描述的是 B（例如“专辑（Deluxe）”第 2 碟第 3 首），A 的曲目必然不符，结果是：A 上那首歌已拥有时不会跳过，而准入基线又因精确曲目已存在把它送进 `ambiguous` 复核（runner.go:379）——正好是 D3 想消除的那次人工。规则改为两段证明：
   - 输入 ↔ 候选 C：用 C 自己的曲名、署名、专辑、位置、时长，按 `MatchOwnedInput(输入, C, exactRef=true)` 判定，必须有证据（rank > 0）。这与今天“精确绑定已在库”时的严格程度相同。
   - 候选 C ↔ A 的曲目：录音级相同，且 A 的该清单条目的曲目标识等于本地曲目的绑定。
   - 两段都成立 → `skipped`，证据类型 `group_recording_provider`，记录 C 与 A 两侧身份。第一段不成立 → 复核 `ambiguous`（现状）。
   - 这一步在一个存储事务里完成并重验（条目未终结、曲目绑定未变、清单条目仍在），不经过准入计划。
2. **补全**：`enricher` 用 A 的发行标识与提供者条目的曲目标识调用。沿用 C 的发行标识会在 `applySnapshotTx` 里因发行身份不一致被拒（snapshot_sync.go:94-108）。
3. **已解析身份登记**（`resolved_source/resolved_ref`，用于合并等价输入）：登记提供者条目的曲目标识。输入与候选上下文的一致性仍按 C 校验。
4. **日志与复核证据**：写明“由已有发行 A 提供”，并保留 C 的身份供排查。

请求预算：A3 对每个导入条目，最多为 G 内同来源且清单不完整的发行各发一次详情请求；同一发行成功一次后即为 `complete`，响应也有缓存。不会为不同来源的发行发起补取：跨来源成员保持不可判定或文本级可判定，自动路径不会因此自动创建发行（跨来源不自动，D9）。

### 2.2 交互入库（复核接受、搜索加入、灰色行、本地新建、编辑器、归组提议）

所有交互入口共用同一个计划与确认弹窗（frontend/src/stores/admission.ts、AdmissionDialog.vue；编辑器保存经 `SaveEdit` → `store.CommitEdit`，基线与批准校验相同，store/editor_save.go:201-204）。因此规则只在基线与弹窗实现一次。

**不替用户改选**：用户明确选择了发行 B 上的候选时，不静默换成 A；只把“使用发行 A”作为默认动作提供。

按覆盖结论分支（目标发行为 B，组为 G）：

| 覆盖结论 | 弹窗 | 进入 B 的条件 |
|---|---|---|
| `provided` | 标题“这首歌可由已有发行 A 提供”，展示提供者详情（5.1）。按钮“使用发行 A”（默认）、“创建发行 B”。 | 输入 `Yes` |
| `possible` | 同上，证据标注为“疑似：曲名与时长相同”。 | 输入 `Yes` |
| `unknown` | “无法确认组内已有发行是否包含这首歌”，列出不可判定的发行。前端自动发起一次“获取清单并重新预览”（推论 5）；仍为 `unknown` 时提供“创建发行 B”。 | 输入 `Yes` |
| `absent_proven` | B 不存在且原生组标识已映射到 G：不需要任何确认。否则是现有的“确认发行成员变化”。 | 普通确认或无 |
| `absent_text` | 现有的“确认发行成员变化”。 | 普通确认 |
| `not_applicable` | 无（组不存在等）。 | 无 |

- 目标发行就是主发行时不弹窗，例如点击“使用发行 A”之后得到的新计划。
- B 已经在库（不是新建）但不是主发行，或覆盖结论为 `unknown` 时同样弹窗，第二个按钮文案为“仍加入发行 B”，同样要求输入 `Yes`。（推论 1）
- “使用发行 A”：服务端基于当前计划重新准备，把曲目换成主发行的提供者条目（保留导入条目与条目终态），返回新计划；新计划若不再需要确认则直接提交。提供者是本地已有曲目时等同于复用该曲目。提供者条目没有曲目标识时按钮置灰并说明原因。
- 输入确认：服务端校验确认词去首尾空白后等于 `Yes`（区分大小写），通过才签发**用途不同于普通成员确认**的批准凭证；提交事务里“需要输入确认”的计划只接受这种凭证。前端的输入校验只用于启用按钮。
- 决定留痕：写入 `release_membership_decision`，并为（提供者所在发行，B）写入并存记录（4.2），供 2.3 排除。覆盖结论为 `unknown` 时没有提供者，改为对每个不可判定的发行与 B 写入并存记录——否则清单后到时，用户刚输入过 `Yes` 的这一对又会被提议归并。
- **闸门只针对“一首歌进入某个发行”**。下列计划的覆盖结论恒为 `not_applicable`：
  - 整个发行换组（归组提议、`MoveReleaseID`）：没有单首歌的归属变化，曲目相同的两个发行由 2.3 的归并提议处理。
  - 编辑器保存但曲目不换发行（只改字段）。
- **编辑器**：现在的编辑计划把曲目快照置空（library/editor_save.go:140、editor_impact.go:311-326），基线里拿不到歌曲。曲目换发行或新建发行（`migrates`）时，编辑计划必须在种子里带上被编辑曲目的歌曲事实（曲名、署名、时长、来源、录音标识——取曲目当前值与有效快照），仅用于计算覆盖结论，不参与写入；否则闸门在编辑器路径形同虚设。

### 2.3 迟到事实与归并提议（D6、D2）

- 发行清单同步为 `complete` 后（`applyReleaseSnapshotTx`），与同组、同来源、清单同为 `complete` 的其他发行比较（双方都要有曲目引用；空发行不提议）：双方每条清单都有录音标识，且录音的多重集相同（忽略碟序、曲序）→ 生成“发行曲目相同”的提议。
- 已有并存记录的一对、以及证据未变的已有提议（含已忽略的）不重复生成。
- 不自动改任何关系。本期提议只支持查看与忽略；“执行归并”（把 B 的曲目改绑到 A 的对应条目）会改写曲目标识并使已记住的输入确认关系失效，留到 4-tasks.md 的 4.23 单独评估。（推论 8）
- “集合相同”的判定只用在这里，以及弹窗里“发行 B 与发行 A 曲目完全相同 / 部分相同”的说明文字；不参与任何闸门。

### 2.4 判组（D11）

修改点在 `resolveGroupTx`（store/grouping.go:40-124）及其调用方。

1. **同来源原生组否决**：候选带原生组标识（来源 P、标识 g）且 g 尚未映射到本地组 x，而 x 已映射了来源 P 的其他原生组标识 → 名称证据对 x 的命中作废，x 不进入结果集。作废的命中保留在一个单独的“已否决证据”列表里，只用于展示和日志。
   - 结果集因此为空 → 新建独立的本地组，不进复核、不弹确认。自动路径与交互路径一致。
   - 迟到事实的归组提议（`proposeGroupChangeTx`）经同一函数，自然不再为这类情况生成提议。
2. **否定决定的记忆**：名称命中仍然成立时（跨来源，或有一侧没有原生组标识）照旧要求确认，弹窗增加动作：
   - 命中一个组：“加入该组”（现有）、“保持独立成组”（新）。
   - 命中多个组：“合并到此组”（现有）、“加入此组，不合并其他组”（新）、“保持独立成组”（新）。（推论 3）
   - 选择后两种新动作时保存否定决定（4.2）。否定决定是**两个本地组之间**的“不是同一组”：一侧是这次发行最终落入的组（新建的独立组，或选中的组），另一侧是每个未被选中的命中组。
   - 过滤规则：解析结果里存在**锚定组**（由原生组映射或“发行已在库”这两类强证据命中的组）时，与锚定组之间有否定决定的名称命中组被移出结果集，进入“已否决证据”。没有锚定组时不过滤（全新的发行仍会被询问一次，可以选“加入其中一组且不合并”）。
   - 原稿按“主体”（候选的原生组标识 / 发行标识 / 名称键）保存，有漏洞：用户让 QQ 发行在组 N 独立之后，再向同名 MB 组 x 的已有发行加歌，主体是 x 的原生组标识，查不到当初以 QQ 发行为主体存下的决定，于是每次都命中 {x, N} → 组冲突；x 内发行每次刷新快照也会重新生成归组提议。改成组对后两侧对称，两种情形都被过滤。
   - 之后若用户显式合并了相关的组，删除涉及这些组的否定决定；组删除时级联。
3. 提交时只有计划明确带合并目标才合并组。现在的实现是“命中多个组就全部并入目标”（admission_plan.go:246-264），需要改为受合并目标控制。
4. 候选之间的同组判定（`domain.SameGroup`，用于自动选版的连通性检查）本期不引入原生组否决。（推论 4）

## 3. 判定细节

### 3.1 歌曲身份

- **录音级**：两侧录音标识都有值、来源相同、标识相同。
- **文本级**，仅在录音级无法比较时使用（来源不同，或任一侧没有录音标识）：
  - 曲名按现有 `CompareTitle` 为精确（版本标记必须一致）；
  - 双方时长都已知时，差值在现有容差内（`DurationWithinTolerance`，3 秒）；任一侧未知时只看曲名；
  - 双方署名都有值时，`CompareCredit` 不得为不匹配。
- 同来源且双方都有录音标识时，录音不同即为不同歌曲，不再做文本级比较。（推论 7）
- 建议实现为 `internal/matching` 里的纯函数，供存储层计算基线时调用（存储层已经依赖该包）。

### 3.2 为什么文本级不用于自动决策（D1，必须写入规格与代码注释）

写入 `spec-diff.md` 修改 4 的 `matching/pipeline` 条目、3.1 的函数注释、Runner 自动路径调用处的注释，以及 internal/importer/README.md。要点如下，措辞可调整，含义不可缺：

> 当前自动导入默认只使用 MusicBrainz，而 MusicBrainz 为每条曲目提供可追溯的录音标识，所以自动决策只接受录音级相同。文本级相同（曲名、时长、署名）只是启发式证据，现在只在有人在场的交互路径里作为提示。
> 如果将来实现多来源自动导入（例如 MusicBrainz 无结果时自动切换其他上游搜索），其他来源没有录音标识，届时必须先实现判断文本级可信度的逻辑，明确哪些文本级相同可以自动入库，再放宽这条限制。

多来源自动导入与文本级可信度逻辑本期不设计、不实现，届时另立修改记录。

### 3.3 覆盖结论的计算

在存储层的准入基线里计算（`admissionBaselineTx`，store/grouping.go:197-294），事务内无网络，提交时重算并与计划比较。输入：计划中的曲目快照、目标组、目标发行。

参与范围：目标组内除目标发行以外、**至少有一条曲目引用**的发行（与修改 3 对“已有发行”的口径一致，含同步专属曲目）。没有曲目引用的空发行行不参与，也不为它补取清单——否则预览或迁移残留的空发行会让覆盖结论变成 `unknown`，把整组的入库都挡在输入确认后面；用户删光某个发行的歌之后，新歌也不该被吸回那个空发行。

歌曲 s 的来源：普通准入取计划里的曲目快照；编辑器迁移取 2.2 所述的歌曲事实；整发行换组与不换发行的编辑没有 s，结论为 `not_applicable`。

对参与范围内的每个发行 r：

| r 的情况 | 取证方式 | 结论 |
|---|---|---|
| 有上游身份，清单 `complete`，与 s 同来源，且 s 有录音标识 | 清单的录音标识 | 录音级可判定：有相同录音的条目即为提供者（证据级别“录音相同”）。 |
| 有上游身份，清单 `complete`，但来源不同或任一侧没有录音标识 | 清单的曲名、时长、署名 | 文本级可判定：文本级相同的条目为提供者（证据级别“疑似”）。 |
| 有上游身份，清单不是 `complete` | — | 不可判定。 |
| 没有上游身份（本地发行） | 该发行的曲目行 | 文本级可判定。（推论 6） |

汇总：

- 存在录音级提供者 → `provided`
- 否则存在文本级提供者 → `possible`
- 否则存在不可判定的发行 → `unknown`
- 否则全部发行都是录音级可判定 → `absent_proven`（组内没有其他发行时也是它）
- 否则 → `absent_text`
- 没有目标组，或 s 既没有录音标识也没有曲名 → `not_applicable`

提供者列表与不可判定列表要按稳定顺序输出，因为基线会参与计划哈希和提交时的相等比较。

基线上的闸门：

- 需要输入确认 = 这次提交会让一首歌进入目标发行（不是已存在的精确曲目，也不是 `not_applicable`），并且满足其一：覆盖结论为 `unknown`；或覆盖结论为 `provided` / `possible` 且目标发行不是主发行（3.4）。目标发行本身参与主发行排序，尚未建立的发行没有曲目引用，必然排在已有提供者之后。这样自动路径把歌曲替换到主发行之后，不会再被组内其他提供者挡住。
- 现有“需要确认”的条件（store/grouping.go:292）增加一个例外：覆盖结论为 `absent_proven`、没有组冲突、原生组标识已映射且不是新映射时，新发行加入已有组不需要确认（D4）。

### 3.4 主发行排序

排序对象是各提供者所在的发行，加上目标发行（若已在库）。有曲目引用的数量多者优先（含未入库的同步曲目，与修改 3 对“已有发行”的口径一致）→ 清单总曲数多者 → 发行行 id 小者（先建立）。

`selectCandidate` 里“多个已有发行候选”的排序（library/selection.go:102-121）同步改为把“曲目引用数”放在总曲数之前。（推论 2）

## 7. 实现推论与待确认点

以下做法用户没有逐条确认，执行前可以否决或调整：

1. 目标发行 B 已经在库时，只要组内其他发行能提供（或无法排除能提供）这首歌，交互路径同样弹窗并要求输入 `Yes`（按钮“仍加入发行 B”）。依据是 D10 的意图；若只想在新建发行时提示，去掉这一条即可。
2. 自动路径在 B 已在库时，若组内另一发行的曲目引用更多且本地清单已含该录音，改用那个发行；多个已有发行候选的排序把曲目引用数放在总曲数之前。这修改了修改 3 的规则，目的是让共同歌曲集中在一个发行。
3. D11 生效后同名而独立的组会并存，必须增加“加入其中一组且不合并”“保持独立成组”两个动作，否则没有原生组标识的候选只能把这些组合并。
4. 候选之间的同组判定不引入原生组否决。否则同名的专辑与单曲里的同一录音，会从“自动选版”变成“跨组复核”，复核量上升。
5. 交互预览遇到 `unknown` 时自动获取一次清单再重新预览。这是对“接受不发网络请求”（internal/app/bindings_review.go:241 的说明）的有限例外，只在组内存在清单不完整的发行时发生。
6. 没有上游身份的本地发行用它的曲目行当作清单，按文本级参与判定。
7. 同来源且双方都有录音标识时，录音不同即视为不同歌曲，不做文本级比较。重制版因此会被当作独有歌曲，可能自动建立第二个发行。
8. 归并提议本期只有查看与忽略。
9. P5 不实施。
10. 新增复核原因 `song_unresolved`。
11. `plan_stale` 连续重排的上限数值由执行者确定并记录。

以下 12–17 是执行前复核（4-why.md“执行前复核”）补上的，同样未经用户逐条确认：

12. A2（B 已在库）也按需补取组内同来源发行的清单，不再限定“只用本地数据”。
13. 覆盖结论只看有曲目引用的发行；空发行不参与、不补取、不生成归并提议。
14. 替换为提供者条目后，已拥有判重按“输入 ↔ 候选 C”与“C ↔ A 的曲目（录音级）”两段证明，补全、已解析身份、日志改用替换后的身份（2.1.1）。
15. 判组否定决定按“组对”保存，并以锚定组为条件过滤，取代原稿的“主体”模型。
16. 闸门只针对单首歌进入发行：整发行换组与不换发行的编辑为 `not_applicable`；编辑器迁移时由种子携带歌曲事实。
17. `unknown` 下输入 `Yes` 时，对每个不可判定的发行与 B 写并存记录。

- 名称近似的自动并组（P8 只做提示，见 4-tasks.md 的 4.14）。
