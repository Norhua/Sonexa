此文件由 apply 后所有修改会话共同维护。原 change 的 proposal/design/specs/tasks 保留规划基线；归档时须将 change delta 与本文件最终行为合并同步主规格，不把中间状态重复叠加。

## 修改 1：QQ 读取与完整构建

依据：[1-why.md](1-why.md) 中原始提示词及用户对过滤策略的明确选择。实现/验证见 [1-tasks.md](1-tasks.md)。

### `upstream/playlist-read` — 官方输入（实现修复/补充场景）

现有“支持 QQ 官方歌单详情链接”的要求不变，补充场景：

- WHEN 提交 `https://i2.y.qq.com/n3/other/pages/details/playlist.html?...&id=9385819575&...`
- THEN 离线解析为 `qq / 9385819575`，分享参数不影响去重；不请求用户 URL，不放行任意 QQ 子域名/路径，仍拒绝用户信息、端口、片段、重复或冲突 ID 参数。

### `upstream/playlist-read` — 完整性先于同步（用户批准的行为修改）

原要求仅容许可核对原始位置的非歌曲排除项，并规定歌曲缺失使整轮失败。修改为：

- 来源必须核对所有原始条目数量及分页覆盖；允许来源**明确报告稳定歌曲身份和已知类型**、但不提供歌曲详情的过滤项作为 `unavailable_track` 交付，预览明确显示数量、歌曲身份及原因；不得静默丢弃。
- 过滤项缺少原始位置时如实表示未知（协议 `Position=0`），不虚构原始位置；可读歌曲维持相对顺序。`TrackCount + ExcludedCount = RawSeen = DeclaredTotal` 仍须成立。
- 未知过滤类型、缺少稳定身份、无法解释的过滤计数、分页短缺/重复、真实总数/名称变化、业务限制、超限或取消仍整轮失败，旧快照不变。
- 首次绑定仅为可读歌曲建立导入需求，过滤项不补造元数据、不入队。

QQ 适配实现细节（不是业务中的平台分发）：

- 固定 CgiGetDiss / NoStore / 每页 1000（修改 2 将原 100 扩大），不加入自动端点回退。
- `total_song_num` 为扣掉**当前页** `filtered_song` 的值；加回本页过滤数后核对原始总数，`song_begin` 依原始项数推进。
- 普通歌曲以 `id/songid` 数字 ID 为同步 TrackRef，过滤项用 `songid`；仅 type 13 的明确歌曲过滤项可报告。
- 元数据 MID 绑定、导入匹配与人工接受语义不变。旧开发数据的 MID 同步键不做迁移；按项目早期数据重置约定，测试前清空旧数据或重建绑定，脚本不自行清空。

新增验收场景：同一歌单各页分别过滤 1/0 首，原始总数稳定时不误报“歌单变化”；1067 项示例交付 1064 首 + 3 个明确过滤项，而非把 1064 当作无过滤的完整成员集。

### `library/synced-playlists` — 已过滤歌曲不生成删除（新增保护场景）

- WHEN 新快照包含稳定歌曲身份的明确过滤项
- THEN 通用 Diff 按 `TrackRef` 保护该身份所有既有出现项，不将它们分类为上游删除；保持最后已确认字段、位置、upstream_present、local_state、track 引用及活动导入需求。
- THEN 不把历史缺席项自动恢复、不恢复 ignored、不创建新导入；重复出现无法定位具体副本时保守保护已有所有副本。
- WHEN 后续该身份可读
- THEN 按原有出现键复用；WHEN 后续已确认完整快照既不含该歌曲也不含对应过滤项，THEN 正常应用原删除策略。

过滤项的稳定身份由各 provider 提供，业务不解释 QQ 码、数字 ID 规则或 `switch source`。

### `platform/app-shell` / `library/synced-playlists` — 预览提示（补充场景）

绑定及刷新差异预览显示排除数量、稳定歌曲身份和来源原因。原位置未知显示“原始位置未知”，不显示“位置 0”；多个无位置排除项均可展示。

### `platform/sidecar-runtime` — 显式完整构建入口（补充构建要求）

原有“随应用交付、无运行时安装、固定路径、版本/完整性校验”的要求不变，增加：

- 仓库提供 macOS/Linux 的 `build.sh` 和 Windows 的 `build.bat`，共享 `scripts/build.py`。在已安装 Go、Node/npm、Python 3.14+ 和原生系统工具链后，一次命令自动准备哈希锁定 CPython/wheel、冻结 helper、前端/Go 依赖、Wails 编译、许可/资源装配和冻结自检；自动检测 `~/.go/bin/wails`，缺 CLI 时按 go.mod 版本安装到私有构建目录。
- macOS/Windows/Linux glibc 各 amd64/arm64 六个原生目标使用固定归档锁；拒绝交叉冻结。`--offline` 仅使用已有校验缓存，缺失即失败。
- 完整输出为 `build/release/<os>-<arch>/sonexa.app` 或 `sonexa/`，平铺产物包含 `resources/spotify-helper/`；不得只分发主可执行文件。
- 普通 `wails build` 仍只构建主应用，缺 helper 时明确不可用，不回退系统解释器；文档必须明确推荐完整入口。
- 自检在无 PATH 工具、无效 Python 注入变量、中文/空格路径下启动冻结 helper 并校验资源未变。macOS 另有 OS sandbox 和 ad-hoc 签名检查；Windows/Linux 无 OS 沙箱保证，未做原生验收的平台不得宣称发行通过。
- 不自动安装系统 SDK，不生成/声称已验收 NSIS/AppImage/DMG 或发行签名、公证。

## 修改 2：大歌单性能与复核/批次展示

依据：[2-why.md](2-why.md) 中提示词与复核率最终更正，执行证据见 [2-tasks.md](2-tasks.md)。

### `matching/pipeline` — 离线整理保持语义、避免无变化重复计算

- 读取复核或汇总前仍按全部 track 当前事实、有效快照、确认原文及候选证据离线整理，手搜保护、版本/位置/时长冲突、歧义、目标投递与最终写事务重验不变。
- 数据库持久化相关事实修订；同一修订已完成整理时，后续读取不再运行全量比较。相关写入（含另一连接）提交使缓存失效，回滚不更新已完成修订；封面/响应缓存等无关变化不重新整理。
- 曲名/译名保守索引只缩小需要比较的集合，不充当身份依据；所有活动输入候选集合取并集，保持每条输入独立消歧，不借首条输入消歧其他输入。
- 队列 DTO 完整性不变，输入/目标在只读快照批量查询；候选本地绑定/归属批量读取；任务计数不加载候选。同步列表及相关只读预览不占用 SQLite 写事务，实际修改仍原子提交。

### `upstream/playlist-read` — QQ 分页效率（实现细节修正）

QQ 页大小由 100 调整为 1000，1067 原始项由 11 次发送降至 2 次；沿用同端点、同共享桶与全部分页/过滤核验。字节、时间、发送、条目上限不变；短页不伪报成功、失败不回退接口。此次真实公开只读验证得到 1064 可读 + 3 明确过滤项，未提交应用数据库，不据此证明同步增删的在线验收。

### `import/table-import` / `matching/pipeline` — 历史批次布局与复核率（新增行为）

历史列表即使只有一个批次也可查看，列顺序为：**批次、状态、已导入、复核中、失败、复核率、目标、时间**。

- “已导入”是本批次新建成功的 imported 数，不宣称入库；重复仍保留 skipped 统计。
- “复核中”是当前 review 数，接受/移出后减少；failed 单列。
- “复核率”是本批次累计进入复核页的有效输入数 / 累计已处理有效输入数，百分数显示一位小数；点击该批次的值，在百分数与“分子 / 分母”间切换。分母为零显示“—”，比值模式显示“0 / 0”。
- review（含无匹配）及终止自动重试后进入复核页的 failed 都算人工介入；每次输入只累计一次。接受、离线跳过、移出、重新搜索、重试不抹除历史，不重复累计，重试也不缩小历史处理分母。
- 合并任务按每个仍有效输入保留自身批次归属，进入复核时累计这些输入；新输入合入当前 review/failed 同样累计。已撤销需求不再被别的共享任务重新计入；忽略恢复建立新输入尝试，按新批次统计。
- 目标独立成列，音乐库普通色、同步歌单显示名称及橙色，长名可完整换行。

验收场景：导入 15 首、处理 10 首，其中 7 自动导入、3 进入复核；人工接受 1 首后，历史显示 **8 已导入 / 2 复核中 / 0 失败 / 30.0%**，切换为 **3 / 10**。

### `platform/data-store` — 新历史事实及代际

`import_item.review_entered` / `processed_once` 通过事务内状态触发器单调保存，原文/分母不改写，重启保持、失败回滚。`review_revision` 随影响证据/队列的数据库写入失效。新模型代际为 `streaming-playlists-v2`；按项目早期约定，旧数据拒绝打开，用户测试前清空后重建，不伪造历史率、不自动清库。

### `platform/app-shell` / `review/review-queue` — 候选列宽与动作反馈

共享候选表支持拖动列边界调整宽度（expand），窄窗口横向滚动；标题、艺术家、歌集等长文本有全文提示，歌集含类型说明。接受处置期间显示忙碌并避免重复提交；同一轮同步事件合并读取，旧响应、手搜草稿和确认取消语义不变。

### `library/synced-playlists` — 大列表渲染

超过 200 项的同步列表使用 45px 行虚拟滚动，仅挂载可视窗口和余量；数据与操作集合不截断，排序/全选/上下文菜单仍基于全部已导入出现项。键盘 End/Home/箭头能滚动并聚焦对应真实行；重复出现的 entry key、上游缺席状态、按 track 去重入库不变，普通/专辑表格不受本次虚拟化阈值影响。

### 修改 2 的验收边界

离线大数据、数据库竞争、真实绑定及 Chromium/WebKit 自动测试不是原生 WKWebView 人工验收。QQ 仅公开只读，Spotify/跨平台冻结资源未变，不扩大原平台/在线验收完成范围。性能实测是本机合成数据及本次网络条件，不给任意曲库/上游延迟作保证。

## 修改 3：复核发行存在标记与全 track 已有发行优先

依据：[3-why.md](3-why.md) 中排查及用户本次修改请求，实施及验证见 [3-tasks.md](3-tasks.md)。本次不修改原生组/名称双路径归组规则，也不重做发行确认弹窗。

### `matching/pipeline` — 自动选版的已有发行范围（行为修改）

原 change design 第 7 节保留了“仅已入库发行优先”，实现改为：

- 仍先执行原高置信、非 ReviewOnly、三字段精确子集优先、组证据及曲目内容/录音、版本、同发行多位置歧义检查；本地发行存在不证明歌曲身份，不覆盖这些检查。
- 选版偏好中的“已有发行”是：当前候选的非空 provider + release_ref 精确命中本地发行，且该发行仍有至少一个 track 引用，**不论该 track 是否 in_library**。音乐库与同步专属发行同等参与，空发行、同名专辑、只有原生组相同或 recording 相同不构成此偏好。
- 有已有发行候选时在其子集中选版；唯一时不必补取用于比较的总数，多个时仍按总曲数、已知非世界国家、provider/release_ref/match_ref 的原顺序决策，无法取得必要总数则复核。没有已有发行时沿用原全部有效候选流程。
- 仍通过统一准入与原子投递。复用已有发行免新增成员确认，不代表绕过新组映射、组冲突、目标撤销或精确 track 输入核验；旧计划失效重新排队。新建 track 的入库归属由有效目标决定，不修改原有同步曲目归属。
- 不在复核读取或手动重新搜索后自动接受，不重新处理历史终态；此规则作用于 Runner 的自动处理/显式重试。

补充场景：

1. 库中无已入库歌曲，但同步歌单的一首其他歌曲引用发行 A；同组同录音有效候选来自 A/B，A 为已有发行而 B 未建立。自动选择 A，为当前歌曲创建 track 并投递目标，不创建 B、不要求新增发行确认。
2. A 在音乐库、B 仅在同步歌单，均包含有效同曲目候选：两者同等作为已有发行，再按原总数等规则比较，不优先 in_library。
3. 已有发行同时命中 CD/DVD 不同录音或同发行多个 track 位置：仍复核，不能因为“release 已存在”任取一条。
4. 已有发行候选属于低置信、ReviewOnly，或被三字段精确子集排除：不得恢复其自动资格；选定新发行仍执行新成员确认。

### `review/review-queue` / `platform/app-shell` / `matching/provenance` — 复核来源标记

- 复核候选来源列增加两个可同时显示的标记：`release group 已存在`、`release 已存在`。来源列默认加宽并保留拖动宽度、换行及完整提示。
- 标记分别查询同来源的原生 group_ref 映射、具体 release_ref 身份，范围是所有本地结构（含同步专属），不是仅音乐库。原生组身份未知/未映射时不借名称相同或已有发行所属组推断为已存在。
- 标记与现有“本地 + 上游”track 徽章独立，只有精确 track 命中才显示“本地”并提供跳过；仅发行/组存在的候选仍为接受，包括 ReviewOnly 候选。提示明确说明不代表已入库、不代表当前歌曲已存在或可自动导入。
- 自动候选快照、手动改搜返回及后续刷新采用同一实时本地投影，删除/换绑后清除旧状态，不从持久化候选布尔值沿用。前端仅复核显示新增标记，搜索/编辑表格不扩展展示范围。
- 后端 DTO 增加 `releaseExists`、`releaseGroupExists`；候选批量查询仍为单条只读 SQL，沿用精确身份索引，不对每个候选执行全库名称归组或加载完整快照。无需新增数据库代际。

本轮有 macOS arm64 完整构建/自检、QQ 只读大歌单及离线回归证据；没有 Spotify 真实在线歌单、真实已观察增删、Windows/Linux 原生执行或原生 UI 完整验收。不要因此勾选原 change 4.2/4.3/11.4/11.5 的全部验收，归档前仍需逐项处理这些边界。

## 修改 4：匹配状态机修复、判组否决与「同一首歌默认只绑定组内一个发行」

依据：[4-why.md](4-why.md) 中的排查结论与用户对 D1–D11 的选择，实施设计见 [4-design.md](4-design.md)，执行与验证见 [4-tasks.md](4-tasks.md)。以下是已实现并验证的最终行为；未实现的部分在“未实现与已知局限”里单列，归档时不得当作已有行为同步。

### `library/release-grouping` — 发行组的 Purpose 与判组（行为修改）

Purpose 由“允许同组多版本长期共存”改为：**曲目不同的版本可以共存；同一首歌默认只绑定组内一个发行**。同组里两个发行含同一首歌，只在用户输入确认词后才成立。

名称路径的两道否决（修改原场景“名称路径独立命中……不因原生组标识不同否决它”）：

- WHEN 候选带有某来源的原生组标识，该标识尚未映射到本地组 x，而 x 已映射了**同一来源**的其他原生组标识
- THEN 名称证据对 x 的命中作废，x 不进入判组结果；结果因此为空时直接新建独立的组，不进复核、不弹确认。自动路径、交互路径与迟到事实的归组提议一致。同名的专辑与单曲由此各自成组。
- WHEN 用户此前判定两个本地组“不是同一组”，且这次判组存在锚定组（由原生组映射或“发行已在库”命中的组）
- THEN 与锚定组之间有否定决定的名称命中组不进入结果。没有锚定组的全新发行不过滤，仍会被询问一次。
- 被否决的证据连同原因（同来源原生组不同 / 此前已判定不是同一组）保留在结果里，只用于展示与日志。

名称命中仍然成立时（跨来源，或有一侧没有原生组标识）照旧要求确认，并提供三种互斥的判组动作（修改“资料不足与多组冲突”）：

- 合并到某组：只有计划明确带合并目标才合并组，目标可以在命中组之外；被并入的组删除，相关否定决定随之清除。
- 加入其中一组，不合并其他组；保持独立成组（仅限发行尚未入库、不是整发行换组）。这两种动作都会按**组对**保存“不是同一组”的否定决定：一侧是这次落入的组，另一侧是每个未被选中的命中组。
- 没有任何命中、但去掉版本后缀或署名附注后同名的组只作提示，不改变判组结果，不自动并组。

候选之间的同组判定（自动选版的连通性检查）不引入原生组否决。

### `library/release-catalog` / `library/admission` — 组内歌曲归属（新增要求）

发行的存储身份不变（来源 + 发行标识唯一）。新增：一首歌要进入某个发行时，准入基线先回答“组内已有发行是否包含这首歌”。

歌曲身份分两级：

- **录音级**：两侧录音标识都有值、来源相同、标识相同。同来源且双方都有录音标识而不同，即为不同歌曲，不再做文本比较。
- **文本级**（仅在录音级无法比较时使用：来源不同，或任一侧没有录音标识）：曲名精确（版本标记一致），双方时长都已知时差值在 3 秒内，双方署名都有值时不冲突。

参与范围是目标组内除目标发行以外、**至少有一条曲目引用**的发行（含同步专属曲目）。没有曲目引用的空发行不参与、不为它补取清单。各发行的取证方式：有上游身份且清单完整时用清单；清单不完整为不可判定；没有上游身份的本地发行用它的曲目行按文本级参与。

覆盖结论：

| 结论 | 含义 |
|---|---|
| `provided` | 存在录音级相同的清单条目 |
| `possible` | 只有文本级相同的条目（疑似） |
| `unknown` | 没有命中，且有发行不可判定 |
| `absent_proven` | 没有命中，且每个参与发行都能按录音判定（组内没有其他发行时也是它） |
| `absent_text` | 没有命中，但有发行只能按文本判定 |
| `not_applicable` | 没有目标组、精确曲目已在库、整发行换组、不换发行的编辑，或拿不到歌曲事实 |

主发行排序：曲目引用数多者优先 → 清单总曲数多者 → 先建立者。提供者列表按主发行在前给出，目标发行（若已在库）参与同一排序。

两道闸门，在提交事务内重算并与计划比较，清单或成员一变计划即失效：

- **输入确认**：覆盖结论为 `unknown`，或为 `provided` / `possible` 且目标发行不是主发行。这类计划只接受“输入确认”类型的批准凭证；普通成员确认凭证、把一种凭证标成另一种，存储层都拒绝。入库提交与编辑器保存共用同一校验。
- **新增成员确认的放宽**（修改“向已有组加入发行需额外确认”）：新发行加入已有组时，若覆盖结论为 `absent_proven`、只命中一个组、候选的原生组标识**已经**映射到该组（不是名称路径命中，也不是这次才建立的映射），不再要求确认。其余情形照旧。

输入确认词是 `Yes`：服务端去首尾空白后逐字比较，区分大小写，通过才签发凭证；前端的输入校验只用于启用按钮。提交后写入决定留痕，并为这次落入的发行与每个提供者所在发行、每个不可判定的发行记下“允许并存”。

场景“发行边界：同组 CD 与数字版为两个发行”改为：两者含同一首歌时，第二个发行只在用户输入 `Yes` 后成立。“仅用户明确选择的候选参与交互入库，不自动更换版本”保持——交互路径只提供默认动作，不替用户改选。

### `matching/pipeline` — 自动选版与组内歌曲解析（行为修改）

- 检索阶梯只在候选池里已有可自动入库的候选时停止推进；仅供人工查看的候选不再截停阶梯（P1）。
- 自动候选要求曲名精确；模糊曲名只供人工（P4）。
- 多个已有发行候选的排序把曲目引用数放在总曲数之前（修改修改 3 的“多个时按总曲数比较”）。
- 选出候选后做**组内歌曲解析**：组内与候选同来源、有曲目引用而清单不完整的发行，各取一次详情并保存；请求失败按请求失败处理（退避、计次），不进复核。之后按覆盖结论处理：
  - `provided` 且目标不是主发行：改为准入主发行里的那条清单条目，不新建候选所在的发行，不产生确认。同一录音在主发行里出现多次时取碟号、音轨号与候选相同的那条，取不到则复核。
  - `absent_proven` 且满足上面的放宽条件：自动新建发行并准入。
  - `absent_text`、只经名称命中的组：复核 `new_release`。
  - `possible`、`unknown`、清单取回后仍不完整、提供者条目没有曲目标识：复核 `song_unresolved`（新增原因，文案“无法确认已有发行是否包含这首歌，需复核”）。
- 候选所在发行已在库时同样走这套解析：组内另一发行引用更多且含同一录音时改用它；主发行就是它自己时照旧准入。
- 自动路径永远不带输入确认凭证。
- `plan_stale` 连续重排加退避与上限（1 秒、2 秒、3 秒后转普通失败）；分组键带来源（P11）。

**文本级歌曲身份不用于自动决策。** 当前自动导入默认只使用 MusicBrainz，而 MusicBrainz 为每条曲目提供可追溯的录音标识，所以自动决策只接受录音级相同；文本级相同（曲名、时长、署名）只是启发式证据，只在有人在场的交互路径里作为提示。将来若实现多来源自动导入（例如 MusicBrainz 无结果时自动切换其他上游搜索），其他来源没有录音标识，届时必须先实现判断文本级可信度的逻辑，明确哪些文本级相同可以自动入库，再放宽这条限制。同样的说明写在 `matching.CompareSong`、`library.resolveGroupSong` 的注释与 `internal/importer/README.md` 里。

### `matching/provenance` — 已拥有判定（行为修改）

- 检索后的已拥有判定只用可自动入库的候选作旁证，选版后只用选中的候选；候选池大小不再决定同一首已拥有的歌是跳过还是复核（P3）。
- 手搜过的复核条目仍按原始输入与当前库事实离线收敛，不读写手搜草稿、候选快照与手搜来源（P6）。
- 候选被替换为已有发行的清单条目后，已拥有判定按两段证明：输入与候选一致（用候选自己的曲名、署名、专辑、位置、时长，与“精确绑定已在库”时同样严格）；候选与已有曲目是同一来源的同一录音，且该清单条目的曲目标识就是本地曲目的绑定。两段都成立则跳过，证据类型 `group_recording_provider`，记录两侧身份。已有曲目已拥有而第一段不成立时复核 `ambiguous`，不以已有身份绕过。
- 替换后登记的已解析身份、补全用的发行标识、日志与复核证据都改用替换后的身份；复核证据保留候选原本的身份供排查。

### `review/review-queue` / `platform/app-shell` — 确认弹窗与复核（行为修改）

所有交互入口（复核接受、搜索加入、灰色行、本地新建、编辑器保存、归组提议）共用同一弹窗：

- 覆盖结论为 `provided` / `possible` 且需要输入确认：标题“这首歌可由已有发行提供”，逐个列出提供者所在发行（标题、署名、来源与发行标识、已收藏数与清单总数）及其条目（碟号-音轨号、曲名、时长、证据级别“录音相同”或“疑似：曲名与时长相同”；已是本地曲目时注明“已有曲目，将直接复用”）。主按钮“使用发行「A」”；“创建发行「B」”（目标已在库时为“仍加入发行「B」”）点击后展开输入框，输入 `Yes` 才启用。
- “使用发行 A”由服务端基于当前计划重新准备，保留导入条目与条目终态；新计划不再需要确认时直接提交。提供者是没有上游身份的本地曲目时等同于复用该曲目；提供者条目没有曲目标识时按钮不可用并说明原因。编辑器保存与整发行换组不提供这个动作。
- 覆盖结论为 `unknown`：标题“无法确认已有发行是否包含这首歌”，列出不可判定的发行与原因；进入弹窗时自动获取一次清单并重新预览，失败给出原因并保留“重新获取清单”。这是对“接受不发网络请求”的有限例外，沿用补拉清单的出站闸门与交互优先级。
- 判组区块提供上述三种动作，并展示已否决与名称近似的证据；来源名取自证据，界面不写死任何上游。
- 带确认（含输入确认）的入库提交成功后，同一发行或同一目标组、未手搜、原因为 `new_release` / `song_unresolved` / `group_conflict` 的复核条目重新排队并由所属批次的驱动器继续处理（P2）。
- 复核页显示新原因文案，以及证据里的提供者、不可判定的发行、已否决与名称近似的判组证据。

### `library/browse-views` — 迟到事实（新增行为）

- 发行清单同步为完整后，与同组、同来源、清单同为完整且都有曲目引用的其他发行比较录音多重集（忽略碟序、曲序，要求每条清单都有录音标识）；相同则生成一条“发行曲目相同”提议。
- 已记为允许并存的一对不提议；证据未变的已有提议（含已忽略的）不重复生成。提议只供查看与忽略，不改任何关系。
- “多版本收藏：CD 与数字版同组且各有收藏，包括同一录音的不同收藏”成为例外情形：只在输入 `Yes` 后出现。专辑视图既有文案（“相同歌曲优先显示收藏，拆分后可查看各版本”）在新定义下仍然准确，未改动；灰色行加入曲库时若组内已有发行含这首歌，由确认弹窗提示。

### `platform/data-store` — 表与代际

- 模型代际为 `streaming-playlists-v3`；旧数据拒绝打开，不迁移。
- 新增三张表：发行并存记录（`release_coexistence`）、发行归并提议（`release_merge_proposal`）、判组否定决定（`release_group_separation`，按组对，任一组删除时级联）。
- 移除只写不读的 `release_group_match_key` 及每次准入、清单同步、编辑保存时的全量重建（P10）。
- 准入基线新增字段：覆盖结论、提供者列表、不可判定的发行、是否需要输入确认、已否决与名称近似的判组证据。批准凭证新增类型（成员确认 / 输入确认），按用途用不同前缀签名。

### 未实现与已知局限

- 设计 5.1 里“发行 B 与发行 A 曲目完全相同 / 部分相同”的说明文字没有实现：预览时候选所在发行通常还没有清单，给不出结论。
- “执行归并”（把一个发行的曲目改绑到另一个发行的对应条目）只做了评估，结论见 4-tasks.md 的 4.23：需要另立修改记录。
- P5（总数未知时的兜底）、P9（跨来源身份桥）、发行别名、跨来源自动解析、文本级用于自动决策、旧数据迁移均未实现。
- P10 的读侧没有解决：判组每次仍读取全库的名称证据，单次准入耗时随库规模近似线性增长（实测见 4-tasks.md）。本次只去掉了写侧的全量重建。
- 名称有差异（版本后缀、署名附注）而被分到不同组的发行之间不做歌曲解析；只有提示。
- 上游把同一首歌登记成两个录音时（常见于重制版），解析不到已有发行，会按独有歌曲处理并可能自动建立第二个发行。
- 验证范围：离线单元/场景测试与 Chromium、WebKit 自动化。没有调用真实上游，没有在原生 WKWebView 里人工验收，没有在 Windows/Linux 上执行。原 change 55/59 的平台与在线验收状态不因本次修改变化。
