# Design

## Context

动机与用户确认范围见 [proposal.md](proposal.md)。下表是最初规划时的源码基线，不代表实施至今的状态。阶段实现已增加模型、评分及部分来源适配，但仍通过 `Payload → DocumentFromPayload` 在业务侧完成组装；这条路径不符合最新确认的“上游返回完整规范化文档”，必须重构。历史实施记录中的 6.2 证据阻塞由本次允许受限启发式的决定解除，不代表算法或新交付契约已经实现。

## Goals / Non-Goals

**Goals:**

- 各上游能力实现成功返回前完成来源适配、原文选择、通道识别、规范化、合并和输出校验；业务侧只接受统一完整文档，不接收等待其收尾的原生内容或 Payload。
- 公共歌词模型/格式工具独立于业务编排和具体上游，供上游适配器复用；具体实现仅由应用装配层创建并经能力接口注入，来源规则不进入业务包或前端。
- 每份文档只确定一个原文主时间轴；统一模型同时生成可读行和唯一采用文本，两者不能各自拼接。
- 用共享合成语料验证 Go 序列化、前端显示及存储往返，不依赖联网证明解析正确。
- 保留有界、取消、不可变文本和修订提交，不为新格式引入持久化通道模型。
- 搜索、预取、预览、采用是四个独立状态；前端无需选中即可比较附加通道，但后台已下载不代表用户已审阅。

**Non-Goals:**

- 不移植 Lyrimuse 的完整引擎、播放同步、跨源歌词拼接、来源偏好、跨源内容共识或别名网络扩查；不下载每源全部 20 项，不在 Top 3 失败后自动补下一名。
- 不调用外部或系统翻译、生成模型、本地音译算法补造附加通道；不以删除职员表、长尾奏比例或语言偏好猜测来“改善”正文，不改变元数据匹配权重。
- 不新增本地二进制导入、YRC 文件导入、导出 UI 或历史数据迁移。

## Decisions

### 0. 上游完整交付与依赖注入

采用三层责任，而不是“provider 返回半成品、lyrics.Service 统一收尾”：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 具体上游 `internal/provider/<source>` | 请求、加解密、原生格式、业务码归一化、来源占位、协议回退、原文选择、通道识别；完成规范化、合并、序列化及输出校验后交付文档 | 候选业务分数、会话版本、预览批准、写库 |
| 公共工具 `internal/lyricdoc` | 统一行词/通道/文档类型；标准 TXT/LRC 解析、时间范围检查、等价 offset、保守对齐、去重、序列化、只读契约校验 | 网络、注册表、具体来源判断、业务调度、持久化；不能根据 source 字符串选择算法 |
| 业务 `internal/lyrics`、App 绑定及前端 | 匹配/内容评分、Top 3、预算/调度、会话、摘要、预览批准及采用 | 上游返回后的原文选择、通道分类、重挂时间、合并/去重/重写内容、解释原生错误码 |

调用与依赖方向：

```text
app/upstreams.go --creates/injects--> lyrics.Provider implementations
lyrics.Service --FetchLyrics(ctx, candidate)--> provider/<source>
provider/<source> --uses--> lyricdoc (pure model/format helpers)
provider/<source> --returns--> completed lyricdoc.Document
lyrics.Service --reads/validates only--> document --> score/session/adoption
```

歌词消费侧声明所需能力接口，保留在 `internal/lyrics`；各上游按自身支持的能力实现，获取签名改为返回 `*lyricdoc.Document`（或等价完整类型）。`Payload`、普通/逐字双原文等只可作适配器内部构建输入，不再跨能力边界；业务服务中删除 `DocumentFromPayload` 后处理入口，不能改名为通用转换器继续保留调用。公共工具可以复用同一套标准算法，但由上游实现于返回前调用；不得把这些工具留在带服务/注册表/评分的业务包中造成反向依赖。

成功文档必须同时含最终采用文本、选定原文及保留的附加通道毫秒结构、阅读行投影、真实格式、通道状态/依据及警告。多份投影只能来自同一构建结果，不能让业务重新解析字符串补结构。未知可选通道或通道部分失败允许连同有效原文成功返回；无原文、最终构建失败或超限返回统一错误，不返回“成功但待修复”的文档。

业务入口可调用不修改对象的契约校验：检查非空有效原文、时间/大小、文本与结构/状态的一致性；不合格直接拒绝，不能补默认通道、筛行、重新选择或重新序列化。评分只读取已规范化结构并计算数值，不改变文档。原生业务码由适配器映射为统一错误类别/停止语义，业务可按统一类别停止来源工作，不检查平台码或错误文案。

具体来源由 `internal/app/upstreams.go` 这一装配位置构造并注入能力集合；其他业务路径不得导入、类型断言或自行创建具体来源。来源 ID 仅用于登记、身份、展示、稳定排序和按键限额，不用于专有内容分支。`provider` 父包仅提供共用契约/传输设施，不反向导入业务包或具体上游；`lyricdoc` 不依赖这两类包。前端只读通用状态、格式和诊断。

本地 TXT/LRC 导入是独立的文件输入适配路径，可在进入统一业务前调用同一公共工具并保持 BOM/换行之外的原文保真；不得把本地解析入口复用于远程文档的二次内容处理。在线采用校验会话权限与契约后原样保存 `Document.Text`，详情渲染不回写。

**替代方案**：保留当前 Service 组装虽少改接口，却继续让业务承接来源未完成的工作；让每个上游复制解析/合并又会产生行为漂移。选择独立公共工具加上游完整交付，并用直接能力调用测试与生产依赖检查验证边界。

### 1. 两阶段评分、Top 3 预取与稳定排名

#### 1.1 第一阶段：歌曲匹配与候选选择

`rankCandidates` 继续使用 matching 默认分项和当前歌词准入/高置信规则，输出 `MatchScore`（0–100）、`MatchTerms` 和 `MatchNotes`。现有时长差超过 10 秒扣 20 分只计算一次，不在内容阶段重复扣歌曲时长差。所有值由后端计算，元数据配置仍不影响歌词默认权重。

每源先按 Source+Ref 去重，再按 MatchScore 降序、HighConfidence 降序、稳定歌曲身份升序冻结 Top 3。重复身份保留匹配分最高项，同分用确定性字段决胜；不足 3 项就取现有项，不补造、不分页，也不因失败/内容排名变化继续取第 4 项。其他已准入项仍在列表的未评分区域，保留人工获取。

后端生成不含下载 accesskey 的 `SortKey`，随机 `ID` 继续表示会话身份，不充当决胜键或允许跨会话采用。Go 与 TypeScript 使用同一字典序契约及 fixture，不依赖 locale 或网络完成顺序。

#### 1.2 第二阶段：已取得歌词的综合分

新增后端纯函数对当前候选的规范化原文和附加通道评分，不在前端另写质量判据。`TotalScore` 是可空有符号整数，只有原文有效才存在；不将未检查、无歌词或失败写成 0/-1 分来混入有效排名。`ScoreTerms` 的分项之和等于 TotalScore，显示为「综合分」而非百分比或正确概率。

初始公式（Sonexa 设计值，尚无线上效果验证，不照搬 Lyrimuse 的数值）：

| 分项 | 初始规则 | 含义及防误计 |
| --- | --- | --- |
| 歌曲匹配 M | MatchScore，0–100 | 先通过身份/版本准入；不能靠内容加分复活被过滤项 |
| 同步信息 S | `floor(10 × 有效计时原文行数 / 非空原文行数)`，分母为 0 时为 0 | 只数规范化主原文，不数翻译、元信息或重复副本；纯文本不扣分，只是不获同步加分 |
| 逐字覆盖 W | `floor(20 × 有效逐字覆盖字符数 / 原文字符数)`，分母为 0 时为 0 | 字符统一数 Unicode 字母/数字；只有一行含至少两个带非空文字且起点不同、顺序有效的词片段时才计该行逐字覆盖，不把整句套一个时间或全词同刻当精细逐字；终点未知不猜造，已提供终点须校验 |
| 翻译 T | 可确认且有效的上游翻译 +15，否则 0 | 可以未同步或部分提供；空、占位、错误、无法确认不加分，不按目标语种或语言偏好过滤 |
| 罗马音 R | 可确认且有效的上游罗马音 +5，否则 0 | 同样可未同步；来源声明与解析内容须支持该分类，谐音字不冒充罗马音 |
| 时间轴异常 P | 已知曲长下，有正文的原文行/词开始或显式词终点晚于曲长 5 秒以上，扣 30，一份文档只扣一次 | 比较 offset 后实际时间；未知曲长不扣，末句提前/尾奏长不扣；有该项则 `AutoPreviewEligible=false` |

`TotalScore = M + S + W + T + R - P`。不将总分钳制到 0，避免低分时吞掉翻译/罗马音增益；负综合分仍是有正文但质量较差，不等于无歌词。最多 150 分，同等其他条件下翻译增加 15、罗马音增加 5，二者叠加。例：M=90 的完整逐行无译文候选为 100；M=85 的完整逐行含翻译候选为 110，可反超；若再有完整有效逐字与罗马音则为 135。此处“完整”仅指已取得原文内的计时覆盖，不声称与真实演唱全文一致。

附加通道的“有”和评分可用来自上游完成文档时确定的同一个校验结果：来源提供、可成功解码、类型符合明确格式或第 3.2 节酷我受限规则、保留非空有效文字。业务不重新识别类型；酷我启发式命中仍标明推断，不声称有官方类型字段。无时间戳不是不可用；只有原文重复副本、来源占位或错误不冒充附加内容。部分文字仍有存在性加分并标注部分，不为加分删除或补写正文。原文无效时即使翻译齐全也没有可采用文档和 TotalScore。

借鉴 `match.go` 的实际内容/逐字/附加通道分项，但不引入它的播放器同源加分、按行数鼓励长歌词、跨源共识、仅同步译文可加分或仅日文罗马音加分。跨源共识在每源多条候选下还需防同源重复票，本轮不纳入，避免新增隐式依赖。

最终顺序：有 TotalScore 的项在前，按 TotalScore、MatchScore、HighConfidence 降序，再按来源 ID、SortKey 升序；未评分项置后，仅按 MatchScore、HighConfidence、稳定身份排列。两个区域不按来源分组。不管候选由自动还是人工获取，都用同一公式；点击已预取项不加分，文档版本改变才重算。

#### 1.3 预算、调度与异常收尾

用户触发一轮搜索后，各来源按冻结的查询快照独立执行“搜索→匹配→Top 3 预取”，不等其他来源搜完才启动本源预取。以下为初始工程预算，不新增设置 UI：

- 每源预取至多 3 项，四源至多 12 项。只计自动预取对象，不把“可用的三项”作为无限补取目标。
- 每源轮次从开始搜索起 60 秒，覆盖搜索、队列、配额等待、重试、下载和解析；单候选 40 秒且取较早 deadline。来源预算 context 是会话的子 context，到期只停止工作，不能使已完成文档立即失效；会话仍有创建起 30 分钟寿命。
- 每源每轮实际 HTTP 发送上限 16（含搜索、重试、重定向及回退），四源最多 64。上限不是要用满的目标；正常协议路径最多为网易云 7、QQ 7、酷狗 10、酷我 7 次。重复查询、来源重试各创建新明确轮次，不后台重开预算。
- 歌词获取使用进程级有界池，最多并发 4 项、同来源最多 1 项；各源 Top 3 按匹配顺序串行，避免同平台瞬间发出 3 组多步骤请求。继续复用平台配额，不因池存在而加额度。池等候可取消，关闭应用须等待已登记工作退出。
- no_lyrics 或单候选一般解析失败可继续本源剩余 Top 3；auth/rate_limit/TLS/too_large、出网禁用、轮次超时/耗尽则停止本源剩余项，已完成项仍可用。无论失败类型，都不自动补取第 4 项。
- 预算在实际发送层扣减一次，不能直接复用 `RequestGate` 的调用次数（它也在多处校验而非仅发送时调用）。为歌词 context 增加发送预算，重定向也记账及遵守共享配额；其他用途未携带预算时行为不变。429/认证等停止条件不得先被底层通用重试隐瞒，需歌词上下文的停止策略。
- 用户可选中排队/获取中的 Top 3，等待同一工作，不能重复 Fetch。未进入 Top 3 的候选在该来源本轮结束后才允许显式获取，每次只取一项，40 秒/8 次实际 HTTP 发送、同一个并发池和平台配额；成功加入综合排名，不触发邻项预取。来源仍受限制时禁止以人工入口绕过，明确提示。

预算到期或停止后，所有本轮排队项必须落为明确的 skipped/timeout/error 终态，显示原因和未确定通道，不能留在 loading。只有真正发起检查且失败的通道才设 error；未执行的通道保留 pending 并附停止原因，未能判断类型的已有文字为 unknown。结束状态不代表每项都成功：来源摘要分别给已搜索数、已选预取数、成功/无歌词/失败/未完成数。

#### 1.4 会话接口、事件与预览批准

保留独立来源会话和现有 SearchLyrics/FetchLyrics/AdoptLyrics 边界，新增 `StartLyricsPrefetch(sessionID)`（名称可随实际 API 风格调整）。SearchLyrics 在后端保存查询快照、匹配结果和 Top 3；Start 只使用服务端冻结名单，幂等，不能由前端提交任意候选集合或预算。前端收到搜索结果即发起 Start，不要求先选中。

后端用递增版本的 `lyrics:progress` 事件推送会话 ID、来源轮次、phase、候选摘要、通道状态、内容分项和文档版本；不把全部歌词正文随每个事件重复发送。监听在启动前建立，提供一次会话状态快照用于衔接事件，不以轮询维持进度；初始调用结果与后续事件按单调版本归并，迟到事件不能回退状态。规范化文档留在后端会话，用户预览时 FetchLyrics 读取现成文档，不再访问上游。内部新增逐候选 in-flight 合并，网络工作在锁外执行，完成时短锁校验会话并提交文档，取消不能被长时间网络锁阻塞。

采用必须使用同一份后端 `Document.Text`，并新增文档版本对应的 `PreviewedVersion`。预取不会设置该字段；前端成功显示有效选择的文档后，以 session/candidate/documentVersion 调用 `AcknowledgeLyricsPreview`，后端只接受仍存在的同版本文档。AdoptLyrics 校验该标记及原有目标修订；重新获取或替换文档会清空批准。桥接确认代表界面完成展示，不声称证明用户读过每个字。

自动预览等待所有当前来源搜索及 Top 3 进入终态，然后选全局综合顺序中 `HighConfidence && 原文有效 && !时间轴越界` 的第一项。无需最高综合分项一定高置信；没有满足条件的项保持未选。预取、排序事件和任何后来到达的候选都不能覆盖用户选择。用户选择尚未完成的项也算人工选择，后续不能自动跳走。

单源重试使用已提交查询快照，取消并替换该源的旧 session、预取、文档及批准，不影响其他来源。改搜索框而未提交不改变原轮次评分基准。来源重试状态和任何进度事件继续受 generation/job/session/sequence 校验。

**替代方案**：仅在模板显示 `store.cards` 无法获知未获取候选的翻译/罗马音，也无法进行内容排序；把所有候选并发取完会放大平台请求和内存；等待整轮结束才返回所有文档会妨碍部分结果及时展示。因此采用每源固定 Top 3、后端有界工作、摘要事件和按需读取已预取文档。

### 2. 结构化内存模型与唯一序列化文本

在独立公共包 `internal/lyricdoc` 定义与上游语法及业务会话无关的结构，建议形态：

```text
Word { startMs, endMs?, text }             // 有真实终点才填写 endMs
Line { startMs?, endMs?, parts[], text }   // text 为去控制标记后的完整正文
Track { lines[], metadata[], offsetMs, diagnostics[] }
Channel { track?, status, origin, syncStatus, diagnostics[], message? }
Document { text, format, rows[], original, translation, romanization,
           additional[], wordTiming, offsetMs, diagnostics[], warnings[] }
PreviewRow { timeMs?, text, channel, translation?, romanization? }

// 以下属于业务会话，不由上游创建
SessionDocument { document, version, previewedVersion }
CandidateSummary { matchScore, totalScore?, matchTerms[], scoreTerms[], sortKey,
                   fetchState, translationStatus, romanizationStatus, documentVersion? }
```

上游可在内部用 Track 或已解码的标准文本构建文档，但不把构建输入作为成功结果返回。所有原生 QRC/YRC/KRC 解析、格式选择和回退仍在各 provider 子包；公共工具只处理已经解释好的标准模型/文本，上游利用它完成合并及最终检查后返回 Document。原始 `Payload.Text` 的单能力来源同样迁移，不能成为绕过完整交付的兼容分支。

- 源时间用受范围检查的整数毫秒，单次数字加法前检查溢出；原生逐字时长必须非负，绝对时间采用现有 24 小时安全上限。
- KRC 相对词开始允许负数，只要换算后的绝对时刻有效，就保留词早于行首的事实；不能把 QQ 的“词必须位于该行区间”约束生搬给 KRC。绝对负时间或超限不钳制成假时间，报告逐字失败并走可用普通原文。
- 增强型 LRC 连续标签区分词结束和下一词开始；没有显式终点时不借下一词开始声称真实终点。空白片段保留正文和时间，不复制 Lyrimuse 为填色而延长前词的算法。
- 本地 `ParseText` 保持 BOM/换行处理与原始文本保真，不把新规范化强加为写盘重排；线上多通道与格式转换生成规范化合并文本。格式标签识别限定在对应语法位置，普通括号、`1 < 2` 和 HTML 样式文字不删除。
- 扩展多个行首时间戳后再按时间稳定排列；同时间、同可见文字且时间结构相同可去重，行级与逐字同文重复时保留含真实词时间的那项。不同词时间不能误当完全重复，重复副歌在不同时刻保留。
- `format` 基于最终可用内容；逐字状态基于选定原文的有效非空词，而不是看到一个 `<...>`、请求了 qrc 或只有罗马音带词时间。

仅 `Document.Text` 进入 `StageLyrics/SaveLyrics`；`rows`、各通道诊断、评分、文档版本、预览批准、解析中间对象和上游密文不入库。前端不能把纯正文回传作为采用内容。候选摘要只带状态和分项，不携带整份 Track；未选中时前端无需持有歌词全文。

**替代方案**：直接在 Vue 中去掉标签能短期改善显示，却无法解决上游绝对/相对时间、通道归属和重复序列化；单纯把三种格式统一转成 YRC 字符串又引入前端专用方言，不如通用模型加既有增强型 LRC 保存格式。

### 3. 返回前的通道关联与内容保留

#### 3.1 标准模型的保守合并

各上游在返回前选择原文，优先级为可用逐字原文 → 普通同步原文 → 纯文本，选一种，不重复输出 YRC 和 LRC 两套原文。普通轨作为回退及诊断依据留在该适配器本次处理中，业务不接收两套轨再选择。

独立附加通道仅在校正各自 offset 后的精确行时间可唯一归属时附到原文行；同刻多个原文导致归属不明时单独显示附加行。未匹配的有时间通道保留自己的时间；无时间文字放入非同步区。暂不采用 700ms 最近邻、按行号对齐或 LCS 自动重挂，避免重复副歌及不同断句被误配。

KRC language 是明确的格式内关联例外：先保留原始所有计时行（含空行），验证 language 行数，再将声明的行索引转换成真实时间。之后才筛空和排序。数量不符但文字有效时按附加轨原序保留非同步文本并警告；编码/结构损坏保持 error。type=0 不是天然“罗马音”：来源声明须配合有效拉丁音译文字才能确认，不能凭汉字比例推导出另一套音译。未能确认的类型保留为 additional 文本，罗马音状态为 unknown（无法确认），不是 unavailable，也不给罗马音加分。

所有翻译/罗马音仅来自上游，不注册翻译服务或本地生成模块。通道 origin 标明 independent/embedded/unknown；独立字段、明确内嵌格式或第 3.2 节限定启发式命中，经上游完成文档时的同一有效性校验产生状态、卡片摘要和加分依据，避免卡片显示“有”但评分忘记加分。未同步/部分内容单独记录 syncStatus/diagnostics，不影响确认存在性；无法确定语言类型的 additional 不假称为已确认通道。

酷我没有独立翻译字段时，按第 3.2 节受限规则识别；不再以“必须有明确类型字段”阻塞实现。未达到规则门槛不代表上游没有翻译，原始内容保留，翻译状态为 unknown。其他来源仍只使用各自明确格式，不自动应用酷我规则。

offset 处理作为公共规则：正 offset 表示提前，比较实际时间 `stamp - offset`；只在合并多轨时折算到同一轴，输出一个等价全局 offset，避免重复应用。无偏移/相同偏移保留等价含义；需要负实际时间时通过统一全局 offset 保持序列化标签非负，不截断句首。重复且矛盾或无法解析的 offset 作为格式诊断处理，不静默选择一个。时间列展示最终序列化行时间，与「原始文本」可核对；有非零偏移另提示。单文本导入不重写 offset。

**替代方案**：独立轨仍不以最近邻或语言比例强行重挂。酷我内嵌译文是有边界的例外，只改变经第 3.2 节识别的译文行归属，不改变原文或词时间。

#### 3.2 酷我两层受限启发式

规则在 `internal/provider/kuwo` 内实现，借鉴 Lyrimuse `adoptKuwoBakedTranslation` 的行为而不移植其源码或夹具。openapi/H5 共用同一处理；在来源行序尚未排序、去重之前运行，保留空计时行供相邻时间判断。存在无效时间或矛盾 offset 时禁用启发式，按已有规则保留整份普通文本并诊断，不先提取再丢失原序。

**行分类与输入**：仅计有有效时间的正文行；空行、元信息、可识别署名/版权声明不参与统计且不删除。F 为含假名/谚文的行，或不含汉字且至少两个 ASCII 拉丁字母的行；H 为至少两个汉字且无拉丁字母/假名/谚文的行；其余为混合行。外文歌曲辅助判据使用冻结候选的通用曲名/艺术家，不向业务索取平台参数：二者均有非空值且都不含汉字，或至少一半 F 行含假名/谚文。这里的字符分类仅是酷我识别依据，不是全来源语言偏好或评分项。

**第一层：整首交替检测**。F、H 各至少 8 行，H/F 在闭区间 0.7–1.3，至少 80% H 行的前一个参与分类行是 F，且满足外文歌曲辅助判据。门槛命中后，将可唯一关联到前面最近 F 行的 H 行移入翻译；同一原文后的多行译文保留各行文字，不吞并段落。紧随 F 的混合行只有其拉丁单词全部出现在该 F 中、去掉这些词后为 H 时才可纳入。没有前置原文、遇到有文字的署名/演唱标签、或原文归属歧义时保留该行不拆。

**第二层：酷我同下一行时间检测**。对第一层剩余行继续识别：中文候选紧跟一句 F，时间严格晚于该 F，并与后面第一条计时行完全相同；空计时行可作为后继证据。一句 F 最多认一行。中文候选可只有一个汉字；混合行须含汉字、无假名/谚文，且 ASCII 字母数不超过汉字数的一半，或全部拉丁单词来自该 F。“男：”“女：”“合：”等只有演唱标签的行不算译文，并切断关联；其他有文字的跳过行也切断。不得仅因为同刻有中文就认为它是上一句翻译。

未由第一层确认时，至少需要 4 个强匹配才采用第二层结果；强匹配不计原文仅为 Ooh/Yeah 等拟声的情况，也不计无后继的全曲尾行。第一层已确认则允许补提一行。全曲最后一条计时行仅在已有连续译文链、其对应 F 非拟声且不存在歧义时可跟随提取，不单独触发门槛。拟声/演唱标签的识别词表及混合文本边界用独立合成反例固定，不扩大成跨来源正文清洗。

**输出与评分**：识别先于最终文档构建和内容评分。命中行移到翻译通道，采用关联原文的行时间；不改原文、词起止、词间隔，也不生成新文字。文档记录 `origin=embedded`、`available`，同步/部分状态按实际保留内容给出，并附“启发式识别”诊断，包括规则版本、命中层及行数；关联记录保留来源行位置、原时间和归属时间供核对，受文档内存上限约束，进度摘要不广播正文。阅读和原始文本模式都使用同一已完成文档；“原始文本”指实际采用的规范化文本，不宣称是未处理的 HTTP 响应。有效原文下翻译按同一规则 +15，业务不按来源重判或再加一次分。

**保守边界**：未命中/有歧义的行留在原文或已归类的附加区，不重复输出也不丢正文；完全不能确认翻译则 unknown、无翻译分。不将版权/译者声明当成强证据或删除，保留文字但不计歌词翻译存在性。不开启 QQ/网易云/酷狗的通用交替行拆分，不接入 LRCX、机翻或音译。规则是经验推断，不声称官方类型保证；误判与漏判风险在诊断和验证记录中明确。

### 4. 默认阅读模式，原始模式只供核对

新增轻量可复用预览组件（例如 `LyricsPreview.vue`），搜索页使用 `Document.rows`，两列为行时间和正文；同刻可靠附加文本在正文下以次级样式显示。原始模式使用纯文字 `<pre>` 展示 `Document.Text`，不通过 HTML 拼接。默认模式每次打开为阅读，切换不请求后端。

`frontend/src/lib/lyrics.ts` 仍服务详情的纯文本展示，补充与后端一致的标签边界测试；不再靠“删除所有方括号/尖括号”扩展识别。将合成的 TXT/LRC/增强型 LRC fixture 作为 Go 与 TypeScript 共同语义基准。详情不需要知道 QRC/YRC/KRC，因为采用前已转换。

候选左栏和来源状态区分开，来源状态显示 searching/prefetching/done/partial/stopped 等阶段和预取完成数。卡片显示「歌曲匹配」「歌词综合」两种分数、可展开分项、格式，以及两个始终可见的翻译/罗马音徽标：available→有、unavailable→未提供、pending→待检查、loading→获取中、error→失败、unknown→无法确认。有非同步或部分内容时附短说明；通用诊断标明启发式时展示「有（启发式识别）」及依据，不在前端按来源 ID 判断或重跑算法。没有文档的 TotalScore 显示 `—`，不显示 0 或假置信百分比；尚未预取的其他候选位于同一列表末尾，明确「未预取，手动获取」。

状态与分数必须来自同一文档版本，预取完成事件一次性更新候选摘要；先前版本的失败不得覆盖较新的成功状态。已获取条目随新文档到达动态排序，但用稳定候选 ID 保持选择、键盘焦点和预览。长行换行，长列表和预览内部滚动，模式切换可键盘操作，不引入播放控件。

### 5. 四来源获取与回退

每个候选获取共享最多 40 秒 context；自动预取还受本轮来源剩余期限约束，来源结束后的人工单项使用独立的显式操作期限/预算，不复用已到期的工作 context。保留 NoStore、4 MiB 响应、2 MiB 解码/转换/合并限额和生产配额。下表每条候选路径同时用于自动预取与显式获取，不复制第二套协议；底层有限重试及重定向另消耗实际发送预算。缺失或失败的 Top 3 候选不会自动换成下一首歌曲。

| 网易云 | 首选 `GET https://music.163.com/api/song/lyric/v1?id=...&lv=-1&tv=-1&rv=-1&yv=-1`；可回退既有 WEAPI `song/lyric`，最多两个阶段 | 首选端点来自参考代码，实施时验证业务码、纯音乐标记、YRC、普通/附加轨和结构化署名；禁止把 GET 当作 WEAPI 加密请求，传输仍通过 provider.Client；不追加 EAPI/跨桶轮询 |
| QQ | 保持 MID 的一个 musicu 请求取逐字/普通两块，必要时一个 legacy 阶段 | 复用既有改造 DES，不换标准 3DES；QRC 提取先正常 XML，再对已知容器形态做唯一边界的受限容错；多轨确定性选择，不用横跨多个 Lyric 节点的贪婪表达式 |
| 酷狗 | hash 查候选 → 最优有效候选 fmt=krc → 必要时同候选 fmt=lrc，最多三个阶段 | 搜索解码补 song/singer，hash 路径不把上传者名强当歌手身份；仍检查可比较标题/版本、id/accesskey、时长；同分稳定选择。暂不增加去 hash 关键词补查 |
| 酷我 | 采用 `https://www.kuwo.cn/openapi/v1/www/lyric/getlyric?musicId=...` 的逐行路径；可回退已有 HTTPS H5 路径，最多两个阶段 | Referer 随主机，code 与 status 两种响应各自校验；新增许可主机仅为确认的 HTTPS 域名；不启用 mobi/LRCX 或 HTTP 路径 |

网易云 YRC 原生 `(start,duration,flag)` 在文字前，QQ QRC `(start,duration)` 在文字后，KRC `<relativeStart,duration,flag>` 在文字前；各自解析后输出统一模型，不能仅替换括号。网易云结构化署名仅按已识别 schema 还原文本，没有可靠时间则保留为非同步文字，不凭结构中未确认字段猜测时间。

QQ 各通道共享“解码后按实际格式分类”的纯函数；`crypt`、`qrc` 用来选择已知编码，不以反复尝试不同解码算法把损坏数据伪装成纯文本。QRC 容器无法确定边界时失败，正常纯文本不误判为 QRC。占位/提示识别只放对应来源，任何新提示过滤只在有明确来源语义和测试时新增，不删除真实署名或版权信息来假装歌词完整。

KRC 校验 `krc1` 后使用已知 XOR+zlib，严格 LimitReader(max+1) 检测超限；language 单独解 Base64/JSON，并受同样字节边界。原文有效而可选通道坏时只使该通道失败；整个响应/解压超限不得靠回退掩盖。

错误分类新增或沿用可由 `errors.Is/As` 判断的类别：no_lyrics、decode/format、unsupported_endpoint、auth、rate_limit、transport/TLS、cancel/timeout、too_large。只有明确可回退的缺失、格式异常或已确认端点不可用才启动下一阶段；限流/认证、TLS、取消、超限立即停止后续网络动作。QQ 同一响应已取得的普通块不算“继续请求”，可以保留，但必须附部分失败诊断。不得根据错误消息字符串包含某几个字决定是否绕过限制。

**替代方案**：完全照搬参考项目的备用域名、HTTP、失败即换桶等路径与 Sonexa 的安全规格冲突；保留所有旧端点不动则无法充分覆盖已识别的 YRC/KRC 和酷我逐行问题。

### 6. 验证分层和回归矩阵

- **公共模型/纯函数**：毫秒精度、BOM/CRLF、混合文本、多时间戳展开上限、重复副歌、空白/emoji/括号、偏移、同刻歧义、词开始/结束/间隔，解析→序列化→解析的文字和时间不变量。
- **QQ**：延伸现有 synthetic 密文生成器，补字面引号、动态轨名、多轨、附加通道 QRC、仅逐行/纯文本、损坏原文/附加通道及禁止回退分类。
- **网易云**：YRC-only、YRC 缺失/损坏、翻译错序、独立时间轴、结构化署名、占位及业务码、普通端点回退。
- **酷狗**：合法头/坏头、Base64/XOR/zlib 各失败及压缩炸弹、相对/负偏移、language 对齐含空行、行数不符、谐音轨不误报、候选标题冲突与时长选择、KRC→LRC 回退。
- **酷我**：两端点状态码形态、歌词缺失和错误区别、时长单位、非法时间全部保留、逐字未接入；两层启发式的 8 行/比例/80%/4 强匹配边界，中文歌外文段、单字/混合译文、拟声、尾行、演唱标签、同刻合唱、声明保留、偏移、歧义不拆；同样输入交给其他来源不触发酷我规则，摘要/翻译加分/原文计数与结果一致。
- **交付与依赖边界**：直接调用每个来源的能力即取得可显示/采用的完整文档，不借业务服务补齐；单能力 fake 注入、错误文档拒绝且不修复、已完成文档经评分/预览/采用不改变内容。AST/依赖检查覆盖业务、装配例外、公共工具和 provider 父包，禁止具体来源导入、专有分支及改名隐藏的后处理。
- **匹配/内容评分**：准入后 Top 3 冻结、重复身份去重、M/S/W/T/R/P 分项与总分、翻译 +15/罗马音 +5、非同步和部分附加文字、总分可负、未知通道无加分、内容反超匹配分及版本不能复活、短词/长尾奏不误罚。
- **调度/预算**：3×4 候选、60 秒来源期限与 40 秒单候选期限、每源 16 次含跳转发送、进程并发 4/同源 1、Top 3 失败不补第 4 项、来源停止不阻断其他源、人工单次 8 请求、取消等待和应用关闭排空。
- **集成/前端**：进度事件与快照竞态、同分稳定、两个分数字段、两种通道徽标未选即可见、人工选择不丢失、摘要版本与文档一致、已预取预览不出网、未经预览采用拒绝、旧批准不能采用新版本、修订冲突保持旧文件、Chromium/WebKit 可读性。

默认测试使用独立构造的短文本和 mock HTTP，不把参考仓库的整首歌词纳入测试库。真实网络按 README 现有显式开关和 `internal/app/lyrics_sources_test.go` 的有界入口扩展；原在线总预算若小于生产轮次预算，以较小者为准，不能因 Top 3 自动抬高 probe 授权上限。记录候选/请求数、内容分项及通道摘要，遇限制停止，不输出 accesskey、请求正文或歌词全文。离线通过、真实来源成功和原生 UI 验收分别记录。

## Risks / Trade-offs

- **非公开端点变化** → 实施先补契约夹具，再运行显式有界 probe；验证失败作为来源风险或阻塞报告，不悄悄切换不安全路径、不宣称四来源已通过。
- **QRC 引号容错吞入下一轨** → 正常 XML 优先，容错仅处理可唯一界定的已知容器片段，多轨/截断/恶意边界有专门测试。
- **YRC 与 LRC 不同时间轴** → 不自动猜测重挂，未对齐附加内容保留原时刻；接受部分译文展示不紧邻原句的代价。
- **KRC 音译轨语种不明确** → 保守标作未分类附加文本，保留文字并警告，而非假称罗马音。
- **Top 3 增加网络量与等待时间** → 固定候选预算、逐源串行、60 秒整轮上限和发送计数，摘要事件渐进展示；未完成不当失败歌词、不自动补取下一名。
- **初始内容权重未校准** → 分项固定且可解释，用翻译增益、版本过滤、纯文本、长尾奏与时间越界反例回归；记录实际样例结果，后续改变权重必须同步基准，不宣称直接复用 Lyrimuse 即可靠。
- **预取误充当用户审阅** → 文档版本批准与采用分离，预取不设置 PreviewedVersion；后端测试直接调用采用必须拒绝。
- **酷我启发式误判/漏判** → 固定两层门槛和来源范围，先保留原序再识别，增加真正双语/合唱/拟声反例；命中仍标推断依据，歧义保留，不把经验规则说成官方保证。取消“必须先取得类型字段”的实现阻塞，在线样例只补充效果证据，不替代合成验收或放宽预算。
- **业务继续补做上游工作** → 接口不再返回 Payload，公共工具独立成包，直接能力调用覆盖完整结果；业务契约检查只能拒绝而不能修复，补生产依赖与调用链测试。
- **字符串与结构同时驻留增加内存** → 前端仅接收摘要并按需读文档，来源完成文档后释放原生响应及构建临时对象；保留评分必需的规范化原文结构与受限诊断，不保留第二套原文。每来源会话文本、结构/关联记录和行投影累计最多 32 MiB，进程全部歌词会话最多 128 MiB；超额显式拒绝新文档而不驱逐正在预览的版本，不截断内容。既有 32 会话上限与 30 分钟有效期仍保留。
- **前后端排序或标签规则漂移** → 共享 fixture 和完全相同排序契约；采用始终使用后端会话文档。
- **安全错误导致回退次数减少** → 这是有意约束，优先明确失败而非规避认证/限流；普通块已经可用时仍显示诊断并保留可用内容。
- **GPL 参考及依赖风险** → 不直接复制 Lyrimuse 实现/夹具；沿用 Sonexa 已存在的 qrcdes 及其许可证说明，新实现不增加 GPL 运行时依赖。

## Migration Plan

1. 无数据库迁移；不改写既有歌词文件或用户数据。按项目早期开发约定测试可使用清空后的数据，但不能自动清库。
2. 首先将已实现公共模型/格式算法提取至独立工具包，迁移所有来源及 fake 到完整文档返回，删除业务 Payload 组装路径并验证注入边界；旧算法测试继续复用。再落实酷我两层启发式、补齐来源及评分回归，随后接入预取、版本批准和前端。`matchScore/totalScore`、摘要及预览 API 随桌面端同步生成，不维护旧桥接协议。任务勾选只代表已完成部分，接口重构及新增场景需重新验证。
3. 实施完成后更新 README 和当前架构/缺口文档的已交付内容；规格同步/归档另按工作流完成，不在提案阶段改写主规格。
4. 如需回滚，回退应用代码及生成绑定即可；已采用的 TXT/LRC/增强型 LRC 文件仍属于原有可读取文本格式，不需要迁移回滚。
