# Proposal

## Why

Sonexa 的歌词搜索直接展示增强型 LRC 原始标签，逐字起止时间挤占正文；后端和状态层虽已评分，页面仍按来源分组，用户无法按匹配程度比较全部候选。现有通道模型与格式转换也不完整，需要参考 Lyrimuse 的实现补齐网易云 YRC、酷狗 KRC，并保证可读展示不损失保存内容。

## What Changes

- 搜索采用两阶段流程：每个来源最多搜索 20 个歌曲候选，先按曲名/版本、艺术家、专辑和时长的匹配分过滤、去重并取 Top 3，自动获取原文及上游附加通道、统一格式，再按歌词综合分跨来源排序。四来源每轮最多自动预取 12 份候选歌词，不按来源分组。
- 保留现有歌曲匹配准入、默认权重与高置信条件；新增歌词内容评分，考虑实际同步/逐字信息和时间轴异常，有效上游翻译额外加分，罗马音给予较小加分。分别展示歌曲匹配分、综合分及结构化明细，不按来源品牌或请求速度加分，不让内容加分挽救身份/版本不符的歌曲。
- 候选卡片直接显示真实歌词格式、翻译和罗马音状态，区分有、未提供、待检查、获取中、失败和无法确认；不要求逐个点开预览才知道附加通道情况。未预取候选保留手动获取入口，不参与已获取歌词的综合排名。
- 仅获取上游已提供的翻译和罗马音，缺失时不调用翻译服务、模型或本地音译算法生成；独立通道、明确内嵌格式以及本变更限定的酷我启发式命中内容均需保留，无法确认归属时保留文字及诊断，不谎报缺失。酷我借鉴 Lyrimuse 的整首交替检测与“译文同下一计时行时间”补充检测，识别在酷我适配器内完成，附启发式依据及时间关联诊断，不泛化到其他来源。
- 搜索预览默认展示可读歌词行，行时间放在独立列，逐字标签不插入正文；提供「原始文本」切换以核对实际采用的合并文本。详情页继续只显示正文，隐藏标签不改动保存文件。
- 引入独立于业务编排和具体上游的公共歌词模型/格式工具。各上游能力实现在成功返回前完成原文选择、通道识别、规范化、合并、去重及序列化，交付一致的最终采用文本、毫秒行词结构、预览行、格式和通道诊断；业务侧不接收待组装的 Payload，不再补做歌词内容处理。保留 Unicode、标点、空白及真实词时间；独立附加轨不按行号猜配，酷我命中的内嵌译文允许按限定规则重挂行时间并标明推断依据。
- 明确依赖注入边界：能力接口由消费业务侧声明，具体来源按支持的能力实现，由应用装配层创建并通过接口/注册表注入；业务包只负责查询、评分、调度、会话和采用；来源协议及专有规则不得进入业务包、前端或共用传输设施。公共格式工具供上游复用，业务入口只能对已完成文档做不修改内容的防御性契约检查。
- 网易云新增 YRC 获取和解析，保留普通 LRC 与附加通道回退；酷狗优先获取 KRC，解析相对词时间及内嵌语言通道，失败时有界回退 LRC。QQ 完善 QRC 容器/通道格式识别与普通歌词回退；酷我完善逐行获取、状态报告和异常时间处理。
- 预取有候选数、并发、请求预算和整轮期限，仍共用现有 HTTPS、配额、响应/解压大小及单候选 40 秒获取限制。成功文档只保留在受限内存会话；自动预览等待当前搜索及预取结束，按综合分选择具备资格的高置信候选，人工选择优先，预取本身不算预览或采用。

用户已确认参考项目是 `tmp/lyrimuse/`，`tmp/lrc-change/` 的两份调查仅作历史线索；格式扩展包含网易云 YRC / 酷狗 KRC，不包含酷我 LRCX。当前流程以「每源 Top 3 预取 → 内容综合排序 → 翻译加分、罗马音较小加分 → 候选卡片显示两种通道状态」为准，替代此前按需取词、仅匹配分排序的方案。本次规划修订进一步确认酷我受限启发式与上游完整文档交付边界，替代原先禁止此类启发式和业务侧组装 Payload 的设计；已有实现须按更新后的任务重构，本次修订不执行代码修改。

## Capabilities

### New Capabilities

无。新增格式仍属于现有独立歌词搜索能力，不拆出重复的歌词能力目录。

### Modified Capabilities

- `upstream/lyrics-search`：两阶段评分、每源 Top 3 有界预取、跨来源综合排名、卡片附加通道状态、仅消费上游翻译/罗马音、可读预览与会话隔离；新增完整文档交付、酷我受限启发式、YRC/KRC 解析及可靠回退要求。
- `upstream/provider-registry`：强化业务能力调用契约，明确上游差异由上游实现封装、应用装配依赖注入及禁止业务侧补做来源处理。
- `upstream/qqmusic`：同一获取契约支持预取和显式获取，完善在线 QRC 容器及各通道实际格式识别；不改变元数据链路和匿名 MID 请求方式。

## Impact

- 后端：从 `internal/lyrics` 提取不依赖业务服务或具体来源的公共文档模型/格式工具，歌词能力改为返回完整文档；`internal/provider/{netease,qqmusic,kugou,kuwo}/` 内完成来源适配与文档构建。`internal/lyrics` 保留内容评分/预取调度等业务，`internal/app/upstreams.go` 负责装配注入，`internal/app/bindings_lyrics.go` 集成候选/预览 DTO、进度事件、版本及预览批准。扩展依赖边界和单能力替身测试；实际请求计数仅作用于带歌词预算的上下文，不修改其他用途配额语义。
- 前端：`frontend/src/stores/lyricsSearch.ts`、`frontend/src/views/LyricsSearchView.vue`、`frontend/src/lib/lyrics.ts`，以及必要的可复用歌词预览组件；更新 Wails 生成绑定及 Go、Vitest、Playwright 回归。
- 文档：实施后按真实交付更新 `README.md`、`openspec/design.md`、`openspec/known-gaps.md` 的格式限制及验证入口；本提案不提前覆盖主规格或宣称在线接口已验证。
- 存储仍采用 UTF-8 不可变合并文本，不新增数据库通道表；本地仍仅导入 TXT/LRC，不导入二进制 QRC/KRC 或原始 YRC。
- 不增加歌词来源、播放器、高亮动画、自动翻译/音译、跨源正文混搭、自动采用、独立导出界面或元数据评分变更。
- Lyrimuse 为 GPL-3.0 参考项目：借鉴行为、协议与边界，按 Sonexa 架构独立实现，不直接移植其代码/夹具或引入运行时依赖。非公开接口的最新可用性必须在实施阶段以显式启用的有界验证确认。
