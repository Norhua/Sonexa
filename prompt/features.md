# Sonexa 功能清单（v1）

本文件是功能维度的简明索引。技术约束、数据模型、算法细节与页面规范见 `start-prompt.md`。

约定：每个功能统一为 **目标 / 范围 / 关键规则 / 验收 / 非目标** 五段，每段力求一到三行。

---

## F1 曲目库管理

**目标** 管理用户的全部音乐收藏，收藏的存在不依赖本地音频文件，也不依赖上游匹配成功。

**范围** 两层字段：基本信息（曲名 / 艺术家 / 专辑名，结构稳定，永不增删字段）与丰富信息（详情展示与未来写标签所需的全部字段，结构可演进）。

**关键规则**
- 每首曲目必有基本信息；丰富信息可以整体为空（如「无需匹配」入库的条目）。
- 丰富信息逐字段记录来源（`provenance`）与用户锁（`locked`）；用户改过的字段不被上游自动覆盖。
- 曲目可被删除；删除同时清理其歌单/标签关联与艺术家关联。`release` 曲目清单不受影响——该位置在专辑视图中回落为灰色行。

**验收** 丰富信息为空的曲目在列表页与详情抽屉中都能正常显示（缺失字段显示 `—`，不报错、不空白）。

**非目标** 本地音频文件扫描、播放、写入音频文件内部的元数据标签（v2）。

---

## F2 歌单与标签

**目标** 让用户用两种方式组织收藏：有序的歌单，与扁平的标签。

**范围** 歌单/标签的增删改名、把曲目加入/移出、按歌单或标签筛选曲目。

**关键规则**
- 后台同一套模型（`collection` + `collection_item`，用 `kind` 区分），前端两种呈现。
- 歌单有序（支持拖拽），标签无序。
- 「全部曲目」是虚拟视图，不占 `collection` 的行。
- 加入歌单/标签只在库内进行（曲目表格多选 + 工具栏/右键）；搜索页与复核队列不提供该动作。

**验收** 一首曲目可同时属于多个歌单与多个标签；从歌单移出不删除曲目本身。

**非目标** 智能歌单/规则歌单、歌单嵌套、歌单封面。

---

## F3 艺术家与角色关系

**目标** 把「一首歌的所有参与者」结构化，使角色名与声优各自可被浏览到。

**范围** 演唱者（含虚拟歌姬）、器乐演奏者、作曲、作词、编曲、制作、混音、指挥、角色；专辑艺术家；曲目级与发行级主要艺术家署名。

**关键规则**
- 关系表存储（`artist` / `artist_link` / `track_artist`），不用 JSON。
- 署名原串（`track_credit` / `album_credit`）单独存为文本列，原样保真，不由关系表推导。
- `角色名(CV:艺人名)` 解析为两个艺术家 + 一条 `voice_of` 关系 + 两条 `track_artist`，同时保留原串。
- 括号语义需先分类（版本标识 / 翻译 / CV / 歧义消解），不可无脑剥离。

**验收** 对 `涼宮ハルヒ(CV:平野綾)` 这首歌：搜索 `平野綾` 与搜索 `涼宮ハルヒ` 都能返回它；详情抽屉「参与者」区按原串 `涼宮ハルヒ(CV:平野綾)` 展示，其中两段分别可点击进入两个歌手视图，两个视图都包含这首歌。

**非目标** 艺术家详情页（简介 / 头像 / 外部链接）、同一艺术家不同写法的合并、艺术家别名表。

---

## F4 本地搜索与浏览视图

**目标** 在库内快速定位曲目，并提供艺术家、专辑两个浏览维度。

**范围** 快速搜索（单框，作用域跟随当前视图）、高级搜索（曲名/艺术家/专辑分别条件 + 年份区间 + 标签 + 载体/国家/类型）、艺术家视图、专辑视图（含未入库曲目的灰色行）。

**关键规则**
- 本地搜索结果不跳页，在当前曲目表格内筛选，顶部出现可清除的筛选 chip。
- 艺术家视图 = 按 `artist_id` 过滤的曲目表格，支持按 `role` 分面。
- 专辑视图基于 `release` 表（上游曲目清单的镜像）：显示该专辑的**完整**曲目，未入库的以灰色行呈现，计数为 `已入库/总数`。
- 分组键三级降级：release group → 单个 release → 派生分组（无上游标识的曲目，此级无清单也无灰色行）。
- 灰色行不是曲目：不可多选、不打开详情、不参与导出、不进全文索引；动作只有 `[加入曲库]`（已有上游标识，可直接带溯源入库）。
- 专辑至少拥有一首曲目才出现在列表中——灰色行用于补全已开始的收藏，不是上游目录浏览。
- 曲目清单在首次打开该专辑时懒加载（可在设置中改为匹配时拉取），不阻塞已入库曲目的渲染。
- 高级搜索面板上有 `[到上游搜索 →]`，把已填条件带到上游搜索页。

**验收** 高级搜索的三个字段可任意留空；留空字段不参与条件。一张 12 首的专辑仅入库 8 首时，专辑视图显示 12 行（4 行为灰色）并计数 `8/12`；删除其中一首后该行变为灰色，计数变为 `7/12`。

**非目标** 全文模糊排序调优、搜索历史、保存的搜索；专辑级的用户数据（评分 / 收藏状态）；浏览完全未拥有的专辑。

## F5 上游 Provider 抽象

**目标** 让所有需要上游信息的地方面对同一套接口，具体上游可增删替换。

**范围** v1 落地两个：MusicBrainz、iTunes Search API。接口与注册表设计需容纳后续新增上游。

**关键规则**
- 统一 `Provider` 接口 + registry；所有「选上游」的 UI 从 registry 动态渲染，禁止硬编码。
- 每个 provider 声明 `Capabilities()`，UI 据此决定某列显示 `—` 还是隐藏。
- 每个 provider 一个全局共享限流器（搜索 / 导入 / 详情共用一个桶）。MB 1 req/s，iTunes 约 20 req/min。封面图片服务（CAA / mzstatic）不在桶内，由封面工作池的并发上限约束。
- 所有字段可空；缺失即为缺失，不用空串或零值伪装。
- MB 请求必须带 `User-Agent: Sonexa/<版本> ( <联系方式> )`；未配置联系方式时禁用全部出网。

**验收** 新增一个上游只需实现接口并注册，无需改动任何页面代码。

**非目标** Apple Music API（需付费开发者账号，推后）、Discogs / Last.fm 等其他上游。

## F6 上游搜索

**目标** 让用户在上游按曲名/艺术家/专辑检索，并把结果直接加入曲库。

**范围** 独立页面。可选上游（多选，含聚合），聚合结果以标签页分组呈现。

**关键规则**
- 三个输入字段可任意留空。
- 结果粒度是 **track**（recording × release × medium × 位置），不是 recording。
- 各上游独立 loading 状态，谁先返回先显示。
- 结果行动作只有 `[加入曲库]`；已在库中的行显示 `[已在库中]`（可点击跳转）。

**验收** 同一首 recording 在多个 release 上时，作为多行分别列出，各行的载体/国家/年份/曲序不同。

**非目标** 在搜索结果上直接加入歌单、批量加入。

---

## F7 封面获取

**目标** 让列表快而详情清，且不因追求画质拖慢浏览。

**范围** 三个使用场景：详情抽屉（高质量）、上游搜索列表（缩略图）、复核队列列表（缩略图）。

**关键规则**
- 自动获取时，图片来源跟随该条结果的来源：MB → Cover Art Archive，iTunes → iTunes 图片地址。
- 列表缩略图约 250px；详情抽屉取可得的最高质量（含降级链）。
- 详情抽屉支持手动重新获取：用曲名/艺术家/专辑向**所有**上游查询，结果按置信度排序，同一来源的多个规格收拢为一条并标注规格。
- iTunes 只提供 `3000 / 1200 / 600 / 100` 四档；选中时先验证可用性，失败自动退档。
- 列表缩略图进临时 LRU 缓存（有 TTL）；详情抽屉确认采用的图片按内容哈希落盘并记录来源。
- 缩略图**并发获取**：一个进程级工作池，默认 8 并发（可调），上游搜索列表与复核队列列表共用。取图不占 provider 的 API 令牌桶（CAA 与 mzstatic 不是受限端点，CAA 的 JSON 索引同理）；但 iTunes 的图片地址来自 search 响应，那次 search 照常占桶。按缓存键合并并发请求，视口内优先，滚出视口未开始的任务取消。
- 图片字节由 Go 取，经 Wails 的 AssetServer handler 以本地 URL 供 `<img>` 加载，不经 IPC 桥 base64 回传，也不由前端出网。

**验收** Cover Art Archive 无图（404 是常态）时显示占位图，不阻塞其他列渲染；25 行的结果列表不会因逐张串行取图而长时间空白。

**非目标** 封面编辑（裁剪 / 上传本地图片）、多张封面（背面 / 内页）的完整管理。

---

## F8 表格导入

**目标** 从表格文件批量建立收藏，尽量不让用户手动配置。

**范围** CSV / TSV / XLSX。自动探测编码、分隔符、表头、列映射，预览后提交。

**关键规则**
- 自动探测优先：顶部一行显示「已识别: UTF-8 · 逗号分隔 · 含表头 [调整]」，点击才展开手动控件。
- 探测置信度低（编码 < 80%，或未能映射到「曲名」）时自动展开手动面板并高亮。
- 预览至少展示前 20 行，并统计将被跳过的行（如缺少曲名）。
- 提交后窗口关闭，条目进入匹配队列并自动开始。
- MB 联系方式未配置时，导入入口禁用。

**验收** 一个常见的 UTF-8 逗号 CSV，从选文件到可提交无需任何手动设置。

**非目标** 从剪贴板/文本框导入、导入时直接指定歌单、增量同步。

---

## F9 匹配流程与置信度

**目标** 让能自动确定的条目自动入库，不能确定的交给用户，且过程可中断可恢复。

**范围** 本地去重检查 → 上游查询 → 置信度评分 → 分流（直接入库 / 进复核 / 出错重排）→ 统计输出。v1 导入阶段只用 MusicBrainz。

**关键规则**
- 每个上游可用不同的置信度算法，但满分与「高置信」的判定标准一致，保证跨上游可排序。
- 「高置信」是结构性条件（曲名对上 **且** 署名或歌集至少一处精确匹配），不是单纯的分数线。
- 多个高置信且同属一个 release group 时，按确定的 release 优选阶梯选一个，结果对同一输入必须可复现。
- 输入含翻译/异写括号时生成查询变体；采用渐进式策略（原串无高置信才试变体），避免吞吐降为四分之一。
- 5xx / 429 / 超时走指数退避重排队，尊重 `Retry-After`，满 5 次标记失败不再重排。
- 队列持久化，可暂停与恢复，重启后继续。

**验收** 导入结束输出统计：本次导入 / 进入复核 / 未匹配 / 失败各多少条，随后逐行列出所有失败条目的原始输入。

**非目标** 音频指纹匹配、机器学习打分、并发多上游查询同一条目。

---

## F10 复核队列

**目标** 用一个统一界面处置所有需要人工判断的条目。

**范围** 逐条浏览。上半展示可编辑的原始输入与条目动作，下半展示候选结果列表。

**关键规则**
- 单一界面，不按进入原因分成多种界面；`待选 / 匹配中 / 失败` 只是状态标签。
- 候选来源以徽章标注；库中已有且上游也存在时同时标注两个徽章。
- 上游为单选下拉，默认 MusicBrainz；选 iTunes 时才出现地区下拉（带脚本探测建议）。
- 改写搜索条件只影响本次查询，不改动条目的原始导入值。
- 条目动作：`[无需匹配]`（按原始输入入库，溯源置空）、`[删除记录]`；候选动作：`[接受]`、`[合并]`（命中库中已有时）；列表底部 `[无一匹配]`（保留在队列，可换上游再试）。

**验收** 「疑似重复」不需要独立界面：库中已有的曲目作为一条候选出现在同一列表里，动作为 `[合并]`。

**非目标** 批量处置、复核规则自动化。

---

## F11 编辑与重新匹配

**目标** 让用户完全掌控每个字段的值与来源。

**范围** 一个编辑页，同时展示基本信息与丰富信息两组字段。

**关键规则**
- 重新匹配上游**只能**在这里发起，其他任何地方不自动重新匹配已入库曲目。
- 逐字段呈现「当前值 / 上游值 / 操作」；`source = user` 的字段默认不勾选填充并显示「用户」徽标。
- `[全部填充]` 默认跳过用户锁定项。
- 填充后该字段来源改为对应上游并清除用户锁；用户手改则置为 `user` 并加锁。
- 匹配溯源（来源 + 上游唯一标识）在此可手动修改或置空。

**验收** 用户手改过年份后重新匹配上游，年份不被自动覆盖，且界面明确提示可手动选择填充。

**非目标** 批量编辑多首曲目、编辑历史与撤销。

---

## F12 导出

**目标** 让用户能把收藏带走。

**范围** 格式 CSV / JSON；范围 全库 / 当前歌单 / 当前筛选结果 / 选中项；可选「仅基本信息」或「基本 + 丰富」。

**关键规则** 不打包封面图片（来源版权各异）。导出文件默认 UTF-8 with BOM，便于 Excel 直接打开。只导出已入库曲目，专辑视图中的灰色行不参与。

**验收** 导出后的 CSV 可被本应用的导入功能读回，且列映射自动命中。

**非目标** M3U / 播放列表格式、导出到流媒体平台。

---

## F13 设置

**目标** 集中所有需要用户配置的项，且明确标出哪些是出网的前置条件。

**范围** 常规 / 上游 / 匹配 / 导入导出 / 缓存 / 关于。

**关键规则**
- MB 联系方式是必填项；未填写时全局禁用出网（导入、上游搜索、封面获取），并在首次启动引导中要求填写。
- 匹配阈值、release 优选偏好、重试上限等算法参数可调，且有明确默认值。
- 上游列表从 registry 渲染，每个上游一个配置分组。

**验收** 首次启动时若未填联系方式，所有出网入口均为禁用态并给出统一的原因说明与跳转设置的入口。

**非目标** 配置导入导出、多配置档案。

---

## F14 匹配溯源与去重

**目标** 用记录而非猜测来判断「库中这首」与「上游这条」是否同一个。

**范围** 丰富信息上的 `match_source` + `match_ref` 两个字段，及其唯一约束。

**关键规则**
- 赋值时机：上游搜索加入、复核队列接受、导入自动入库、编辑页重新匹配确认、用户手填标识。
- 置空时机：`[无需匹配]`、用户在编辑页手动清空。
- `match_ref` 取值：MusicBrainz 用 **track MBID**（不是 recording MBID）；iTunes 用 `{country}:{trackId}`。
- 判定顺序：标识相同 → 同一个；否则 ISRC 相同 → 同一个；否则仅对**没有溯源标识**的曲目做文本标准化后的模糊比对，且结果标为「疑似」交用户确认。

**验收** 同一条上游结果不会被重复加入曲库；从上游搜索添加已在库中的曲目时，按钮显示为 `[已在库中]`。

**非目标** 跨上游的自动实体统一、模糊去重的自动合并。
